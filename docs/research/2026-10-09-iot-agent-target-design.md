# 物联 Agent 目标设计与能力证明

日期：2026-10-09。状态：设计与验证方案；首条照明提案隔离候选已实施并完成四情境诊断，完整Agent可靠性未证明。用户认可此前缺陷诊断，但尚不能据此相信整体设计和交付能力；本文件补齐正向设计及其可被反例否定的条件。

基线：mp `8e741b5`、Runtime `b5736f3`。沿现行双 Agent 来源、Task/Plan/Occurrence、显式确认和后台执行规则。既有调查见[设计审查](2026-10-09-iot-agent-design-audit.md)和[外部源码](2026-10-09-coding-agent-reliability-primary-sources.md)。本文件不扩展持续控制、条件自动化、人员识别、告警处置或模型自主执行权限。

## 要交付的产品能力

一个好的物联 Agent 应让用户用业务语言完成委托，而不必替系统找查询条件、拼设备 ID、理解调用顺序或维护任务 JSON。

它要在正常业务中完成五种判断：准确理解对象和范围；取得足以决策的事实；把目标变成可执行且可审阅的安排；在多轮补充和纠正中保持委托一致；依据真实结果解释完成、失败和下一步。

例如“工作日下午六点关公共办公区的灯，走廊留着”包含空间关系、设备角色、重复安排和排除项。模型可以结合真实目录推理，但不能把“走廊留着”扩写成“自动开走廊灯”，不能用自己的办公区常识替代目录成员，也不能擅自决定是否包括法定节假日。工作日按当前已认可的周一至周五规则解释，提案显示该口径。若用户只说“六点”且上下文不能判定上午/下午，应问清时刻。

好用还包括节制：目录已有的答案自行取得；真正影响结果且无法从事实判断的歧义才问用户。查得出、改得动、结果可信，与权限约束同时成立。全拒绝和全猜测都不合格。

## 明确模型与业务模块各自负责什么

| 问题 | 模型的职责 | 业务模块的保证 |
|---|---|---|
| “这里的主灯”是哪台 | 结合用户措辞、当前页面和真实候选理解语义；不够明确时消歧 | 返回足够名称、位置和引用；不会用查询失败扩大来源 |
| “把后者改成五点” | 理解指代与变更作用域，继承其他已明确目标 | 引用当前对象，读取权威版本；保护历史与在途快照 |
| “关灯，走廊留着” | 判断包含/排除含义，不自动补相反动作 | 验证每个操作目标和能力，显示实际影响集合 |
| “舒服一些” | 识别目标尚未形成明确设备设定，取得可用环境/空调事实并给建议 | 不把设定温度当室温；不允许模型声称会持续维持舒适度 |
| “执行失败怎么办” | 根据具体失败事实解释、区分是否需要新操作 | 回执、未知结果、权威回读和未执行项分别保存，不盲目重放 |
| “最近能耗为何变高” | 判断所需证据、统计口径和解释限度 | 没有历史接口时不能由最新瞬时功率计算电量变化 |

模型负责语言和有证据的判断；授权、引用解析、参数合法性、对象版本、确认、调度、幂等和回执属于代码保证。确定性业务校验不等于用固定流程替代 Agent。

## 对话承接的设计

要区分三种信息：

1. **用户表达与选择**：哪个目标仍在讨论，哪一组已选，什么已被排除，修改只影响本次还是周期。这些信息可从对话形成有限工作上下文，但模型理解仍可能出错。
2. **证据**：查过哪些真实设备，名称/位置/能力是什么，是否完整、何时读取、有哪些未知项。证据必须能通过稳定引用继续取得。
3. **权威业务状态**：提案是否已退役、任务是否已确认、哪个版本可修改、哪个检查点已执行、报告属于哪次发生。由业务存储提供，不能由聊天摘要决定。

继续使用原始历史和现有持久对象；模型窗口中的有限视图不能另变成任务数据库。新一轮可以重新生成提案，同时保留尚未解决的用户目标；已完成或取消对象不自动恢复成待执行安排。

关键设计要求是每条可影响后续操作的信息都能追到原用户表达、原查询或权威对象。引用只定位讨论对象，不自动授权，也不预设用户想修改。原始对话的保留、模型投影和业务授权是三件事。

不先建通用 Goal 表或对话状态机。先验证现有历史、候选引用和对象上下文能否承担；确有稳定选项映射缺口时，再加入服务端校验对象引用的小型澄清记录。普通问答不强制物化为计划。

## 工具接口应提供怎样的环境

采用 codebase-design 的原则：调用方只需学习少量业务概念，来源绑定、解析与强制校验由模块内部处理。以下是语义契约，具体工具名和 schema 在实现前冻结，不承诺立即合并或改名。

| 工具用途 | 模型需要表达 | 返回应足以支持什么 |
|---|---|---|
| 发现对象 | 用户的范围、类型和对象描述；硬范围与软相关性清楚分开 | 相关设备与必要位置，真实匹配依据、覆盖边界、稳定引用和继续读取路径 |
| 取得事实 | 已有设备、Task 或 Plan 引用，所需状态/能力/报告 | 当前授权下的事实、来源、时间、未知项；无需重搜整个目录 |
| 准备操作或任务 | 目标引用、目标值、时间/重复规则，以及明确排除项 | 完整验证后的提案，或具体可修正问题；生成提案没有设备副作用 |
| 准备修改 | 对象引用、预期版本、修改作用域和所需变化 | 合法的新版本差异及实际影响；保持未修改部分和历史事实 |

不是必须减少到四个工具。现有 `find_device_candidates`、`read_device_states`、`get_task`、`propose_task` 等可以继续使用。要减少的是隐藏顺序依赖与无关负担，而不是按工具数量判断质量。

几个接口层面的具体取舍：

- 名称描述不应默默成为授权或强过滤条件，但真正命中应出现在明细中；命中引用必须有可取得的完整记录。查“格栅灯”与只列“26楼前十台”需要有实际区别。
- 用稳定目标引用准备提案。服务器保存其来源和发现证据，重新绑定当前目录；逐台要求模型同时维护设备句柄、候选集关系和已核验状态，能在模块内完成的应收进去。修改外部参数前需兼容已有历史和恢复。
- 提案模块自动执行必要的能力、目标、时间和版本校验。只有模型需要能力事实来选择方案时，才单独读取能力；不依赖固定工具前置顺序。
- 错误要区分目标不可见、对象歧义、能力不支持、目标参数非法、版本已变、时间已过、上游不可用。只给“失败了”或立刻关闭所有工具，会消除修正机会。
- 原始完整集合、显示分页和单次批准动作限额分开。不会因屏幕只展示少量设备就要求模型重新猜位置，也不会把前一页默认为用户要的全部。
- 不新增任意客户接口调用工具，也不提供设备控制工具；模型不能借更灵活的工具绕过现有确认边界。

## 用一个完整委托检验设计

下面是预期行为推演，**不是实际运行记录**。目标是在已有的设备控制与周期任务范围内验证跨轮一致性。

用户：“工作日下午六点关公共办公区的灯，走廊留着。”

Agent 检索当前来源中的公共办公区和走廊事实。如果存在多个公共办公区且当前页面不能唯一确定，展示真实名称/位置并询问；不能静默选第一个。如果已唯一确定，取得设备集合和能力后直接准备待确认计划。走廊设备排除，未安排额外开灯。下面承接的是实际列出两组选项的分支；没有两组选项时，“第二个”必须先澄清。

用户：“第二个，改成六点半。”

Agent 承接同一条关闭目标，选择前文第二个办公区，把时间改为18:30，保留工作日规则和走廊排除；需要时补读对象事实。合法的再次查询不算失败，不要求用户把全部指令再说一遍。计划卡展示实际设备、18:30、周一至周五和排除说明。

用户确认后：“今天先别执行，以后照常。”

Agent 读取计划与今天发生的权威状态。尚未落实际 Task 时提出跳过本次；已经落账但未结束时提出取消本次尚未执行部分；不直接停用整个周期。两种情况继续沿现有对象规则，而非根据“今天”关键词固定调用某个工具。

第二天用户从结束消息打开报告：“为什么这盏没关？再试一下。”

Agent 用同一次报告区分拒绝、未执行、已受理未核验与结果未知。需要判断现在状态时重新读取；已经达到目标就说明无需再操作。结果未知且缺乏可核验现态时，不能盲目重复下发。可以准备合法的新提案，但必须明确这是一次新操作，不能把历史确认当新授权。

这个委托检验设备消歧、排除、时间、周期语义、当前发生、结果追问和新操作边界。第一轮能生成卡片只是其中一小部分。

## 哪些证据才能增加交付把握

| 需要证明的能力 | 可观察证据 | 什么不能替代它 |
|---|---|---|
| 业务设计连贯 | 同一委托经过选对象、改时间、跳过、报告追问后，语义仍一致 | 分别挑选互不相关的成功截图 |
| 模型能使用工具 | 真实模型在固定目录/协议夹具上完成多轮目标与恢复 | faux model 预先指定工具调用 |
| 设计能迁移 | 更换设备名称、位置、数据顺序、用户表达后，仍选择对应目标 | 为原句追加同义词或“后者”特例 |
| 能正确承认未知 | 缺历史能耗、缺实时状态、目标不唯一时给有限且有用的回答 | 全部拒绝，或用不存在事实补全 |
| 真正设备闭环可用 | 用户在明确场景确认后，真实下发、回读、报告与页面可追问 | 模型说成功、接口200、只有模拟器数据 |

先用当前模型和冻结协议夹具，把原失败、上述完整委托及必要反例跑成可检查的真实模型轨迹；保留未参与设计调试的变体验证迁移。根据结果再做模型与工具版本的同条件对照。重复次数、成功标准、成本和延迟预算在实际实验前固定，失败全部保留，不能只汇报最好的那一次。

以目标设备集合、操作语义、时间/周期/编辑作用域和结果事实为主要判断；工程测试另行保证来源、确认前零下发、版本和幂等。正常场景的便利性与需要澄清场景的克制同时验证，不要求固定调用顺序。

按单个真实闭环推进实现，设计检查跨场景迁移；不同时重写所有设备。先做“正确选择照明并形成定时提案”，继而检查同样工具/上下文修正是否适用于排除和多轮修改。通过一条闭环只证明该闭环；完整周期/报告场景需要自己的验证记录。
