# Agent 工具错误恢复：一手规范与重试边界

- 日期：2026-10-24
- 访问日期：2026-10-24（Asia/Shanghai）
- 范围：核对 MCP、Anthropic、LangGraph、OpenAI Agents SDK 以及官方工程文档对工具失败、模型回流、框架重试和写操作幂等的定义。本文只记录外部一手来源与由其支持的工程判断，不修改业务代码。

## 结论

用户关于“工具或工具卡片失败不应过早直接抛给用户”的判断，对**模型仍能修正的失败**成立：参数校验错误、缺少必填参数、工具选择错误、可替代的只读查询失败，以及已执行但只缺展示转换的失败，都应先作为结构化结果回到 Agent loop，让模型选择修正参数、换工具、补充澄清或诚实收尾。

但社区一手材料没有形成一条“所有错误都必须交给模型”的统一强制标准。MCP 只规定协议错误与工具执行错误的消息分层，并明确协议不规定具体用户交互模式；Anthropic、LangGraph 和 OpenAI Agents SDK 都把“是否将错误交回模型、捕获哪些异常、是否直接使运行失败”做成各自的实现或配置选择。因此，本项目应采用**按错误类别决定回流、重试、核实或终止**的策略，不能把“回流模型”当成通用异常处理器。

对于有副作用的写操作，超时或连接断开不能证明没有执行。必须先依据操作 ID/幂等键查询状态或回读；只有服务端明确提供幂等保证时，才可以安全重试同一写请求。授权失败、权限边界、需要人工确认和执行结果未知时，模型可以解释和请求下一步，但不能通过再次调用绕过服务端裁决。

## 规范如何区分错误

### 1. MCP：协议错误与工具执行错误不是一回事

MCP 的基础协议采用 JSON-RPC：响应必须包含 `result` 或 `error` 之一，协议错误至少有整数错误码和消息。当前 Tools 规范把未知工具、格式不符合 `CallToolRequest` 的请求、服务端错误列为协议错误；工具已经被调用但下游 API、输入值校验、业务规则或执行过程失败，则放进正常工具结果并设置 `isError: true`。规范明确指出，工具执行错误包含可操作反馈，客户端 **SHOULD** 将其提供给语言模型以便自我修正和用调整后的参数重试；协议错误也可以提供，但成功恢复的可能性较低。

这仍然不等于“所有错误都给模型”：规范规定消息形状和安全边界，却明确实现可以采用不同用户交互模式。协议没有规定必须重试、必须再次调用、必须展示卡片，也没有规定模型在错误后的循环次数；`SHOULD` 是工具执行错误的互操作性建议，不是对授权失败、未知副作用或程序崩溃的无限重试授权。

### 2. Anthropic：错误结果是 Agent loop 的一次观察

Anthropic 的客户端工具流程是：模型给出 `tool_use`，应用执行工具，再以匹配的 `tool_result` 继续发送给模型。执行异常可以带 `is_error: true`；文档明确模型会把错误纳入后续答复。缺少必填参数的例子直接回送错误结果，文档说明 Claude 会用修正后的信息重试 2–3 次，之后才向用户道歉。

这支持以下有限规则：

- 参数形状、缺参、可从上下文补齐的工具选择错误，优先回流模型。
- 只读工具的瞬时错误可以回流模型，由模型改用替代查询、缩小范围或说明暂不可用。
- 只有在错误连续重复、达到循环预算、没有可用替代工具，或错误本身属于授权/副作用/程序级问题时，才进入终态。

“2–3 次”是 Anthropic 对该场景的文档行为说明，不是跨模型、跨框架的通用标准；项目应按自己的模型、工具和风险设定合适的上限并保留终止原因。

### 3. LangGraph：捕获范围是显式策略

LangGraph `ToolNode` 的接口同时支持：捕获全部异常并生成 `ToolMessage`、只捕获指定异常、用函数生成错误消息，以及 `False` 直接让异常传播。当前默认处理器只把模型提供的无效参数包装成可反馈的错误消息；普通工具执行异常会重新抛出。源码还把系统注入参数从验证错误中剔除，只把模型可控制的字段反馈给模型。

因此，框架给出的可迁移原则是“**只把调用方有能力修正的内容作为模型观察**”。授权、内部状态、注入依赖、恢复值不匹配或基础设施崩溃，不应伪装成模型可以通过改参数解决的问题。若项目决定捕获网络/业务异常，也应显式分类并返回结构化错误，而不是把任意异常堆栈直接暴露给模型。

### 4. OpenAI Agents SDK：模型可见失败与硬失败并存

OpenAI Agents SDK 对 `@function_tool` 提供 `failure_error_function`。默认函数把工具崩溃变成模型可见的错误；自定义函数也会把返回文本发给模型；显式传 `None` 则重新抛出错误，由程序处理。对异步工具，超时默认 `error_as_result`，可改为 `raise_exception`。

这不是“默认任何错误都安全回流”的保证。错误函数只是传递信息，模型能否恢复取决于错误是否可操作、是否有替代工具和是否会重复副作用。对于严格结构化工具输出，官方文档还提示自由文本错误可能不符合输出 schema，这时需要 schema 兼容的错误结果或程序级失败。

## 重试与写操作不确定结果

AWS 的工程文档给出的边界很清楚：重试适合短暂、随机、低副作用的失败，但重试会增加下游负载；应使用退避、抖动和次数上限，并尽量只在一层做重试。更关键的是，超时/失败并不说明远端副作用没有发生；有副作用的 API 通常只有在提供幂等机制时才适合重试。

Stripe 的幂等请求文档提供了可操作的具体例子：相同幂等键代表同一逻辑请求，服务端保存首次执行结果，重复请求返回同一结果；改变参数会被拒绝。参数校验失败或并发冲突导致端点尚未开始执行时，则可以重试。这个例子不能直接替代本项目的接口契约，但说明“可安全重试”必须由服务端定义，不应由模型猜测。

建议把恢复决策写成下表，而不是统一 `catch -> 用户报错` 或统一 `catch -> 再调用`：

| 错误类别 | 典型例子 | 先交给模型 | Runtime 自动重试 | 必须停止/核实 |
| --- | --- | --- | --- | --- |
| 模型可修正 | 缺参、枚举/格式错误、工具名选择错、范围表达不完整 | 是，返回可操作字段和约束 | 通常不需要；由下一轮模型修正，次数有界 | 连续同一错误、预算耗尽后终止 |
| 瞬时只读失败 | 网络抖动、上游 5xx、限流、短超时 | 可在重试耗尽后回流，允许换只读工具或缩小范围 | 是，单层、退避、抖动、上限 | 认证/权限失败或持续不可用时停止 |
| 授权/确认失败 | 用户无权、设备不在范围、需要人工确认 | 可以说明事实并请求澄清/确认 | 否；不能靠换参数绕过 | 服务端拒绝，保持未执行 |
| 写操作未知结果 | 下发后连接断开、客户端超时、无明确回执 | 先告诉模型 `unknown`，让其走查询/解释 | 不得盲目重复下发；先按 operation/idempotency key 查询 | 查询不到权威状态时停在 `unknown`，向用户诚实收口 |
| 程序/协议级失败 | JSON-RPC 响应不合法、模型输出无法解析、会话写入/上下文损坏、预算耗尽 | 不强行回流 | 仅按程序自身恢复策略 | 稳定的程序兜底、日志和可恢复入口 |
| UI 卡片业务操作失败 | 确认时提案过期、版本变化或业务请求失败 | 需要调整业务方案时，将核验后的事实回流；纯渲染/本地回调缺陷由前端修复 | 只重试安全且有意义的读取；不反复触发确定性的渲染缺陷 | 若确认可能已开始执行，先查询状态再决定，不能直接再次确认 |

## 对当前项目的核验标准

以下是把上述来源映射到当前代码路径时应采用的判断，不是对外部规范的强制解释：

1. **同名同参数第二次调用即阻断**可以作为防止无限循环的保护，但不能只凭工具名和参数决定。至少应区分上次是否成功、错误类别/指纹和是否有修正进展：瞬时只读失败可允许同参数重试，缺参/枚举等应允许模型修正参数；授权拒绝、写操作未知结果和协议/程序级错误不能靠重复同一请求恢复。
2. **提案两次失败 `shouldStop`**应表示“模型可修正尝试耗尽”或“进入不可安全恢复类别”，并把最后一个结构化错误留在 Agent 上下文。不能把两次任意异常都视为业务完成或已向用户解释。
3. **`finally` 将草案标记为 finished**只能在终态已确定时执行。若工具错误已被包装成模型可见结果并准备继续 loop，草案仍处于处理中；若写操作状态未知，终态应是 `unknown`/待核实，而不是成功或普通失败。
4. **前端 `confirmTaskProposal` 的 catch**如果只有 `errorMessage + restore`，只能恢复 UI；它没有恢复 Agent loop。对于尚未发出副作用的参数/状态错误，应把结构化结果送回原会话；对于可能已发出的确认，应先查询任务/操作状态，再决定是否允许新的确认动作。
5. **模型无法运行时**（模型响应不完整、上下文/协议损坏、会话持久化失败、超出预算）应由程序提供稳定兜底和可回放证据。不能为了“让模型自愈”把不可解析的响应或权限拒绝反复投喂模型。

## 采用边界

本次来源支持的是一套分层工程原则，不是一个可直接复制的统一标准：

- MCP 提供协议层的错误形状与工具结果标记，不规定 Agent 如何恢复。
- Anthropic 提供一个明确的 `tool_result.is_error` 反馈循环及有限修正行为。
- LangGraph 和 OpenAI Agents SDK 把捕获/回流/抛出做成可配置框架策略，且默认策略不同。
- AWS 和 Stripe 说明重试必须受瞬时性、负载、幂等键和副作用不确定性约束。

因此，本项目的验收应观察：错误是否被正确分类；模型可修正错误是否在用户可见失败前完成一次有界回流；瞬时失败是否只在安全层重试；授权和写操作未知结果是否停止并核实；程序级失败是否有诚实、可恢复的兜底；UI 卡片失败是否回到同一业务事实而非制造第二次副作用。
