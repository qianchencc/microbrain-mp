# 从社区经验重审 Agent 的继续、暂停与退出

2026-10-25。用户重新明确的目标是：智能体承接委托，过程错误优先进入恢复和推理，卡片操作不能成为脱离委托的死路。本轮是设计审视，不实施产品补丁、不部署、不执行客户设备控制。

## 结论与证据边界

目前没有修复完备。已有工具参数纠错、只读重读、幂等确认、报告保留等能力，但它们不能证明“委托跨工具、确认卡和应用错误连续推进”。本轮发现的问题集中在**委托的连续性**：业务事实是否可供后续推理使用，外部交互是否能恢复原委托，退出是否确有业务理由。

## 社区经验提供的设计依据

| 一手来源 | 来源实际支持的原则 | 本项目的设计推论 |
| --- | --- | --- |
| [Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents) | 模型根据环境反馈决定后续动作，以真实工具结果评估进展；允许人工检查点和预算限制，鼓励简单实现 | 应先明确委托完成条件，再判断是否继续；预算是成本边界，不是任务已完成的证据 |
| [Anthropic：Writing effective tools](https://www.anthropic.com/research/writing-tools-for-agents) | 工具应提供有用上下文；校验错误给出具体、可行动的修正信息；用真实复杂任务评估效果 | 工具报错必须让模型知道还能做什么；只改善面向用户的失败文案不等于恢复 |

| [Microsoft：AG-UI human in the loop](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/ui/ag-ui/human-in-the-loop) | 前端显示审批并把决定送回服务端；同一会话继续。运行结束事件也可能表达审批中断 | UI 卡片不是模型输出后的孤立表单；运行终态与业务终态必须分别理解 |
| [Anthropic：Managed Agents 工程经验](https://www.anthropic.com/research/managed-agents) | 会话事件记录独立于当前模型上下文和执行进程；可依据记录恢复工作；宿主假设需要随模型能力重新审视 | 需要能重建委托进展的权威事实，不能只有页面看得见的历史；固定的防打转规则应由业务反例检验 |
| [MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling) | 工具执行失败可作为模型可见的错误结果；协议不强制某一种交互架构 | 采用“错误作为观察”原则，不声称 MCP 要求所有异常都自动恢复或都调用模型 |

这些材料不是统一强制标准，也不构成更换 Pi、引入 LangGraph/AG-UI 或托管服务的理由。借鉴其状态与交互原则即可。独立的一手来源调查见[社区来源笔记](2026-10-25-agent-continuation-community-sources.md)。

## 当前设计的三个可复现反例

脱敏输出见[探针记录](agent-error-recovery-acceptance/continuation-audit-2026-10-25.json)。探针从 `buildApp` HTTP 进入，使用进程内网关和受控 runner/provider，不联网、不确认控制。红灯断言表达尚未满足的业务要求，不加入正常 CI 伪称回归已经通过。

### 1. 卡片失败没有成为可恢复的委托事实

先通过消息生成并保存真实提案，确认时让 Office 目录读取失败。包含现行客户端的一次 POST 重放后，两个确认请求都返回503；总共四次底层失败读取。服务恢复，再调用当前会话恢复接口：

- 错误码是 `AUTHORIZED_SCOPE_UNAVAILABLE`，携带 `recovery.kind=retryable_read`。
- 恢复后仍为 `awaiting_confirmation`，轮次1→1，新增公开事件为空。
- runner 调用仍只有最初生成卡片的那次。没有新的恢复工作被承接。

这里已经有程序重试、幂等与 UI restore，不能说“完全没有恢复”。缺口是这些尝试耗尽后，失败没有作为原委托的持久事实交接，系统也没有对外提供正在恢复或明确阻塞的后续状态。

源码对应：Runtime `app.ts` 的任务确认读取失败分支；MP `apis/agent/index.js` 的一次安全重放，以及 `AgentConversation.vue` 的 `confirmTaskProposal` catch→restore。`TASK_DEVICE_UNAVAILABLE` 仍直接要求重新创建，已过时间只返回 `needs_new_time`。这些业务错误并非都适合自动改动，但必须保留原对象与意图，再由智能体请求真正缺少的决定。

重现（Runtime 根目录，需既有依赖）：

```sh
/opt/homebrew/opt/node@22/bin/node --import tsx ../mp/.scratch/agent-error-recovery/probes/card-handoff.mts --expect-agent-handoff
```

约1.4秒，预期当前退出1。探针在当前请求/客户端重放/恢复读取这一有界链路内观察；没有宣称测试了不存在的后台恢复调度器。

### 2. 新进展被检索次数守卫当作无进展

用户明确指定五个会议室。受控模型在同一个回合依次查五个地点，每次成功返回一台不同设备，随后准备同一份待确认任务：

- 四地点对照：后续20个工具仍可用，成功 `task.proposed`→`run.awaiting_confirmation`。
- 五地点：五次都取得新结果，但后续工具被全部移除，未出卡；公开终态为 `run.completed/outcome=message`。
- 仅使用两次模型响应、五个检索，尚未达到默认六回合/十工具调用的总预算。

源码对应：`pi-runner.ts` 的 `kindFindCounts >= 5` 会设置 `finalizeWithoutTools`；普通 `modelText` 返回分支又没有携带已设置的 `stoppedReason`。不能把“调用了五次”视为“没有进展”，也不能用提高一个阈值代替重新定义进展。

```sh
/opt/homebrew/opt/node@22/bin/node --import tsx ../mp/.scratch/agent-error-recovery/probes/progress-exit.mts --four
/opt/homebrew/opt/node@22/bin/node --import tsx ../mp/.scratch/agent-error-recovery/probes/progress-exit.mts
```

各约0.9秒，当前分别退出0/1。这是宿主策略的反例，不代表真实模型一定选择先做五次检索，也不证明所有复杂请求都失败。

### 3. 页面保存了委托，后续模型却不知道委托

模型启动前让目录读取失败，当前消息以 `run.failed` 结束。恢复接口仍返回原用户请求。恢复服务后，用户发送“继续”：runner 收到的历史和当前输入都不含原委托。

源码对应：常规目录加载在 `options.runAgent` 之前；外层 catch 仅在显式停止/超时有 `abortReason` 时补存用户消息，普通读取异常没有对应的模型历史补存。由此出现 UI 历史与模型可恢复上下文的分离。

```sh
/opt/homebrew/opt/node@22/bin/node --import tsx ../mp/.scratch/agent-error-recovery/probes/entry-handoff.mts
```

约1.4秒，当前退出1。观察模型输入边界，未要求假模型模拟理解能力。

## 继续、等待与退出的候选业务规则

以下是根据用户目标和上述来源提出的设计判断；不是已经实施的状态机或新增接口契约。

| 当前事实 | 下一步责任 | 面向用户的状态 |
| --- | --- | --- |
| 目标未完成，取得新事实，仍有合法且有意义的动作 | 智能体继续补查、修正或准备下一步 | 处理中，过程错误归入处理记录 |
| 参数构造错误，答案已经存在于委托或当前事实中 | 将可行动错误回流模型修正 | 不要求用户补技术参数或重复描述 |
| 暂时性只读失败、数据准备中 | 程序在统一截止时间内重读/等待；需要策略判断时回流模型 | 正在核实/等待，有真实进度 |
| 确认回包未知、状态冲突 | 先按原操作读取权威状态；成功返回原结果，变化则让模型承接差异 | 同一对象，不虚报未创建，不重复下发 |
| 缺少真实业务决定、权限或新的确认 | 保留已完成事实与待决问题，等待必要输入；决定到达后继续原委托 | 等待决定/确认，不当作业务失败 |
| 已部分完成，仍有可安全推进的未完成项 | 保留成果，继续未完成项；不能重做已确认副作用 | 明确部分成果和剩余工作 |
| 连续同一失败，无新证据且无合法替代动作，或达到总预算 | 明确阻塞原因与恢复入口；禁止无限循环 | 本次未完成/部分完成，不标成功；没有持久安排时不承诺后台继续 |
| 用户停止、替换意图，或权限失效 | 取消相关恢复；隔离旧结果，保留已发生事实 | 已停止/需要授权，不自动复活旧操作 |
| 结果满足本次委托的完成条件并可验证 | 交付权威结果 | 已完成 |

“完成”依委托而定：用户要求创建定时任务，登记成功并返回同一任务就是本次创建委托的交付；未来执行另由已确认任务承担。生成待确认卡只表示准备完成，不能冒充已经创建；调度器等待明天也不需要保持一个模型循环常驻。

权限、幂等、确认、可重试资格仍由服务端确定。模型负责在这些约束中选择下一步。卡片状态应保持服务端权威，但相关状态和失败不能对智能体不可见；不需要每次勾选都调用模型，也不能把系统事件伪造成新的用户指令。

## 业务场景复核

| 场景 | 已有正确基础 | 仍未补齐的连续性 |
| --- | --- | --- |
| 查询→工具报错→修正 | 参数修正、只读有限重读已存在 | 仍有按次数撤掉全部工具的宿主限制；不同错误/新证据不能与打转混同 |
| 创建→确认卡失败 | 过期重开、成功重放、客户端安全重放 | 可恢复读失败耗尽、设备变化、新时间请求没有统一的委托承接；反例1 |
| 修改/取消/周期启停 | 有版本核对、原作用域和部分最新状态回传 | 页面 catch 常止于错误与刷新；最新差异和原操作目标未自动进入后续推理 |
| 即时草案选择/重核/确认 | GET核实原版本、保留回执、禁止盲重放 | 非瞬态冲突与恢复耗尽主要停在页面；最近草案摘要不是完整待恢复操作事实 |
| 能耗准备/附件 | 工具内有界等待、已存报告保留 | 等待耗尽后仍要用户主动续接；是否有必要继续由实际截止时间和准备进度决定，不能无限等 |
| 对话启动/引用/恢复 | 租约重开、模型建连有限恢复、断流不等于取消 | 普通目录失败可能直接结束；UI保留原请求不等于模型上下文保留，反例3 |

上述管理与草案路径为静态核对，不能称每一项均新增故障注入验收。已有生产正常路径与旧验收记录继续有效，但不能据此推算恢复覆盖率。

## 后续应如何推进

先明确“同一委托有哪些权威事实、当前还欠什么、哪些外部事件会唤起它、哪些条件可以退出”，再选择首个窄业务验证设计。优先业务是**确认任务卡出现可恢复错误后，无需补救消息，沿原任务自动核实到成功、新的必要确认或明确阻塞**。

这条闭环应同时验：成功但丢响应、明确未创建、版本/目标变化、权限拒绝、停止/新意图，以及重开后的续接。需要推理时用真实模型验证错误确实进入模型且采取合法下一步；确定性幂等由公开接口验证。继续使用既有 HTTP/NDJSON/会话恢复与真实微信入口，不预设新的测试接缝、通用恢复引擎或工作流框架。

其后再推进管理卡/即时草案的同样业务模式，以及有新进展时的工具继续条件。按真实业务逐条闭环，不按错误码数量铺补丁；不先提高回合数、增加重试层数或扩写一整套提示词。
