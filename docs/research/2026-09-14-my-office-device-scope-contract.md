# 办公室用户设备范围接口族契约

日期：2026-09-14

## 结论

物联 Agent 的设备范围应来自客户 Office/工作区业务层的同级用户设备接口族：先取得当前用户被分配的办公室/区域上下文，再聚合所有同级来源暴露的设备。“我的办公室”只是一个已核验但不完整的页面实现；“智慧空调”“智慧照明”“智慧门禁”“智慧监控”等独立入口属于云起智慧面板，不参与 Agent 范围发现。

本记录来自客户小程序 `web-view` 实际加载的 owner 子应用 `pages/office/index` 生产 bundle 和当前测试账号的只读接口复核。记录不保存 token、办公室 ID、设备 ID、provider ID 或凭据。

## 页面数据流

```text
当前用户
→ 查询“我的办公室”列表
→ 选择一个办公室
→ 按办公室 elementId 查询设备
   ├─ 中央空调专用分页
   ├─ 通用设备分页：照明
   ├─ 通用设备分页：安防 / 门禁子类
   └─ 通用设备分页：安防 / 视频子类
```

该页面当前声明四个设备标签：空调、照明、门禁、监控。空调使用专用分页；照明、门禁和监控使用通用办公室设备分页。这里仅能证明该页面来源的覆盖范围，不能证明 Office 用户设备接口族已经完整。

这不是区域树递归接口。此前从首页“智慧门禁”组件观察到的固定根区域 → 子区域 → `devicePage` 链路，只属于该智慧门禁组件，不能作为“我的办公室”的范围契约。

## 当前测试账号只读结果

当前账号返回 1 个办公室。该办公室共暴露 7 台设备：

| 类型 | 数量 | 结果 |
| --- | ---: | --- |
| 中央空调 | 2 | 在线、状态正常；列表未直接携带完整控制动作 |
| 照明 | 3 | 在线、状态正常；包含打开和关闭动作 |
| 门禁 | 2 | 在线、状态正常；包含远程开门，并同时出现授权码和静态密码相关动作 |
| 监控 | 0 | 当前类型查询返回业务码 204 |

因此，当前测试账号从该来源观察到 1 个办公室和 7 台设备；这 7 台是该来源的观察值，不是完整 Agent 范围。管理端的 137 条办公室注册记录、未经证明属于用户范围的账号级三类关联目录或云起 333 台底层设备，均不能直接并入 Agent 范围。

监控类型的 204 只说明当前办公室没有监控结果，不代表整个用户范围为空。只有完成全部声明的同级用户来源查询后，才能形成完整或空的 Authorized Device Scope；“我的办公室”页面自身的完整遍历仍只证明该来源完整。

## 对统一注册层的约束

- `OfficeScopeSource` 先读取当前用户办公室/区域上下文，再读取该来源覆盖的设备类型；`OfficeDeviceScopeProvider` 负责聚合所有已声明的同级来源。
- 所有返回设备都进入统一注册和盘点，即使其控制能力尚未接入。
- 规范化设备类型之外仍保留上游原始 `sourceType` 和 `sourceSubtype`，避免未知设备丢失。
- 能力注册与设备注册分离。上游动作名称必须经过白名单和参数 schema 规范化后才能进入草案。
- 管理注册目录和云起目录只能用于内部映射、能力调查或诊断，不能增加 Authorized Device Scope 成员。
- 执行入口优先使用同级 Office 来源暴露的办公室设备引用；只有实际契约需要时，才在内部 binding 中映射云起底层引用。

## 已确定与后续工作

1. 客户上游已经负责根据小程序当前登录用户过滤相关用户接口返回的设备；固定测试 token 只是固定模拟一个用户，嵌入客户小程序后直接继承真实登录态。
2. Office 用户接口返回的设备就是 Agent 应接管的用户授权设备范围；“我的办公室”只是一个页面实现，不是 Agent 的额外隔离层。
3. Runtime 需要消费客户已有的状态响应体，完成生产状态读取和执行后回读；接口不存在响应体不是当前结论。
4. 更多设备类型暂不接入，只保留统一注册和原子检索扩展位。
5. 微信开发者工具已可用，下一步直接做真实小程序端到端验收。
