# 智慧消防告警接口响应与历史信息反馈

日期：2026-11-12。用途：向客户／智慧消防接口提供方反馈实测情况与待确认事项。

## 结论

同一传感器在物联网引擎与智慧消防存在两套设备资料，修改一侧不会保证另一侧名称和安装地址同步变化。智慧消防改名后，同一设备的历史告警查询名称也发生变化，因此现有告警响应的`deviceName`不能视为告警发生时固定保存的名称或位置。

物联助手告警统一采用智慧消防信息：事件内容来自消防告警接口，当前设备名称和安装地址来自消防设备目录，不再混用物联网引擎名称／安装位置。页面展示的“当前位置”是消防设备目录的当前安装地址，不是事件发生时的位置。

## 1. 接口与字段

以下为上游接口路径；物联助手只由既有后台同步读取，前端及普通业务核验不直接调用。

- 消防设备目录：`GET /micro-api/api/perception/device/page?type=FIRE`。
- 告警记录：`GET /micro-api/api/perception/fire/{ledger}/alarm/page`，台账类别按现有接口路由配置。

| 来源字段 | 本端用途 | 注意事项 |
|---|---|---|
| 告警`id` | `eventId`，定位同一事件 | 改名对照使用同一事件ID，不按标题判断是否新事件 |
| 告警`deviceId` | 消防业务设备ID | 与物联网引擎硬件ID不同 |
| 告警`deviceName` | 告警列表／详情标题；保存在`recordedDeviceName` | 实测会随消防设备改名变化；字段名中的“recorded”不代表不可变历史快照 |
| 告警`createdAt` | 转换为`occurredAt`，展示告警时间及设置回放窗口 | 来源字段叫创建时间；其与实际触发时间的严格关系需接口方确认 |
| 告警`alarm`、`report` | 保留来源布尔标记 | 不自行解释为已处置、已恢复或设备当前仍报警；生命周期语义待接口方说明 |
| 告警`elementId`、`elementName` | 现有转换未保留 | 曾有建筑级名称或空值的历史证据；不能据此当作房间位置或摄像头绑定，当前语义待确认 |
| 告警`modifiedAt/createdBy/modifiedBy/version/isDelete` | 原响应包含的记录管理字段，当前本端业务转换未保留 | 未据此重建迁移时间或事发位置；本端不是完整原始响应归档 |
| 消防设备`name` | `currentDevice.name` | 当前消防设备名称，可能不同于某次已同步的事件名称 |
| 消防设备安装地址（适配`installAddress/installAddr`） | `currentDevice.location`及页面“当前位置” | 当前消防资料；不改用物联网引擎地址，不从名称补造地址 |
| 消防设备`hubDeviceId` | 关联同一底层硬件的身份 | 不是位置或历史摄像头关联 |
| 本端`observedAt` | 页面“本次读取”时间 | 本端响应生成时间，不是告警时间、采样时间或后台同步时间 |

## 2. 同一烟感设备的改名前后对照

烟感业务ID：`18d46a9a167fa4659443f7199520a24e`。

| 对照项 | 修改智慧消防名称之前 | 修改之后后台同步取得的结果 |
|---|---|---|
| 2026-11-11 14:54:41事件 | 27楼茶水间光电感烟探测器 | 26楼未来智城光电感烟探测器 |
| 2026-11-11 14:55:52事件 | 27楼茶水间光电感烟探测器 | 26楼未来智城光电感烟探测器 |
| 2026-11-12 09:36:12新事件 | 尚未产生 | 26楼未来智城光电感烟探测器 |
| 消防设备当前安装地址 | 27楼茶水间光电感烟探测器 | 仍为27楼茶水间光电感烟探测器 |

两条旧事件的ID和时间保持不变；本端09:33同步更新了旧名称，新事件09:36:25入本地同步表。查询这台设备已同步的40条烟感历史记录（2024-04-22至2026-11-12），名称全部为改后的26楼名称。

这是后台正常同步结果与改名前留存证据的对照，不是本端用物联网引擎名称覆盖出来的结果。本端按上游事件返回值更新同一事件的名称；未确认上游采用“查询时关联当前名称”还是“改名时更新历史行”，两种机制需要接口方澄清。

## 3. 对监控回放的影响

当前本端从告警响应名称提取地点线索，在当前视频权限内匹配监控，默认回放窗口为告警时间前后15分钟。名称中的地点变化会改变历史事件的摄像头候选，因此不能承诺这就是事发时正确摄像头。返回候选也不保证对应时段录像仍保存。

单纯在本端首次接收时保存当前名称或安装地址不能修复这项缺口：历史补传、延迟上报及搬迁期间同步都可能造成取到的地址不属于事发时刻。本轮未新增历史位置快照、自动推断或批量改写旧事件。

## 4. 请接口提供方确认

1. 告警`deviceName`在生成时写入，还是查询时关联设备资料？设备改名是否批量修改历史告警？
2. `createdAt`表示实际触发时间、平台接收时间还是入库时间？延迟／补传是否另有发生时间？
3. 是否已有不随设备变更而改变的事发安装位置字段、空间ID或可查询的设备位置变更记录？`elementId/elementName`具体代表哪个空间层级？
4. 消防设备名称和安装地址是否独立维护？与物联网引擎设备资料的同步规则是什么？
5. 若要支持“连续更换安装位置，每次告警均保留当时位置”，能否在位置更新生效后，创建事件时保存该位置及稳定空间标识，后续改名／搬迁不覆盖？

需要的是事发时的信息，而不是以当前资料推测过去。已有缺失事发位置的历史事件不能凭空补齐；如果上游另有历史接口，可以据实接入。
