# Agent 请求延迟与答复交付协议研究

日期：2026-10-21。状态：设计研究，未实施。

本文处理同一条请求链上的相关问题：前置设备目录读取、模型请求次数、`reply_to_user`、普通文本流式输出、结构化卡片排序、答复完整性和终态观测。它不把问题拆成“无业务工具就不要读目录”，也不把目录缓存当作单独的性能项目。

## 结论

当前 30 秒以上的体验不是一次上游模型请求变慢，而是本地把多个阶段串在了一条用户不可见的等待链上：

```text
每轮重新加载 Company 目录
  → 第一次模型请求
  → 模型普通文本被当作内部内容
  → 再发一次最终答复模型请求
  → 最后才向前端提交可见答复
```

已有复现记录中，一次没有业务工具调用的简单问题总耗时约 30.35 秒，其中约 12.33 秒发生在第一次模型请求前，第一次本地模型调用约 12.71 秒，`runtime_final_reply` 补交约 5.26 秒。上游约 4 秒的说法只能对应其中某一段，当前观测还不能证明它对应本地记录的完整模型调用边界。

因此解决方向必须同时处理：

1. 目录作为有权限边界的数据快照复用，而不是每轮重新采集。
2. 普通最终答复直接走公开文本流，不再强制模型调用 `reply_to_user`。
3. 工具事实、结构化卡片和最终文字走有序事件流；卡片不必等待最终文字。
4. 业务结果的完成性由服务器事实和业务模块判断，不能靠第二次模型调用“补交”或用简单字数判断。
5. 每个模型请求和每个可见事件都有独立时间边界，先能证明 4 秒与 30 秒分别指什么，再谈优化效果。

## 当前证据与代码事实

当前 Runtime 在 `apps/runtime/src/app.ts` 的 Agent 运行入口中执行 `loadSourceCatalog`。Company 来源会调用 `iot.loadCompanyDeviceCatalog`。该方法会并行读取观察设备、空调、照明、门禁和监控目录。

Runtime 已有 `catalogCache`，但它主要服务 `loadDeviceCatalog` 的 Office 路径。Company 的 `loadCompanyObservationCatalog` 只合并同时发生的请求，并保留一个仅用于上游失败兜底的观察目录；`loadCompanyDeviceCatalog` 没有复用一个正常完成的完整 Company 目录快照。因此“同一身份最近已经读过目录”仍可能在下一轮重新访问多个上游接口。

当前 `apps/runtime/src/agent/pi-runner.ts` 将普通模型文本视为内部规划，并要求最终答复调用 `reply_to_user`。如果模型正常以普通文本停止但没有调用该工具，Runtime 会再次发送 `<runtime_final_reply>`，只允许模型补交最终答复。这正是额外模型请求和内容延迟的直接来源。

当前订阅逻辑也丢弃普通 `text_delta`，而工具完成事件仍会产生设备候选、观察卡片和报告事件。因此前端收到的不是“模型开始说话、工具事实到达、最终答复完成”，而是“工具事件陆续到达，普通文字暂不显示，直到最后一次模型请求完成”。这同时解释了卡片与文字的顺序问题和“像卡住”的体感。

仍有一个必须补齐的证据边界：现有 Langfuse 包装器能记录每次模型 generation 的开始和结束、内容、usage 与 stop reason，但没有稳定记录请求发送、响应头、首个上游事件、首 token/首片、最后一片和上游响应 ID。因此本地 12.71 秒与用户看到的上游 4 秒还不能直接相减归因。

## 外部一手资料收敛出的共同模式

### 目录和外部数据：持久来源、轻量索引、运行快照、分级刷新

Anthropic 对 Agent 上下文的建议不是在每轮预先加载全部资料，而是维护轻量标识和入口，在需要时由工具加载更具体的数据；同时明确指出运行时探索比预计算数据更慢，因此实际系统需要混合策略，而不是把所有查询都变成即时远程探索。[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

Anthropic 的工具设计建议也把过滤、分页、截断和计算下沉到工具中，让模型拿到高信号结果；工具不应把原始全集返回给模型再让模型逐条扫描。[Writing effective tools for AI agents](https://www.anthropic.com/research/writing-tools-for-agents)

Home Assistant 的设备对话模型把设备、区域、楼层和别名作为长期目录事实，助手只暴露允许使用的最小实体集合；它强调目录命名和别名质量，而不是每次对话都重新发现整个实体世界。[Best practices with Assist](https://www.home-assistant.io/voice_control/best_practices/)、[Areas](https://www.home-assistant.io/docs/organizing/areas/)

OpenAI 的提示缓存资料进一步说明，稳定的指令、工具定义和历史前缀可以被复用，但缓存只减少模型处理稳定前缀的成本，不能替代本地目录缓存，也不能解决额外模型请求或上游业务接口耗时。[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

因此对本项目最合适的不是“无业务工具就完全不读目录”，而是：目录是权限和候选事实的基础数据，按身份和来源建立可复用快照；每个 Agent run 固定使用一个快照；动态状态和控制前再按自己的新鲜度策略读取。

### 最终答复：普通文本是终态输出，工具是事实和副作用边界

OpenAI Agents SDK 把“没有工具调用且符合输出类型的文本”定义为最终输出，并提供 `run_streamed`/`stream_events` 让调用方消费中间事件；它没有要求普通最终答复必须再调用一个名为 `reply_to_user` 的工具。[Running agents](https://openai.github.io/openai-agents-python/running_agents/)、[Results](https://openai.github.io/openai-agents-python/results/)

OpenAI 的延迟指南把“减少请求次数”“流式输出”“分块处理”“把步骤展示给用户”和“不要默认使用 LLM”列为独立优化原则，并明确确认、拒绝和标准提示等固定内容可以由传统代码生成。[Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

LangGraph 的流协议把完整状态、状态增量、任务结果和自定义事件放在不同通道，并使用序列/重放机制让客户端可以在实时流和持久状态之间恢复；这说明“模型文字、工具事实、UI 卡片、最终状态”可以是同一运行中的不同事件类型，不需要把所有内容压缩成一次最终答复调用。[Agent Streaming Protocol](https://langchain-ai.github.io/agent-protocol/streaming/)

这些方案共同指向一条边界：模型负责生成语言和选择工具，服务器负责事实、权限、副作用、结构化结果和终态；最终普通文字不应再经过一个额外模型工具才能被用户看见。

## 推荐的目标协议

### 1. 目录快照

目录分成三层，每层有独立的新鲜度和失败语义：

| 层 | 内容 | 复用策略 | 强制刷新点 |
| --- | --- | --- | --- |
| 目录结构 | 设备 ID、类型、名称、位置、能力引用、授权范围 | 按 `source + tenant + principal/授权指纹` 缓存已完成快照，带 `observedAt`、过期时间和来源指纹 | 授权变化、明确要求最新目录、控制确认/执行前、快照过期且不能接受旧值 |
| 模型目录摘要 | 设备类型计数、位置摘要、命名提示、目录完整性 | 从运行快照生成有界摘要；不把完整目录写入每轮历史 | 快照替换时重建 |
| 动态设备状态 | 开关、空调状态、在线态、读数、告警 | 单独按设备类型和业务定义缓存或读取 | 控制 preflight、执行回读、用户明确要求当前状态 |

每个 Agent run 在开始时绑定一个目录快照。缓存命中时直接使用该快照，不重新访问五组上游目录。缓存未命中或需要刷新时才采集新快照；同一身份的并发请求合并到同一个正在采集的 promise。缓存只保存已经成功构建的快照，不把失败结果写成可复用目录。

旧快照可以服务低风险只读查询，但必须携带“目录观察时间/是否当前核验”的事实；旧快照不能越过授权失败，也不能直接作为控制确认和执行的授权依据。控制流程仍然要重新核验授权范围并使用固定快照，动态状态另行读取。

这解决的是“每轮重复采集目录”，不是用一个全局缓存绕过权限，也不是把完整目录塞进 prompt。目录缓存的键必须包含能影响授权边界的身份信息，不能按 tenant 单独共用。

### 关于仪表盘全局快照

当前 `pages/agent/dashboard.vue` 使用的 `companyOverviewCache`/`dashboard-snapshot` 是小程序端的展示缓存。它可以帮助仪表盘避免重复请求，但不是 Runtime 的授权事实：响应已经是面向 UI 的投影，缺少控制、候选引用和来源合并所需的完整元数据，也可能在客户端停留到过期。

因此不能把这份前端对象作为请求参数回传给 Runtime，让 Agent 直接信任它。正确的复用方式是把 Runtime 内部的完整 Company `DeviceCatalogSnapshot` 作为唯一共享快照：仪表盘路由和 Agent run 都调用同一个按身份隔离的加载器；仪表盘从它投影展示数据，Agent 从它建立本轮目录摘要和候选查询。这样复用的是同一份后端快照，而不是再建一层前端到后端的目录协议。

### 2. 普通答复和结构化事件

`reply_to_user` 从普通答复的必经工具降级为迁移兼容能力，目标协议如下：

```text
run.started
  → tool.started / tool.progress / tool.completed
  → observation.reported / action.draft / report.ready（如有）
  → message.delta（最终普通文字，直接流式）
  → message.completed
  → run.completed
```

实际事件可以交错，但每个事件必须有递增序号和 turn ID，客户端按序消费。工具产生的卡片事实在工具完成后立即发布；最终文字不必等待卡片对应的模型解释完成。模型在调用工具前产生的普通文本先暂存在当前模型轮中，不直接暴露为用户答复；如果该轮确实调用了工具，这段文字作为内部规划丢弃。工具返回后，模型下一轮产生的普通文本才作为最终公开文字流出。

如果模型在没有工具调用的轮次直接产生普通文本，就从首个可公开片段开始发送 `message.delta`，不再等 `reply_to_user`。如果业务工具已经产生了结构化结果而模型没有再产生文字，服务器根据已保存事实生成确定性收据，例如“已找到 N 台设备”“报告已生成”“结果部分完成”；不再为补交格式而追加第二次模型请求。

动作草案、确认、执行、回读仍然使用结构化业务工具和服务器状态机。移除普通答复工具不会削弱控制安全边界，因为安全边界在草案、确认和执行模块，不在最终自然语言出口。

### 3. 完成性和半句答复

允许普通文字直接流式输出，不等于把任意模型文本当作业务完成。完成性必须按请求类型判断：

- 普通闲聊或解释：模型无工具调用并产生完整文本即可结束。
- 设备查询：工具返回的事实必须覆盖用户请求的范围；模型文字只是解释这些事实。
- 能耗报告：由 `EnergyReportSpec`、期间、比较要求和覆盖率决定完成/部分/无有效事实。
- 控制和任务：由草案、确认、固定成员、执行、回读和结果状态决定完成。

因此“格式合法但只有半句话”的问题不能通过 `reply_to_user` 解决，也不能引入一个额外审稿模型。应让业务模块产出可判断的事实和状态；当事实已足够时，服务器先发布结构化结果和确定性摘要；当事实不足时明确失败或澄清。模型生成的最终文字不能覆盖服务器已经判定的业务状态。

## 统一实施顺序

这是一个响应可靠性闭环，建议按以下顺序实现：

1. **先补齐边界观测**：记录目录 cache hit/miss、目录采集耗时、每次模型请求的发送/响应头/首片/末片、工具耗时、公开首字节、首张卡片、`message.completed` 和 `run.completed`。先把用户上游的 4 秒与本地 12.71 秒映射到同一请求 ID。
2. **补 Company 已完成目录快照缓存**：复用现有 `DeviceCatalogSnapshot`、身份隔离和 run 内快照，不新增通用缓存平台；补充 TTL、观察时间、过期和授权失败语义。
3. **切换普通答复出口**：无工具的最终普通文本直接公开流；有工具时缓冲工具前文字，工具事实立即发事件，工具后的最终文本公开流；移除“正常停止后再次调用模型补交”的默认路径。
4. **补确定性收据和完成性**：对已有观察、报告、草案、任务结果统一使用服务器事实收口；模型没有最终文字时不再发起第二次模型请求。
5. **最后调整前端排序和恢复**：按事件序号渲染卡片与文字，允许卡片先到、文字后到；断线后按 turn/sequence 从持久化事件恢复，不依据最后一段文字猜测运行状态。

## 明确不做的事情

- 不做“没有业务工具就不读取目录”的条件分支；目录是否读取由快照新鲜度和授权策略决定。
- 不把完整 Company 目录常驻 prompt，也不建设向量数据库或万能上下文平台来解决本次延迟。
- 不用 prompt cache 代替本地上游目录缓存；两者作用不同。
- 不为了让模型看起来在工作而展示内部思考文本。
- 不保留一个每次都额外调用模型的 `runtime_final_reply` 兜底。
- 不用字数、句号、关键词或第二个审稿模型判断自然语言是否“像完整答案”。
- 不因为普通答复改为流式就放宽动作确认、授权重核验、执行回读或未知结果规则。

## 需要保留的验证问题

实现前要用同一条请求链验证以下事实：

1. 目录缓存命中时，简单请求不再触发 Company 五组目录采集；目录快照仍与当前身份和 run 绑定。
2. 目录过期、身份变化、授权失败、明确要求最新目录时，刷新和旧快照行为符合上述边界。
3. 无工具普通问答只产生一次模型请求，并从 `message.delta` 开始流式可见。
4. 工具查询产生的卡片可以先于最终文字出现；文字不会覆盖或重排已经落库的卡片事件。
5. 模型正常停止但未调用 `reply_to_user` 时，不再触发第二次模型请求，也不会把未完成的控制/报告说成完成。
6. 真实回答内容与业务事实不足时，系统能明确给出部分/失败/澄清状态，不能只靠自然语言收尾。
7. 同一请求中能明确区分：上游模型请求耗时、Runtime 前置耗时、工具耗时、公开首字节等待和最终收尾等待。
