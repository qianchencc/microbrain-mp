日期：2026-09-30。任务：总表 S01，服务 T01 周期计划与 T02 结束通知。

状态：账户来源的真实只读核验完成。用户已纠正“Token 频繁过期”的文档前提；跨 Token 实验、刷新契约与失效停用阈值不再作为本轮前置问题。未修改业务代码、身份文件或登录状态。

## 新证据

复用 Runtime 的现有开发凭据，对真实网关 `GET /sso-api/account/me` 连续请求两次。两次均 HTTP 200、业务 `code=200`，`content.id` 为非空字符串且相同。仅输出字段类型与不可逆 ID 摘要，未保存响应原文或个人字段值。

该响应没有 `principalId`、`openid` 或 `wxOpenId` 字段。它包含账户 ID 与姓名等账户属性，不能据此取得微信接收地址。

客户前端已经用 `account/me` 的 `userInfo.id` 调用用户关联业务。`content.id` 是可以由服务端从已认证上游接口取得的账户来源，不再向客户重复索取新的主体字段。本次没有旋转 Token，也无需以旋转实验阻断后续设计。

“跨 Token 稳定性”原指同一账户更换凭据时，业务归属仍是同一个账户；它不表示 Token 失活或经常过期。此前把这个架构区别扩大成当前待解决的运行故障，已撤回。按现有可用凭据推进，不据此引入刷新机制、自动停用阈值或重新登录流程。

## 可采用的处理方向，待规格确认

1. 服务端用请求凭据读取 `account/me.id`，将账户 ID 与上游身份域、园区归属明确组合。Token 作为独立执行凭据加密托管；客户端提交的用户 ID 或 openid 不替代主体验证。
2. 周期计划、其管理操作与通知接收人引用账户主体；执行复用已有可用凭据并重核设备授权。主体解析是我方实现事项，不再作为客户必须补齐的 Token 生命周期契约。
3. 保留现有实际鉴权失败的如实记录，不将网络超时、设备拒绝或权限变化推断成 Token 过期。不基于被纠正的频繁过期前提新增周期停用/恢复机制。
4. 现有 Token owner 的会话与历史 Task 有迁移问题。规格中先声明兼容范围与回退点，不能为了新主体键无证明地合并旧用户数据。
