# 智能体错误恢复路径审视

日期：2026-10-24。范围：社区一手规范与本地当前源码的静态审视；没有运行生产故障注入、执行真实设备控制或部署。Runtime 基线 `e0c76e3`；MP 基线 `ed2f5b9`。这份报告不能用于推算生产错误占比，也不代表新增恢复能力已实现。

## 判断

用户指出的产品问题成立：可恢复错误应先由系统承担处理，工具调用失败不能直接等同于用户委托失败。项目已有普通工具错误回传模型的基础，但部分宿主终止规则会提前截断恢复；卡片确认等模型循环之外的交互缺少同等的恢复承接。

需要区分三种责任：程序恢复基础设施和瞬时失败；模型依据可行动的错误调整参数、补查事实或改用合法方案；用户提供系统无法取得的真实意图或授权。设备动作结果未知时，恢复应先核实事实，不能把超时视为未执行而重复下发。

社区资料与精确引用另见 [一手来源调查](2026-10-24-agent-error-recovery-primary-sources.md)。这些资料包含协议要求和框架实践，不存在一条适用于所有系统的“所有异常必须交给模型处理”的统一规范。

已有正确基础应保留：

- `apps/runtime/src/app.ts:2370` 的 `withSessionWrite` 已对 writer lease 丢失执行重开和一次写入恢复。此类问题由存储层恢复，不需要模型决定如何修数据库。
- `pages/agent/components/AgentConversation.vue:423` 在传输中断后保留进行中状态，通过 restore 追踪服务端结果，避免把断流当成取消。
- `apps/runtime/src/app.ts:2207` 根据是否已进入下发，分别回滚待确认或保存 `INTERRUPTED` 及逐项回执，保护未知结果，避免重复控制。
- 默认总预算为 6 个模型回合、10 次工具调用；预算本身有价值，问题是另有不区分成功/失败/修正进展的硬停止条件。

## 建议的行为契约

| 错误/状态 | 首先由谁处理 | 何时需要用户 |
|---|---|---|
| 参数缺失、类型不符、可由既有意图确定的时间或引用错误 | 工具返回字段级问题和有效约束；模型补查或修正，继续同一委托 | 真实意图有歧义且事实无法消除时 |
| 已知未下发的只读网络超时、限流、短暂上游错误 | 程序依据错误类型、Retry-After 和总截止时间有限重试；必要时模型选合法替代查询 | 恢复预算耗尽，且确实影响委托完成时 |
| 数据后台准备中 | 在有限时间内查询准备状态；若跨轮异步，需真实持久化任务与结果交付 | 系统没有实现异步承接时应如实说明；不得承诺不存在的自动补发 |
| 卡片确认过期、版本变化 | 服务端读取原对象和操作结果，把权威事实交给同会话恢复处理；模型必要时重建提案 | 时间、设备集合或目标值变化等影响授权内容时，重新确认 |
| 重复创建计划 | 读取已存在对象并核对与原委托是否等价，返回该对象或提出修改方案 | 原计划与用户当前需求存在业务差异时 |
| 设备控制超时或连接中断，结果未知 | 先读取原操作回执、执行状态和可用的权威设备状态；保留 unknown | 仍需新操作时按现行确认边界处理；现态不能证明门禁等历史动作是否执行 |
| 401/403、授权范围撤回 | 代码保持访问边界，停止相应操作 | 需要用户登录、授权或改变委托范围时；不能让模型绕过权限 |
| 存储租约、模型连接等运行故障 | 宿主按已知可恢复条件处理；模型不可用时由程序给真实状态 | 无法恢复或需要用户动作时；不把所有运行故障都交给另一次模型调用 |

错误事实至少应足以回答：原操作是什么、对象/版本是什么、哪一阶段失败、是否可能产生副作用、已经成功哪些部分、允许采取哪些恢复动作。字段形式在实施时按现有接口确定，不先构建通用错误编排框架。模型可以解释和选择方案，重试资格、权限、幂等与确认仍由代码约束。

## 展示语义

工具步骤失败属于过程事实；只有恢复完成、需要真实用户输入、达到恢复预算或出现不可继续的状态，才应形成面向用户的结论。

页面可以展示“正在重新读取设备范围”“正在核对上次操作结果”，处理记录保留原失败与后续恢复的关联。最终成功时不应仍保留一条孤立的终态错误；失败时明确已完成部分、未完成部分和下一步。不能用隐藏错误、改写成功状态或无限加载替代恢复。

卡片操作的续接应使用服务端已核验的对象与失败事实，不能伪造一条“用户要求重新执行”的消息。发起恢复本身也不等于授予新的控制权限。

## 首条建议实施闭环

优先选择“用户确认创建任务，遇到可恢复失败，系统承接到成功或新的待确认提案”。先覆盖一种真实常见错误，不同时重写全部工具和卡片。

1. 确认失败后先读取权威对象，辨明成功但回包丢失、已过期、已被修改和明确未创建。
2. 同会话承接原目标与失败事实；可直接恢复的读取由代码完成，需要推理的交给模型。
3. 参数/时间/成员改变时给出新的待确认卡；保持原业务意图，不静默改变时间或设备。
4. 用户得到成功结果、新的明确确认请求或恢复耗尽说明，无需复制错误再发一句“帮我处理”。

最窄公开接口验收：首次读取失败后恢复且只创建一次；确认已成功但响应丢失不重复创建；过期提案重建并重新确认；撤权不绕过；用户停止能终止恢复。另用真实模型夹具轨迹验证模型确实接到错误并作出修正，不能只用预设模型证明推理恢复。

这条闭环之后，再分别推进工具循环的失败重试资格、专用提案的一次失败收尾、能耗 preparing 承接。当前证据不足以承诺新增代码行数；应在冻结首种错误与接口后，先估算差异再实施，不预建全局恢复服务。
