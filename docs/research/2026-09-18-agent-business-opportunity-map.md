# 物联 Agent 业务探索地图

日期：2026-09-18  
状态：开放探索，不是实施规格、排期或合同新增承诺

## 本次讨论确认的方向

我们讨论的是多个业务域，不是只做会议室联动。设备接入、自动化、客户业务平台集成、结构化富交互和告警通知都是探索主线；会议平台是用户认可的下沉业务参考之一，但尚未选为首个实施闭环。

探索阶段保留业务想象力，实施阶段仍按单个真实业务闭环冻结范围。这两个原则不冲突：选择一个切片实现，不能删除其他候选业务，也不能把所有候选业务一并算成当前需求。

## 四条主线

这四条主线不是四个并列页面，而是一个有依赖的探索地图：

```text
真实用户身份与权限边界
        ├── 用户内容、记忆、日程和会议
        ├── 设备范围、设备台账和更多 Provider 能力（可并行探索）
        └── 下沉业务：自动化、告警、通知、富操作面、运营工作台
```

### A. 真实用户隔离

目标不是简单把硬编码 Token 换成登录接口，而是让一次请求能够稳定回答“哪个客户主体、哪个用户、哪个租户、哪个 Agent 工作空间、哪组设备和哪份个人内容”。

需要分别验证：

- 从客户 MP 登录态取得用户主体和 Token；
- Token 刷新、过期、退出和切换用户；
- Runtime 依据真实主体隔离会话、设备范围、记忆、日程、告警和通知；
- 开发身份只用于本地开发，不能混入真实小程序会话；
- 小程序、Runtime、Provider 的身份字段不互相冒充；
- 清除会话只清除会话活动，不误删用户长期内容；
- 用户被撤销设备权限后，旧草案、规则和后台运行如何处理。

这是所有个人化能力的地基，但不应把“用户隔离”误解成只隔离聊天记录。

### B. 用户内容、记忆和日程

这是建立在 A 之上的个人 Agent 内容域。建议探索不同信任等级的内容，而不是一个混合的 `memory` 表：

| 内容层 | 例子 | 关键语义 |
|---|---|---|
| 用户档案 | 姓名、部门、常用办公地点、偏好 | 来源、用户确认、修改和删除 |
| 长期偏好 | 常用空调温度、会议准备偏好、通知偏好 | 可解释、可覆盖、可撤回 |
| 事实记忆 | “某会议室通常在周一使用” | 时间范围、来源和置信度 |
| 会话记忆 | 上次讨论、未完成计划、上下文摘要 | 会话边界、保留期、跨会话检索 |
| 日程与任务 | 会议、待办、提醒、重复安排 | 外部系统权威、冲突和取消 |
| 临时运行状态 | 当前草案、自动化运行、待处理告警 | 不应升级成长期记忆 |

记忆工具候选包括：`remember`、`recall`、`forget`、`explain_memory`、`promote_memory` 和 `correct_memory`。工具不能让模型无提示地把任何聊天内容写入长期记忆；需要来源、作用域、保留策略和用户可见的删除入口。

日程和会议是记忆之后的外部事务域：客户会议系统应是会议事实的权威来源，Agent 只保存必要的关联、提醒和用户偏好，不把外部日程复制成无法校正的第二套日历。

### C. 更多设备和 Provider 能力

这条线与 B 相对独立，可以并行推进，但最终要回到真实用户的 Authorized Device Scope。设备扩展的交付对象不是“新增枚举”，而是：授权来源、统一身份、Provider 映射、状态/事件、能力白名单、错误/未知结果、审计和小程序表现。

客户需要提供的支持应整理成一份按设备类型拆分的清单：设备基线、用户范围接口、Provider 映射、状态/读数/事件契约、控制契约、风险分类、测试条件和验收案例。

历史检查已经发现视频、能源、消防、环境和道闸等不同成熟度的线索，但它们不能共用“已接入”这个状态。应分别归为“发现可用”“只读契约待核验”“事件契约待核验”“控制契约缺失”或“无用户范围证据”。

### D. 下沉业务和高水准交互

下沉能力不是单一功能，而是 B、C 之上的业务编排层。可继续探索：日程/会议驱动的空间准备、办公区开闭、能耗分析、视频值班、安全事件处置、设备报修、访客和活动空间、值班巡检、自动化、通知、接管和多端恢复。

这一层最复杂，因为它同时要求身份、设备、事件、调度、通知、权限和富操作面；应保持场景想象力，但每次实现仍只选择一条闭环。

后续记录统一区分：

- **用户确认方向**：本次讨论明确认可的探索方向，不等于逐项功能已批准实施。
- **已有能力**：当前代码和真实验证记录能够证明的能力。
- **候选场景**：可供讨论的业务设想，接口、权限和收益可能尚未验证。
- **待调查事实**：需要代码、接口、官方资料或客户数据证实的问题。
- **待用户决策**：优先级、预算、风险政策和产品取舍，不由代理替用户决定。

## 设备层探索

当前已有照明、空调和门禁控制闭环；视频有授权来源与只读发现能力，但没有播放闭环。其他类型需分别验证授权来源、身份映射、读数/事件/动作契约和前端表现，不能仅通过添加设备枚举宣称接入。

| 类型 | 已有线索 | 仍需核实 | 可支持的业务 |
|---|---|---|---|
| 照明、空调、门禁 | 已有 Runtime 适配和真实环境记录 | 持续确认状态证据、不同机型能力、风险边界 | 即时控制、节能策略、会议准备、异常处理 |
| 视频 | Office 视频来源、底层视频目录和查看能力线索 | 实时流、回放、鉴权、协议、小程序播放、查看权限 | 区域查看、事件核实、值班联动 |
| 电表 | 历史能源目录和读数样本（09-18 复测：43 台 readTime 停在 2024-09~2025-05，客户侧采集故障，已确认） | 用户/区域权限、指标口径、历史接口、新鲜度、计量层级 | 用电查询、报表、异常用能、效果复盘 |
| 水表 | 接口定义线索 | 真实设备和样本、单位、采样频率、历史和权限 | 用水查询、漏水提示、区域用水对比 |
| 烟感、燃气、水浸 | 底层设备与告警接口线索 | 事件订阅、重复/恢复语义、责任人、处置接口、演练条件 | 告警确认、人工处置、安全联动 |
| 环境、温湿度、人数 | 环境接口声明；人数接口尚未确认 | 具体传感器、读数、更新时间、区域映射和隐私 | 舒适度、使用率、人员密度、条件控制 |
| 道闸 | 合同提到，当前无稳定业务契约 | 设备、动作、状态、权限、安全机制 | 访客到访、停车流程、人工抬杆 |
| 显示屏、投影、窗帘、新风等 | 仅作为业务设想，不视为现场已有 | 是否存在、客户是否要求、接口、风险和成本 | 会议场景、空间准备和恢复 |

底层目录数量和接口样本是有日期的调查证据，不是当前账号应见设备基线，也不是授权。关联目录只作控制引用映射材料的较新裁定必须保留。统一台账优先复用客户台账与稳定映射，是否需要新增维护后台仍待讨论。

## 自动化产品形态

自动化不等同于会议业务，也不等同于确定性开关策略。至少保留三种形态：

| 形态 | 例子 | 规划与副作用边界 |
|---|---|---|
| 定时 Agent 任务 | 每天汇总能耗、巡查异常设备并提出建议 | 可在触发时调用模型分析；默认只读，建议不等于控制授权 |
| 确定性策略 | 工作日定时关灯、在约定条件下调节空调 | 明确规则、参数、有效范围和授权策略，执行路径可验证 |
| 事件驱动业务流程 | 会议变更后准备空间、故障后告警并等待人工处理 | 可以包含分析、分支和等待；每次副作用独立通过权限与风险检查 |

是否需要工作流引擎、调度库、任务队列或事件设施，要由选定切片的恢复、等待、并发和部署需求决定，当前不选择技术栈，也不预建完整平台。

应探索的产品行为：自然语言创建与修改、时间/时区/重复规则、条件和通知策略、预检查、影响预览、试运行、启停、临时跳过、立即运行、运行历史、权限变化、错过触发、并发与冲突、重复事件、未知结果、局部重试、人工审批、暂停和急停。

Orca 与 T3 Code 是参考对象，正确名称为 `pingdotgg/t3code`。参考产品功能摘要仅作为调查入口；具体能力和代码结构仍需按官方资料和固定版本继续核验，不能推断它们天然覆盖物联权限、物理回执或安全责任。

## 下沉业务场景目录

以下全部是候选场景，编号仅用于稳定引用，不表示优先级。会议联动获用户认可为参考方向，其他新增设想尚未逐项获批；未取得接口的客户系统均以“若可接入”为前提。

| 场景 | 业务闭环与用户收益 | 关键依赖 | 交互和安全关注点 |
|---|---|---|---|
| B01 会议预约联动 | 创建/变更/取消会议后准备空间，会后按策略恢复，失败通知责任人 | 会议 API、会议室 ID、设备映射、变更事件 | 预约时间线、设备预览、延期/取消、人工操作优先，不默认联动门禁 |
| B02 办公区开闭与节假日模式 | 按办公日历组织上班准备、下班节能、加班例外和临时暂停 | 办公日历、区域责任人；加班数据若存在 | 周期规则、例外日期、影响范围；不能把定时关闭称为无人检测 |
| B03 空间使用和舒适度 | 结合预约、人数和环境数据形成空置提示或舒适度建议，再按授权调整 | 人数/占用/温湿度数据、可用空调和新风能力 | 当前读数、趋势、条件编辑；无预约不等于无人，设防抖与人工覆盖 |
| B04 能耗查询与经营报告 | 自然语言查询、比较区域和时段，生成日报/月报并导出 | 电/水计量、指标口径、区域层级、面积和历史数据 | 指标卡、图表、筛选、导出；显示数据质量，避免总表和分表重复计量 |
| B05 异常用能与节能复盘 | 发现夜间耗能/突增，核实设备和业务原因，建议处置并复盘效果 | 新鲜能耗、基线、设备归属、业务日历 | 告警证据、比较图、建议草案；不能把估算节能量说成实测 |
| B06 视频辅助值班 | 从区域或告警定位摄像头，授权查看实时/回放并保留审计 | 摄像头权限、流接口、历史回放、事件关联 | 视频面、位置选择、事件时间轴；不自行加入人脸或行为识别 |
| B07 人员数量和密度提示 | 查询区域人数、使用率和高峰，超限后通知责任人 | 客户人数接口、区域面积、阈值和隐私规则 | 人数/密度卡、历史趋势；区分统计与推断，不由普通视频流臆造人数 |
| B08 烟感/燃气/水浸处置 | 事件进入后通知值班人员，确认、指派、核实、处置、关闭 | 告警接口、责任人、处置契约、演练环境 | 事件时间线、确认/指派面；高风险动作需单独授权和人工接管 |
| B09 设备故障与报修 | 离线/故障/状态异常后核实，创建或关联报修单，跟踪处理结果 | 遥测、客户工单/物业系统若可接入 | 设备详情、工单面、处置记录；旧读数不直接判定设备故障 |
| B10 访客到访服务 | 将访客预约、接待空间和设备准备关联，必要时交由授权人员操作门禁 | 访客平台若可接入、预约身份、门禁/道闸规则 | 到访卡、审批和开门草案；预约不自动授予访客或 Agent 设备权限 |
| B11 活动/培训/公共空间 | 按活动排期批量准备区域，变化时调整，结束后恢复和记录 | 活动平台若可接入、空间映射、设备能力 | 排期面、场景预览、批量执行回执；共享设备冲突与恢复归属 |
| B12 值班巡检与运营简报 | 定时检查授权范围内的状态、告警和任务，汇总待办、缺数和异常 | 状态/告警/任务数据、值班范围 | 摘要、异常清单、证据跳转；保留模型分析来源，控制另行授权 |
| B13 自动化运行异常接管 | 控制超时、部分失败、规则冲突后通知用户，核实去向再选择补执行 | 运行记录、动作回执、告警渠道 | 逐动作状态、接管面、局部重试；结果未知不可盲目重复下发 |
| B14 权限/范围变化下的运营 | 设备移交、授权撤销或规则所有者变更时暂停受影响自动化并通知 | 客户稳定主体、授权变化或定期复核 | 受影响规则清单、重新授权面；规则不能保留已失效权限 |

可以从不同业务组合形成场景，但组合不代表同时立项。例如会议使用记录可关联能耗复盘；视频可辅助安全事件核实；工单可关联设备告警；运营简报可汇总其他流程的未处理事项。

## 富交互的探索范围

“活组件”表示有结构化状态和真实操作的业务组件，不是模型生成任意代码或 HTML。普通解释仍可用 Markdown，事实、选择和副作用通过明确的业务对象呈现。

保留的组件族：设备清单/状态面、时间与预约面、规则编辑/预览面、运行轨迹/回执面、告警处置面、收件箱、指标/图表/报表面、审批/接管面、视频面、工单面和多对象关联详情。

需要探索的契约：对象身份、版本和状态；历史快照与当前状态的区别；动作权限；并发/过期/只读/失败状态；来源证据；刷新与恢复；通知跳转目标；异步运行；部分成功。聊天可作为创建和解释入口，持续管理是否需要独立列表、详情或工作台尚待产品讨论。

不先做通用组件平台。选定业务需要的组件先落地，再确认哪些公共行为值得复用。

## 告警和通知的探索范围

告警既包括设备/能源/安全事件，也包括 Runtime 内部业务事件，例如运行失败、权限失效、准备任务未完成和待审批超时。并非所有完成通知都需要创建告警；业务通知和需要处置的告警要区分。

必须分别讨论四个状态维度：告警的处置状态、通知的投递状态、个人的已读状态、系统/设备的恢复状态。已读不等于确认，投递成功不等于收到或处置，设备恢复也不自动证明责任人完成处置。

| 渠道或入口 | 当前性质 | 待调查问题 |
|---|---|---|
| 小程序内收件箱/告警列表 | 需要新增的业务能力 | 接收人、未读、详情、确认/指派、恢复和留存 |
| 微信小程序订阅消息 | 仓库有云函数入口，尚非已验收渠道 | AppID、模板、授权、接收人绑定、发送资格、配额与失败语义 |
| 客户现有消息中心 | 候选集成，未确认契约 | 是否已有消息 API、身份映射、模板和发送审计 |
| uni-push | 有样例，不证明能向目标微信小程序投递 | 适用终端、客户配置、接收标识和实际送达；不是必选渠道 |
| 企业微信/钉钉/飞书 | 候选，未确认客户使用或接口 | 官方接入、组织映射、应用消息/机器人边界 |
| 短信/邮件 | 候选备用/升级渠道 | 服务商、成本、联系人、授权和升级条件 |

告警策略还需调查去重、持续异常合并、限流、防抖、升级、值班表、静默时段、确认期限、接收人变更、渠道降级和消息脱敏。安全事件的实际通知保障必须由客户确认，不能将未经验证的小程序消息作为唯一安全通道。

## 技术和实施边界待讨论

- 客户台账和主体是否可复用，Agent 是否需要补充别名/映射管理。
- 定时 Agent 分析、确定性策略、混合流程分别怎样获得执行授权。
- 后台运行如何与已有会话、草案、执行回执关联，又不被六小时会话期限或聊天清除破坏。
- 未知结果、跨字段部分受理和取消后的动作如何核实，何时允许补执行。
- 多规则、多个会议和用户手动操作争用设备时，谁拥有控制和恢复权。
- 内部事件与投递的一致性、恢复、重试、去重怎样在最小架构中实现。
- 收件箱已读、告警确认和通知投递是否需要独立存储和接口。
- 多人/多端交互、权限变化和长期运行如何验证。
- 哪些能力是合同范围，哪些是未来候选，哪些属于需要客户另行确认的扩展。

## 下一步探索，不预定主线

按 `ask-matt` 路由，当前先保留广度和事实缺口；若要规划整个多会话交付，可进入 `/wayfinder` 建立决策地图，而不是立即发布实现票。选定单个可讨论业务后，用 `/grill-with-docs` 冻结决策；需要可运行答案时才用 `/prototype`；范围和外部契约明确后再用 `/to-spec`、`/to-tickets`、`/implement`。

下一轮可选择的调查题是：更多设备的授权来源与数据契约；Orca/T3 Code 的代码级可借鉴实现；定时 Agent 任务的产品模型；告警事件和实际消息投递；客户会议/访客/工单等平台接口；结构化活组件和导航归属。当前不为这些题目设置实施优先级。

按四条主线拆分调查时，建议顺序是：先验证 A 的真实 MP 登录和用户主体边界；并行向客户索取 C 的设备/接口支持清单；在 A 稳定后探索 B 的最小记忆闭环；最后从 B+C 中选择 D 的一个下沉业务进行原型或规格讨论。D 不必等待所有设备类型完成，但不能绕过 A 的真实身份和 C 的授权设备范围。

研究结果记录来源、日期/版本、响应或代码证据、未验证点；用户取舍记录原话与状态。后续选择一个闭环时，保留本目录，另行冻结该切片的范围和验收标准。
