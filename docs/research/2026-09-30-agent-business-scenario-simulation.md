# Agent 卡片组合与设备参与方式：业务场景模拟

日期：2026-09-30。状态：纸面体验模拟，非冻结规格，未实现新的业务能力。

所有设备数量、读数、时间和执行结果均为假设样例，不来自本轮真实接口调用。本文不执行设备操作、不创建真实任务、不发送通知。

## 模拟前提

- 当前实现：对话查询观察设备；即时操作草案；照明/空调的一次性定时任务；执行与回读记录。
- 已接受、尚未实施的方向：周期计划、独立任务区间、确认时安排且可编辑的未来检查点、区间结束后汇总、成功和异常结束都通知创建者。见 [ADR 0005](../adr/0005-recurring-plans-and-independent-task-intervals.md)。
- 本文进一步探索：任务中的只读检查、传感器条件判断、观察结果报告与按信息用途组合卡片。这些不自动加入已接受的周期一期范围。
- 卡片中的字段、证据和操作由业务协议约束；模型选择需要哪些业务内容，客户端用已有组件呈现。确认动作必须明确对应一份完整提案。
- 设备角色可以不同：执行对象、观察对象、条件来源、结果验证来源。只读设备承担后三类职责，不因此获得控制权限。

## S1：上班前了解办公区

用户：“看看 26 楼现在的环境、摄像头和最近的安全告警。”

预期回复：

> 环境读数已取得，摄像头在线。安全台账最近一条记录较早，不能据此判断当前有无告警。

卡片组合：

1. 环境观察块：温度 27℃、湿度 56%、PM2.5 36；注明设备、位置、观测时间与数据来源。
2. 视频观察块：设备名称、在线状态、查看画面入口；播放页未配置时保留“播放页接入中”。
3. 告警台账块：查询窗口、命中条数、最近事件时间、平台处置标记。

参与方式：环境和安全设备提供事实；摄像头提供在线信息和人工查看入口。没有控制对象，不出现执行确认。

异常模拟：环境只能取得站点级影子值时，不能把它标成该办公室实测；摄像头取流失败不能改写成离线；旧告警不能变成实时报警。

当前可达程度：现有观察事件与组件支持这组内容。具体是否一轮全部查询取决于模型工具调用；视频生产播放仍有部署依赖。

## S2：根据当前温度准备会议室

用户：“先看看会议室温度，太热就把空调调到 26 度，再把灯打开。”

模拟读数：会议室传感器 29℃，数据新鲜且位置匹配；两台灯关闭，一台空调设定为 28℃。

预期回复：

> 会议室实测 29℃，建议将空调设为 26℃并打开两台灯。操作已列入待确认草案。

卡片组合：环境证据块 → 一份灯光与空调的联合草案 → 用户确认后的执行收据。

参与方式：传感器提供本轮决策证据；灯和空调是执行对象；设备回读验证指令相关状态。

正常收口：收据区分无需操作、指令受理、回读确认和失败；空调设定温度达到 26℃不等于室温降到 26℃。

异常模拟：“太热”没有明确阈值时，29℃只能支持建议，不能被记录成用户已授权的长期规则。只有影子值或陈旧数据时先说明不确定性。没有可靠温度时不能声称已满足温度条件。

当前可达程度：本轮查询、模型推理与联合即时草案具备基础。观察和控制的组合需要实际对话验证；当前工具收口要求先读取证据再生成草案，不能任意调整调用顺序。

## S3：会议区间中的条件检查

用户：“明天 14:00 到 16:00 开会，14:00 开灯，14:30、15:15 检查温度，超过 28 度才把空调设为 26 度，16:00 关灯和空调。”

预期创建体验：一张统一任务提案，明确区间、设备、全部检查点、条件阈值和允许的动作；用户确认完整提案后才产生未来执行授权。

模拟执行：

| 时刻 | 输入事实 | 预期行为与记录 |
|---|---|---|
| 14:00 | 灯光未打开 | 按授权打开，保存回执与回读 |
| 14:30 | 新鲜室温 27℃ | 条件未满足，不调空调；保存读数与判断 |
| 15:15 | 新鲜室温 29℃ | 条件满足，将空调设为 26℃；保存动作与结果 |
| 16:00 | 区间结束 | 执行已确认的关闭检查点，相关调用收口后汇总 |

卡片组合：创建时的任务提案 → 工作台同一任务的检查点记录 → 结束报告。报告可展开环境读数、条件判断、动作结果；最终通知链接回同一 Task。

参与方式：传感器同时是观察对象和条件来源；空调与照明是执行对象；空调回读验证设定，传感器后续读数仅提供环境效果证据，不证明变化必然由该动作造成。

异常模拟：15:15 读数过期或传感器不可读，记录“条件无法判断”，不沿用 14:30 的旧值冒充当前值，也不默认条件满足。是否中止后续独立动作需在规格中决定；模型不会在执行中自行新增检查点。

当前可达程度：时间动作可由现有一次性任务部分表达；独立区间、多个检查点尚待实现。只读检查与条件执行是额外扩展，不属于仅放宽阶段数量即可获得的能力。

## S4：每日只读值班巡检

用户：“工作日 18:00 检查办公区的摄像头、环境和安全台账，结束后把结果告诉我，不操作设备。”

预期创建体验：一张周期计划提案，显示工作日 18:00、设备范围、只读检查内容、报告接收人和下一次发生时间。每次发生有独立结果。

模拟结果：四台摄像头中三台在线、一台在线状态未知；环境读数正常；安全台账未找到自上次巡检以来的新记录。

预期报告：

> 本次巡检结束。一台摄像头在线状态未取得，需要人工查看；其余读数和台账查询已完成。

卡片组合：报告摘要 → 视频检查块 → 环境检查块 → 台账查询块。创建者收到结束通知，点击回到本次 Task 报告。

参与方式：全部设备都是观察对象；本任务没有控制动作。不同检查项可以部分成功，报告保留各自查询时间和失败原因。

异常模拟：台账查询失败时不能写“无新告警”；在线状态未知不能写“摄像头离线”；不能从摄像头在线推断画面无人、正常或无安全事件。

当前可达程度：已有查询工具可用于当前对话；周期调度方向已接受但未实现。后台只读任务、观察结果持久化与报告、结束通知均需接线。

## S5：能耗异常调查

用户：“看看昨晚办公区为什么还在用电，有哪些设备值得检查？”

模拟输入：只有一条数月前的电表最新已知读数，以及当前灯光和空调状态；没有昨晚的连续计量数据，也没有可靠的电表到受控设备映射。

预期回复：

> 当前电表数据无法支持昨晚的分析。我可以列出当前仍开启的设备供你检查，但不能据此解释昨晚的用电原因。

卡片组合：能耗读数块（突出真实采样时间） → 当前设备状态清单 → 数据缺项说明。

参与方式：电表提供计量证据；灯光和空调提供各自现态。只有位置与计量覆盖关系明确时，才可联合分析。

用户再说“把现在仍开的灯关掉”时，重新读取当前授权设备状态，生成独立待确认草案。不能把调查请求视为控制授权。

异常模拟：禁止用当前设备状态追认昨晚运行情况；禁止从一条瞬时功率推导整晚电量；数据补齐后也不能把相关性直接写成已证原因。

当前可达程度：陈旧电表读数展示已有。昨晚统计、计量关系、能耗分析卡与独立状态清单的呈现均不应按现有能力承诺。

## S6：安全台账与人工查看

用户：“看看最近的水浸记录，相关摄像头也给我看看。”

模拟输入：台账有一条历史水浸事件，平台标记为已上报，没有恢复记录；摄像头和水浸设备的区域关系尚未核验。

预期回复：

> 台账有水浸记录，已上报标记不能证明现场已恢复。请先选择需要查看的区域或摄像头。

卡片组合：事件台账块 → 明确区域后的摄像头观察块与查看入口。没有可靠关联时先澄清，不直接把相似名称的设备绑定为“相关摄像头”。

参与方式：安全传感器提供事件记录；摄像头辅助人工查看。当前不生成恢复状态，不提供伪造的确认处置、关闭告警或消防联动按钮。

异常模拟：即使视频播放成功，也不能自动将事件标记为已处理；告警投递、人工查看、平台上报和设备恢复保持各自事实。

当前可达程度：台账和视频在线查询已有；生产播放待部署。实时事件触发、关联关系、告警处置接口与高风险联动未形成闭环。

## 从场景得到的产品判断

1. 先按信息用途组合有限组件：事实、提案、执行记录、报告。观察卡可复用；任务继续引用同一个 Task，不为每种设备另造一套任务。
2. 卡片数量不是灵活性的唯一标准。需要能表达“哪些事实支持这项提案”“哪些检查点只读”“为什么本次未执行”“哪些结果未知”。
3. 任务需要容纳纯观察步骤和条件步骤，才能让新增设备参与自动化。观察权限与控制权限分别核验，账号级可见目录不自动证明房间归属或控制权限。
4. 只读角色不能仅靠改名塞进现有 DeviceAction；它没有目标控制状态，也没有下发命令，需明确其执行结果和报告语义。
5. 建议体验模拟顺序：S1 验证多类观察呈现，S2 验证证据到草案，S4 验证后台只读任务，再用 S3 验证条件控制。S5/S6 同时用于检查数据缺失时的诚实表达。

本文不替代已接受的周期一期范围。上述顺序只是新增设备参与方式的探索建议，不修改当前实施排期。
