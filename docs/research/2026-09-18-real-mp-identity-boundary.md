# 真实 MP 用户身份与 Runtime 隔离边界调查

日期：2026-09-18  
状态：历史调查；客户会话桥接已实现，账户来源已于 2026-09-30 核验

2026-09-30 修正：真实 `account/me` 已返回客户业务在用的 `content.id`。用户明确“Token 频繁过期”是误记录；跨 Token 实验、刷新契约与失效停用阈值不作为本轮前置问题。账户主体与访问凭据仍须区分，服务端归属键接入属于我方实现事项。见[主体只读核验](2026-09-30-recurring-principal-readonly-verification.md)。以下 09-18 的环境与未实施状态是历史基线，不能重新引入已撤回的阻塞项。

## 结论

正式交付优先采用“合入客户小程序”的路径，而不是让独立 Agent 小程序再实现一套生产登录：

```text
客户小程序登录
  -> 客户 token + 当前园区/租户上下文
  -> Agent 请求封装
  -> Runtime 身份解析
  -> 当前用户 Authorized Device Scope
```

独立 `apps/agent-miniapp` 继续作为研发、回归和演示壳，只允许开发环境固定身份。它当前没有正式登录入口，也不是客户 AppID，不能通过替换 URL 直接变成生产小程序。

Runtime 的长期模型必须把三类对象分开：

| 对象 | 含义 | 是否适合做长期归属键 |
|---|---|---|
| `principalId` | 客户系统确认的稳定用户主体 | 是，记忆、日程、规则、告警的首选归属键 |
| `tenantCode`/工作空间 | 当前园区、组织或租户上下文 | 需要与主体组合使用，不能单独代表用户 |
| Provider credential | 当前访问上游物联接口的 Token | 否，只能作为请求凭据，不能当作稳定用户身份 |

当前 Runtime 用 `sha256(tenantCode + Authorization)` 作为会话 owner，能在开发和短期会话范围内隔离不同凭据，但它有两个结构性限制：Token 刷新会改变 owner；它不能证明两个 Token 属于同一个客户用户。因此该实现不能直接承载长期记忆、日程、自动化规则或告警归属。

## 已核对事实

### 客户小程序已有登录态

- `App.vue` 在没有 Token 时调用 `wx.login`。
- `store/modules/user.js` 通过客户 SSO 的 `thirdParty` 流程换取 `access_token`，并保存 `token_type/access_token/expires_in`。
- `apis/request.js` 已把客户 Token 放入 `Authorization`，把当前 `district.id` 放入 `tenantCode`。
- 当前 Token 刷新方法仍是注释状态；退出会清理本地缓存，但没有发现 Agent 专属的会话撤销契约。

### 独立 Agent 小程序仍是开发壳

- `apps/agent-miniapp/README.md` 明确没有客户登录、客户 AppID 和生产会话接管逻辑。
- `apps/agent-miniapp/config/index.js` 在开发版读取临时存储，否则回落到 `Bearer local-development`/`LOCAL`；3201 服务端再通过 `AGENT_DEV_IDENTITY` 替换为开发实例的真实身份。
- 独立项目的测试 AppID 登录身份不能等价于客户 AppID 下的真实客户用户。

### Runtime 已有的隔离能力

- 请求要求 `Authorization` 和 `Tenantcode`。
- 会话、草案和候选集按当前身份做 owner/tenant 校验。
- 设备目录由客户用户范围接口提供，Runtime 不应使用 Provider 全量目录越过上游授权。
- 生产范围仍需每次读目录、读状态和执行时重新使用当前身份；Token 不应进入模型上下文、会话正文或普通日志。

## 冻结的不变量建议

这些是不应由前端自行推断、也不应由 Token 哈希替代的边界：

1. 每个 Agent 请求必须绑定一个服务端解析出的 `principalId`、一个当前工作空间和一个 Provider credential。
2. 会话、长期内容、规则、告警和通知订阅按 `principalId + workspaceId` 隔离；Provider credential 只负责访问上游，不进入业务对象归属。
3. Token 刷新不应改变用户的长期内容和规则归属；主体变化或账号切换必须创建新的工作空间上下文。
4. 设备范围不是登录时永久复制的清单。读取、起草、确认和后台运行都必须按当前授权重新核验；撤权后旧草案不能继续执行。
5. 会话清除只清除对话活动和可清理的待确认草案，不删除用户记忆、日程、规则或告警历史。
6. 退出/切换用户后，客户端停止发送旧凭据；Runtime 拒绝新请求。已经开始的高风险控制不因 UI 消失而假报取消，结果按中断/未知事实收口并要求重新核实。
7. 开发身份只能在开发环境显式启用，不能由正式版前端、客户用户或后台任务继承。
8. 所有后台规则和告警必须有明确 owner、工作空间、设备范围快照、当前授权检查和审计 actor；不能仅依附六小时聊天会话。

## 09-18 原调查项与 09-30 修正

下列保留历史问题的主题；本轮不再以全部补齐为自动化的启动条件：

1. 客户用户 ID 来源已关闭：复用已认证 `account/me.id`，不再索取新主体字段；不得把 `openid` 当作业务主体。
2. Token 生命周期不作为当前待补契约。按已有凭据推进，保留实际鉴权失败处理；不因刷新代码未实现而假定频繁过期。
3. 园区/租户切换：`tenantCode` 的定义、用户可见范围、切换后的设备目录变化和权限刷新时机。
4. 退出、禁用、离职、权限撤销和角色变化的通知或查询机制；至少要支持 Runtime 在关键操作前拒绝失效身份。
5. Agent 页面正式集成位置：客户 AppID、开发/体验/正式环境、合法请求域名、HTTPS、流式响应代理和超时策略。
6. 历史短时 Agent token 建议未采用；现行一次性任务已在确认后加密托管执行凭据。后续周期计划沿用身份与凭据分离，不新增换票前置条件。
7. 多端并发与后台运行政策：退出后规则是否暂停、规则 owner 变更如何处理、运行中的动作如何接管。

## 验收案例

下列是身份边界的行为案例，不是等待 Token 生命周期调查的前置清单：

1. 用户 A 登录客户 MP，进入 Agent；Runtime 看到 A 的主体、工作空间和 A 的设备范围。
2. 用户 B 登录同一 MP 或另一设备；B 不能恢复 A 的会话、草案、记忆、规则或告警。
3. A 刷新 Token 后，仍能恢复 A 的长期内容和允许恢复的会话；不能因为凭据轮换生成另一份用户空间。
4. A 切换园区后，工作空间变化，设备目录重新加载；旧园区设备不能被新上下文直接操作。
5. A 退出后，旧请求凭据无法创建或恢复 Agent 资源；重新登录 B 后不得出现 A 的内容。
6. A 的设备权限被撤销后，旧待确认草案在确认时被重新核验并拒绝或缩减；后台规则暂停或进入人工接管。
7. Agent 运行中的网络断开、进程重启或客户端退出后，Runtime 能以真实状态收口，不重复下发不可幂等动作。
8. 每个长期对象和通知投递都能追溯到主体、工作空间、规则/事件版本和当前设备范围，而不记录明文 Token。
