## 结论

当前项目不能把下一阶段理解为“继续增加几个 Agent 工具”。自动化、告警和会议联动会把系统从一次性对话控制扩展为长期运行的业务系统，需要新增规则、运行、事件、通知、人工处置和结构化交互能力。

此前 Orca 参考摘要保留的调查方向包括计划、启停、预检查、时区、错过运行处理、手动触发和运行历史，以及任务依赖、恢复、通知和移动端接管。具体功能、页面路径和代码实现仍需逐项核验；这些不是本项目已验证能力。参考入口：

- [Orca Scheduled Automations](https://www.onorca.dev/docs/cli/automations)
- [Orca Orchestration](https://www.onorca.dev/docs/cli/orchestration)
- [Orca Notifications & Inbox](https://www.onorca.dev/docs/notifications)
- [Orca Mobile Companion](https://www.onorca.dev/docs/mobile)

另一个参考对象是用户明确提供的 [T3 Code](https://github.com/pingdotgg/t3code)。待调查的借鉴点包括 Agent 运行与交互控制面的分离、后台状态、权限请求、远程交互和跨端恢复；尚不能把这些方向逐项记为已核验产品事实。前一轮取得了远端 HEAD，但完整代码拉取未完成，源码级机制仍待核实。

## 对本项目的修正理解

### 自动化不是定时调用控制接口

一条可交付的自动化业务至少要经历：

```text
规则创建/修改
→ 影响范围预览
→ 权限和风险校验
→ 启用
→ 触发事实到达
→ 生成自动化运行快照
→ 逐动作执行与幂等收口
→ 运行结果、失败和人工接管
```

Agent 可以通过自然语言帮助生成规则，但规则保存后必须拥有明确版本、所有者、目标范围、动作白名单和安全策略。触发时不应再次依赖模型决定是否有权控制设备。

这不排除触发时运行 Agent：定时分析、巡检和生成建议，以及包含模型分析的混合流程，都保留为候选。需要确定的是权限和副作用由 Runtime 校验，而不是一概要求每次任务完全无模型参与。

需要参考成熟 ADE/Agent 工作台的能力包括：

- 规则启用、停用、暂停和删除；
- 运行前预检查；
- 时区、重复规则和错过运行宽限；
- 手动立即运行；
- 运行历史和逐动作结果；
- 失败重试与新旧运行区分；
- 规则版本和影响范围搜索；
- 决策门/人工确认；
- 运行心跳和卡死恢复；
- 从手机或小程序进行只读查看、继续、暂停和接管。
- 主机/运行环境保持后台常驻，前端离开后运行仍可继续；重新进入时恢复当前运行和权限上下文。
- 远程连接、设备配对、权限模式和环境选择必须有明确的撤销与失效语义。

### 富文本应升级为结构化富操作面

这里的“富文本”不应理解为让 Agent 输出更多 Markdown，而应理解为 Agent 回复中出现由结构化数据驱动的业务组件：

| 富操作面 | 业务用途 |
|---|---|
| 自动化规则卡 | 展示触发条件、设备范围、动作、风险、启停状态和下一次运行时间 |
| 规则编辑面板 | 修改时间、条件、设备、动作和通知策略，支持预览和保存 |
| 自动化运行卡 | 展示本次触发原因、规则版本、动作进度、部分失败和重试入口 |
| 告警卡 | 展示严重等级、位置、来源、发生时间、影响设备和当前处置状态 |
| 告警处置面板 | 确认、指派、备注、升级、关闭、人工接管和安全动作确认 |
| 通知收件箱 | 查看未读事件、筛选严重等级、跳转来源、标记已读/未读 |
| 统计和趋势面 | 展示能耗、人数、设备状态和异常趋势，不依赖模型拼表格 |
| 计划/审批面 | 在自动化或高风险联动执行前展示影响范围和待确认决策 |

这些组件应消费 Runtime 的结构化事件和业务投影，不消费模型生成的 HTML。组件的关键动作也必须回到公开 API，不能从展示文本反推执行参数。

## 告警能力

告警需要拆成四层：

```text
业务事件
→ 告警实例
→ 通知投递
→ 人工处置/升级
```

### 业务事件来源

- 设备报警或设备离线；
- 空调故障或状态长期未更新；
- 能耗突增、夜间持续用能、数据中断；
- 自动化运行失败、部分成功或结果未知；
- 会议联动准备失败；
- 规则冲突、权限变化或设备移出授权范围；
- 烟感、燃气、水浸等安全事件。

### 告警处置状态的候选模型

```text
OPEN → ACKNOWLEDGED → IN_PROGRESS → RESOLVED
                     └→ ESCALATED
                     └→ TAKEN_OVER
```

不同事件可以有不同的终态，但不能只保留“已推送/未推送”。告警应记录来源、严重等级、责任范围、关联设备、触发数据、当前责任人、处置动作、备注和审计时间线。

上述状态机是讨论示例，不是已冻结 schema。升级和接管也可能是独立属性或事件；个人已读、渠道投递、设备恢复与告警处置必须分别表达。

### 通知渠道现状

当前小程序仓库已有云函数形式的：

- `uni-push`：调用 uniCloud Push Manager；
- `weixin-mp-push`：调用微信小程序订阅消息；
- `weixin-template-push`：保留了模板消息示例。

但这些是独立样例/基础设施，不是 Agent 告警系统。当前尚未发现告警收件箱、通知偏好、渠道路由、投递记录、失败重试或事件与消息的关联模型。现有示例还包含固定 AppID、用户和模板值，不能直接作为生产告警实现。

可选闭环应调查：

1. 小程序内持久化收件箱，保证用户回到页面后仍能看到告警；
2. 微信订阅消息，前提是用户授权并配置正式模板；
3. 客户现有消息中心或其他真实渠道；uni-push 仅作为候选，需先核实适用终端和客户配置，不能假定可直接通知微信小程序；
4. 每次投递记录状态、失败原因和重试次数；
5. 同一事件去重、合并和升级，避免重复轰炸；
6. 点击外部通知后回到告警详情和处置面板。

短信、邮件、企业微信/钉钉等渠道可以通过 Notification Channel 扩展，但不应在第一条闭环里同时接入所有渠道。

## 候选闭环示例：会议预约联动

“会议预约驱动会议室环境准备”能够用于讨论规则、时间触发、设备动作、通知和富操作面，但用户尚未选定它为首个实施闭环。设备扩展、能耗、办公区运营、巡检、安全事件及其他业务保持开放，见完整业务目录。

```text
会议创建/修改/取消
→ 会议室与 Authorized Device Scope 映射
→ 会议前 15 分钟生成自动化运行
→ 打开照明、设置空调
→ 失败动作形成告警
→ 会议取消/延期时处理未执行或已执行动作
→ 会议结束后按策略恢复环境
```

如果以后选择这个示例，可讨论先限定照明和空调；门禁、消防和其他高风险设备单独冻结风险政策。人工暂停、单次运行、运行详情和安全的失败处理也需进入该切片的验收讨论。

## 当前缺口

- Runtime 没有自动化规则、运行、调度和告警领域对象；
- Runtime 的 NDJSON 事件流服务单轮 Agent 回合，不是长期业务事件总线；
- 小程序只有对话、草案和执行结果组件，没有自动化/告警富操作面；
- 已有推送云函数没有接入 Agent 事件和告警生命周期；
- 客户会议平台接口没有在当前仓库中被确认；
- Orca 和 T3 Code 的具体实现仍待固定版本、源码路径和官方资料核验；参考名称已纠正，不再等待所谓“24Tiao”资料；
- 合同附件一仍缺失，告警等级、责任人、通知渠道和急停范围未冻结。

## 下一阶段建议

先不要直接实现完整自动化平台。建议依次完成：

1. 通过 `/grill-with-docs` 冻结 Automation Rule、Automation Run、Business Event、Alert、Notification Delivery 和 Rich Action Surface 的领域语言；
2. 确认客户会议平台、告警事件源和通知渠道资料；
3. 在完整业务目录中选择一个闭环，并为它冻结业务、接口、权限和验收范围；不预先指定会议联动；
4. 再抽取可复用的规则/运行/告警能力；
5. 通过 `/to-spec` 和 `/to-tickets` 形成可独立验收的垂直切片。
