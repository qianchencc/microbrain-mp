# 下一版 Agent 是否更优：探索与对照证据

日期：2026-10-09。状态：只读探索；有局部确定性改善证据，尚无完整Agent优于现版的结论。

## 结论

不能在实施前确保未知请求上的整体表现必然更好。可以用明确业务范围内的前后对照决定是否交付：目标更准确、多轮意图保持、执行与报告连续，现有能力和强制边界不退步。局部改善不够时，继续保留现行主线。

本轮发现一个确定性改善，也发现隔离候选尚不具备直接替换主线的条件。位置分组与简短prompt仍是待验证候选；未因为用户授权探索而把它们升级成批准设计。

## 为什么不能直接宣布候选胜出

静态核对两份runner的工具声明，隔离候选新增 `get_device_details`，但没有当前主线的 `query_environment_history`、`query_energy_history`、`prepare_video_playback`。候选基线落后，不能用整份替换方式集成。该检查只确认源码声明差异，不代替各工具在实际来源下的运行验收。

两个版本仍有整层集合不完整的限制。本轮没有验证选择、排除、修改、恢复、Task/Plan作用域及报告解释。既有[17次诊断](../../plan/2026-10-09-agent-evidence-proof-return.md)包含固定前文，不能填补这些缺口。

Langfuse现有generation输入保存systemPrompt/messages和toolNames，没有在该记录中保存完整工具schema。持久化对话或工具名清单不能等同于完整provider请求。下一轮如需完整输入诊断，可复用既有隔离脚本的stream context捕获，并区分SDK调用上下文和实际线上请求。

## “更优”的建议交付条件

| 业务维度 | 新旧版应比较的实际结果 |
|---|---|
| 找对象 | 所选设备是否符合用户范围，歧义是否真实需要询问；不以拒绝所有请求获得高分 |
| 委托承接 | 自然生成候选后，选择、排除、纠正和改时间是否保留未修改的目标 |
| 操作与安排 | 实际设备集合、动作、时点/区间、重复规则及本次/周期作用域是否正确 |
| 报告追问 | 回到同一任务事实，区分受理、回读、未知与失败；新操作需要新确认 |
| 已有能力 | 两端目录、历史查询、录像准备、任务管理和会话恢复是否仍能完成原业务 |
| 使用成本 | 用户需要纠正/重复描述多少次；延迟与模型用量是否值得改善收益 |

验收同时包含正向请求、需要澄清的请求和非法/未知情况。安全边界由HTTP和执行行为验证，语言与多轮判断由真实模型验证；两类证据分别报告。实验前固定案例、预期、版本和规模；保留全部失败，报告逐例收益与退步，不仅报告总分。新的业务预期应由用户复核；不得把助手生成的答案自动当作真值。

第一条建议仍是自然首轮的照明委托：查候选→用户选择/排除/改时间→正确提案→确认→执行/回读→同一报告追问。需要隔离协议夹具上的真实模型运行才能回答它是否成立；不依靠固定首轮历史。把未参与调试的新表达和更名/重排场景留给最终版本检查，但小样本结果只支持该范围的判断，不代表普遍可靠性。
