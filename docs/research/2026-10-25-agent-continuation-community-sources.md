# Agent 继续语义：社区实践、卡片状态变化与 IoT 控制边界

- 日期：2026-10-25
- 访问日期：2026-10-25（Asia/Shanghai）
- 研究问题：当 UI 卡片失败、过期或读到新状态时，任务怎样继续，才能让 Agent 自己恢复，而不是让用户复制错误再发一遍？
- 范围：只取六份一手来源（官方工程文章、官方文档、协议规范和上游 Agent 源码/变更），比较它们对任务完成、模型轮次、持久状态、人工介入和错误归属的处理。本文不要求采用任何一个框架，也不修改业务代码。

## 结论

社区实践支持一个比“失败后重试几次”更基础的判断：**模型轮次结束、工具轮次结束、UI 卡片结束和业务目标完成是四个不同事件。** 如果模型返回了一个提案卡片，或者卡片动作失败后本地界面恢复了，任务并不因此完成。目标满足才能交付完成；需要用户事实/授权时暂停；无法安全继续时明确阻塞或终止，同时保留原事实。

这些设计让 Agent 能消费结构化事件并继续处理，无需用户把一段错误文本重新贴进聊天框。Anthropic 将 Agent 的会话和执行 harness 分开，并让新 harness 从持久事件继续；LangGraph 用 checkpoint 和 `interrupt()` 暂停、再以同一个线程状态恢复；Pi 在最近的实验性 durable 变更中把工具发出的 `handoff` 写入新上下文后继续同一次提交，直到后续模型回答或明确终止。这些是不同的实现选择，不是统一标准，但它们共同保留了继续所需的事实。

对当前 IoT 场景，最重要的恢复证据不是一个 `retryable` 字段，而是可观察的后续动作，例如：新增了持久事件、重新读取了权威状态、模型确实重新进入、参数或目标发生了有依据的变化，或用户补充了缺失事实。新增事件或模型 re-entry 只能证明“继续活动被调度/发生”，不能单独证明目标有进展；重复记录同一个错误、原样重放同一个读取或重新生成同一张旧卡片，都不应重置 `no_progress`。若错误被标为可重试，却没有新的 durable event、没有模型 re-entry、没有新的事实读取，系统只是在延迟失败，不能算继续。安全上限（模型轮次、费用、墙钟时间和重试次数）仍然必须存在；工具数量只能作为资源上限或观测指标，不能单独作为成功条件。

模型、宿主运行时、用户和 IoT 服务端各自拥有不同的判断权：模型可以修正工具参数、改选只读路径、解释事实并提出澄清；宿主负责会话状态、协议、执行预算和恢复边界；用户负责补充未知事实和作出需要人的授权；服务端负责身份、设备范围、当前能力、版本冲突和物理写入结果。MCP 的工具错误建议把可操作的执行反馈提供给模型，但也明确区分协议错误和工具执行错误；这不等于任意异常都应反复回流模型。

### 需要记住的三个边界

1. **目标完成不是“最后一轮模型返回了文本”。** 宿主可能在工具查询后记录/发出 `run.completed`，模型也可能只生成普通答案，但两者都可能没有产生任务需要的提案、确认或验证证据。终止条件必须看业务目标和权威事实，不看工具数量、模型轮次或 UI 是否出现过卡片。
2. **用户澄清/授权是暂停与恢复，不是错误复制。** 暂停时应保留原始目标、待确认提案、所需补充字段、当前状态版本和安全边界；用户只需要回答缺失问题或做出确认，恢复时这些内容仍属于同一任务。
3. **IoT 写操作不能照搬 Agent harness 的回放。** 断线、超时或卡片过期时，写请求可能已经到达设备或网关。未知结果必须先查权威操作状态或回读；没有明确幂等语义时不能自动重放，确认仍然需要当前授权和当前状态。

## 从来源抽取的行为原则

### 1. 任务完成与模型轮次终止必须分离

Anthropic 的 Agent loop 以环境反馈决定下一步；Pi 的工具控制显式区分 `handoff` 和 `terminate`。这说明“模型输出了一个 assistant message”只代表一次生成结束，不能直接写成业务任务 `finished`。

本项目的判定应至少能回答三个不同问题：

- 这一次模型请求是否已经结束？
- 当前工具/卡片回合是否已经结束？
- 原始用户目标是否已经得到权威事实或安全终态？

前两个可以是 `done`，第三个仍可能是 `continue`、`awaiting_user`、`unknown` 或 `failed`。这是对来源的工程化推论，而不是某个框架的强制状态枚举。

### 2. 卡片失败应成为同一任务的观察

卡片是 UI 对提案、确认或结果的投影。卡片执行失败、卡片过期、范围读取失败和设备状态变化都应产生结构化观察，至少带有：任务/会话关联、原始目标引用、动作阶段、错误类别、是否可能已产生副作用、当前权威状态版本和建议的下一步。

这条原则来自 Anthropic 的“每一步取得 ground truth”、工具返回“specific and actionable”反馈，以及 MCP 对工具执行错误的 `isError` 语义。**推论是：** UI `catch` 只修复显示状态还不够；它必须把事实送回同一 Agent 上下文，或把任务稳定地暂停在等待用户/程序恢复的位置。用户不应负责把错误再翻译成模型输入。

### 3. 错误归属按可修正性划分

| 现象 | 首要归属 | 可以继续的证据 | 终止/暂停边界 | IoT 限制 |
| --- | --- | --- | --- | --- |
| 参数、枚举、缺字段、工具选择不完整 | 模型 + 工具契约 | 错误包含可修改字段，模型重新进入并改变调用或补齐输入 | 同一错误无变化、预算耗尽或缺少可行路径 | 只能修正请求形状，不能代替授权 |
| 只读网络/上游瞬时失败 | 宿主运行时，必要时再交模型 | 单层有界重试，或重新读取/换只读来源，形成新事实 | 持续失败、认证/权限失败、无新的信息 | 读取应标注时间和来源，不能把旧读数当新状态 |
| 卡片过期、范围/设备状态改变 | 宿主 + 业务服务端 | 重新读取权威状态，生成与当前版本匹配的新提案 | 需要重新确认、权限变化或无法确定当前状态 | 不能直接重放旧确认 |
| 写请求已发出但响应丢失 | IoT 服务端/宿主 | 通过操作 ID、幂等键或权威回读确认状态 | 查询不到权威结果时保持 `unknown` | 不能把超时当成未执行，也不能盲目第二次下发 |
| 缺少用户事实或人工批准 | 用户通过可恢复中断 | 原目标和待补字段仍在会话状态，用户只补事实/授权 | 用户拒绝、撤回或上下文已失效 | 授权必须重新按当前身份和设备范围判断 |
| 协议、解析、会话持久化或运行时故障 | 宿主程序 | 恢复入口能加载原任务/事件，或给出明确不可恢复原因 | 不能把损坏的响应伪装成模型可修正错误 | 不得让模型自行越过安全边界 |
| 同一错误持续重复且无进展 | 宿主运行时 | 新事件、新事实、改变后的调用或用户输入至少出现一种 | 进入有界 `no_progress` 终态，保存最后事实和下一步 | 不以“再试一次”掩盖未知写入 |

表中的“可以继续”是验收条件，不是“必须继续”的命令。模型可能仍然选错，服务端可能仍然拒绝；宿主只能保证信息、状态和边界没有丢失。

### 4. 恢复必须有进度，而不是只有可重试标签

从 LangGraph 的可恢复中断、Anthropic 的环境观察和 Pi 的 durable handoff 可以抽出两个适合本项目的判定：一次 recovery attempt 是否被调度，看是否有后续事件或模型 re-entry；一次 recovery 是否有**有用进展**，则必须在此基础上出现以下至少一项：

- 持久化了新的、非重复的事实或错误证据；
- 完成了一次针对当前版本的权威读取；
- 模型重新进入，且输入包含上一次观察并产生了可解释的不同路径；
- 调用参数、工具路径、范围或提案依据发生了可解释的变化；
- 用户提供了缺失事实或当前授权；
- 服务端给出了新的受理、执行、回读或拒绝证据。

若 `recovery.kind = retryable_read`，但没有新增事件、没有模型 re-entry、没有读取结果变化，原 pending card 仍然挂着，那么“可重试”只是分类结果，不是恢复结果。即使新增了同样错误的事件或重新进入模型，只要没有新的事实或可解释的路径变化，也不应把它算作有用进展。这个判断是本项目的推论，用于避免把排队成功误报为任务继续，也避免重复错误把 `no_progress` 计数清零。

### 5. 澄清与授权要恢复同一任务

LangGraph 把人工输入作为图中可恢复的 interrupt；Anthropic 的长运行 Agent 以持久会话重新接管；Pi 的 follow-up 仍然挂在同一 durable run 的边界上。它们都避免把用户的下一句话当作一条没有历史的全新任务。

因此，“继续”必须能重新得到，并在被阻塞等待时保留：

- 原始用户目标及其范围；
- 已完成的事实读取和时间/版本；
- 未完成的提案、确认要求和安全边界；
- 最近一次失败及其是否可能产生副作用；
- 用户补充内容应被解释为对哪一个待处理问题的回答。

部分读取结果、已确认的范围事实和当前阻塞原因也必须随任务保留；等待用户期间不能因为模型轮次结束或 UI 卡片隐藏而丢弃这些上下文。

如果目录或卡片读取在模型第一次运行前失败，之后的显式“继续”只携带这两个字，而没有原目标和失败上下文，系统无法知道继续什么。这不是用户表达不清，而是任务恢复上下文丢失。

## 与当前三个反例的概念对照

以下三项是本项目本地探针提供的观察，不是外部来源的事实；它们用来检验上述原则，不用来推出某个具体代码补丁。

| 本地观察 | 暴露的语义缺口 | 依据上述原则应观察到的外部行为 |
| --- | --- | --- |
| 确认范围读取在 adapter2reads 后失败，`recovery.kind = retryable_read`，但没有新的 durable event、模型 re-entry，旧 pending card 仍在 | “可恢复分类”与“实际继续”被混为一谈 | 用户仍看到同一任务处于处理中或明确暂停；系统应能证明新读取/新模型输入/新事实至少发生一项，否则应收敛到有原因的终态 |
| batch4 多个不同照明搜索后出现 task card；batch5 搜索成功却 0 tools、没有 card，宿主直接记录 `run.completed`，而实际只有 2 次模型轮次、5 次工具 | 把模型轮次、工具批次或宿主终态事件当作目标完成信号 | 终态应依据原始目标是否已获得提案/确认/验证证据；工具数量不是完成证明，但仍可作为独立的资源安全上限 |
| 目录失败发生在模型前；随后 UI 的“继续”没有带回原始 user goal | 用户输入被当成新的孤立请求，任务上下文没有可恢复 | “继续”应恢复同一任务的原目标、失败事实和下一步；若无法恢复，应明确说明任务已失去上下文，而不是悄悄生成无关回复 |

这些反例共同指向一个验收问题：**从用户最后一次可见动作开始，系统能否在没有用户复制错误的情况下，证明同一任务仍在推进、正在等待授权，或已经以可解释原因结束？**

## 要求、框架选择与本项目推论

| 层次 | 内容 | 说明 |
| --- | --- | --- |
| 行为要求 | 模型轮次终止不能直接代表业务目标完成；恢复必须保留原目标和当前事实；卡片失败必须进入结构化任务状态；写操作未知结果必须核实；重试必须有界并能说明进展 | 这些是从多份来源共同机制和 IoT 副作用边界推导出的验收要求，不绑定实现框架 |
| 框架选择 | 可用 LangGraph checkpoint/interrupt、Pi durable inbox/handoff、Anthropic 式 session/harness 分离，或现有 runtime 的等价机制 | 这些方案的状态模型和事件语义不同，没有理由把其中一个升格为强制社区标准 |
| 本项目推论 | 将卡片状态变化当作同一 Agent 任务的 observation；用 `no_progress` 识别“标记可重试但没有有用进展”；让完成判定依赖 IoT 权威证据；将待确认提案和版本纳入可恢复上下文 | 这是面向当前客户小程序和 IoT 写入风险的设计判断，需要由真实业务闭环验证 |

## 反模式

- 在 UI `catch` 中只显示错误、恢复按钮状态，然后把任务标记为 finished。
- 给错误贴上 `retryable`，却没有创建可观察的恢复事件、重新读取或模型回流。
- 用“最后一轮有 assistant 文本”“run.completed”“工具批次为空”作为业务完成条件。
- 让用户发送“继续”后从零创建模型输入，丢掉原始目标、范围、待确认卡片和最后一次事实读取。
- 把同一份旧卡片当成新状态，或在状态版本改变后直接重放确认动作。
- 把 IoT 写超时当成“没有执行”，无查询就再次下发。
- 把协议/解析/权限拒绝的内部细节原样交给模型，期待模型靠改参数越过宿主或服务端边界。
- 以全局工具数或固定轮次数量替代目标、进展和副作用状态判断；同时误以为因此可以取消费用、时间、轮次和重试安全上限。

## 对 IoT 的适用性和限制

可以直接借鉴的部分是：结构化工具反馈、持久任务上下文、可恢复人工中断、模型 re-entry、宿主的有限恢复边界，以及把运行 harness 的故障和业务会话分开。这样 UI 卡片只负责呈现当前提案/事实，用户也不需要充当错误转发器。

不能直接照搬的是 coding agent 常见的自动重放假设。文件编辑或测试命令通常可以通过 harness 重新执行；真实设备写入可能已经发生，网关/设备可能延迟回执，状态也可能被其他控制方改变。对 IoT，确认仍然需要当前身份、设备范围、能力和版本；写操作在结果未知时应停在 `unknown`，先查状态或回读，再决定是否允许新的确认。

本文没有提出分布式工作流平台、全局消息队列或新的基础设施要求。当前问题首先是任务语义：系统是否保存了足以继续的事实，是否把 UI 事件送回同一 Agent 上下文，是否区分了“这一轮结束”和“目标完成”，以及是否在无进展时诚实收口。

3. Anthropic，*Scaling Managed Agents: Decoupling the brain from the hands*，官方工程文章，<https://www.anthropic.com/engineering/managed-agents>。说明 session 与 harness 的分离、事件日志和从 `sessionId` 唤醒。来源展示 Anthropic 的托管 Agent 做法，不代表所有 Agent 必须使用该服务。
4. LangChain，*Thinking in LangGraph*，官方文档，<https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph>。说明状态分解、可恢复错误、人工中断和不可恢复错误的不同路径。来源是 LangGraph 的图模型，不能直接证明本项目应迁移到 LangGraph。
5. Model Context Protocol，*Tools*，2025-11-25 规范，<https://modelcontextprotocol.io/specification/2025-11-25/server/tools>。说明 `tools/call`、`isError`、协议错误与工具执行错误的分层，以及将可操作执行错误提供给模型的建议。规范不定义 UI 或恢复次数。
