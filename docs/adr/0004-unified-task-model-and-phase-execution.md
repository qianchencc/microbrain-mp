# 统一任务模型与任务阶段执行边界

- 状态：已接受（2026-09-25 冻结执行规则与执行身份）
- 日期：2026-09-24

系统只保留一种用户可见的业务结构：`Task`。现在执行的设备草案、稍后执行的设备操作、指定时刻执行的关闭动作，以及覆盖一段时间的会议准备，都是任务；区别只在任务的执行时间和任务阶段数量。持久化不是另一种业务对象，而是任务记录、阶段结果和设备审计的保存策略。当前只支持一次性任务，不支持长周期重复计划。

## 统一任务模型

```text
Task
  id
  regionIds
  purpose / label
  schedule { executeAt | startsAt + endsAt }
  phases[
    {
      at
      devices[
        { deviceId, targetState, command }
      ]
    }
  ]
  report { summary, phaseResults, anomalies, operatorActions }
  status
  sourceConversation / sourceTurn
```

任务阶段保存完整的设备集合和每个设备的目标状态，而不是只保存一句“关灯”。会议任务的第一阶段可以是“空调 26 度、所有灯打开”，第二阶段可以是“空调关闭、所有灯关闭”。单次关灯任务只有一个阶段；延迟五分钟关灯也只有一个阶段。

任务阶段到期时，自动化执行器直接处理任务，不再调用 Agent：

```text
读取阶段中的全部设备状态
  -> 对每台设备与 targetState 比较
  -> 已满足目标：记录 no-op/satisfied
  -> 未满足目标：直接调用对应设备接口
  -> 记录控制回执及可用的权威回读
  -> 阶段完成、部分完成、未核验或失败
```

因此，设备提前被人工关掉不是错误。任务的目标是使设备达到目标状态，而不是证明系统亲自发出了每一条命令。设备无法读取、调用失败、权威回读未达目标或仅有受理回执而无法核验时，阶段保留相应的异常或未核验结果。

## 从用户输入到任务结束

以“下午 14:00 到 15:00 在办公室开会，开始时空调 26 度并打开所有灯，结束时关闭空调和所有灯”为例：

```text
用户输入
  -> Agent 识别办公室和时间区间
  -> Agent 查询并确定目标设备
  -> Agent 获取当前状态，准备任务草案
  -> 用户看到一个 14:00—15:00 的任务卡
  -> 用户确认创建任务
  -> 任务进入办公室区域面板
  -> 14:00 执行第一阶段：全量读取、按需调整、回读
  -> 15:00 执行第二阶段：全量读取、按需关闭、回读
  -> 任务结束；结果和审计进入历史
```

Agent 的职责到任务创建为止：理解意图、找到设备、读取当前状态、整理目标和展示草案。执行时设备已经确定，自动化层直接调用设备接口，不让 Agent 再做一次无意义的设备检索或规划。

## 草案和任务的关系

“帮我关灯”也生成同一种任务，只是它的任务阶段时间是现在：

```text
用户输入：帮我关灯
  -> Agent 读取目标灯光状态
  -> 如果全部已关闭：不生成草案，也不生成任务
  -> 如果仍有未关闭设备：生成一个待确认任务
  -> 用户确认
  -> 立即执行唯一任务阶段
```

“五分钟后关灯”使用相同结构，只把阶段时间设为五分钟后。此时创建任务时可以保留完整设备集合和目标状态，即使创建瞬间灯已经关闭，因为到执行时设备可能再次被打开。

## 任务状态与阶段状态

已确认任务的状态：

```text
scheduled <-> executing（多阶段任务可返回等待下一阶段）
scheduled / executing -> completed / partial / unconfirmed / failed / missed / interrupted / cancelled
```

待确认或已过期的提案不属于已确认任务。阶段状态：

```text
pending -> executing -> verified / satisfied / partial / unconfirmed / failed / interrupted
        ├──────────────> missed
        └──────────────> cancelled
```

`satisfied/no-op` 是正常成功结果，不是异常。任务完成后不再产生新的执行，但区域面板可以保留它的历史记录。任务记录的保留时间不改变任务是否已经完成。

若阶段中所有设备仅有 `unconfirmed/unknown`，且没有明确拒绝或失败，阶段与单阶段任务汇总为 `unconfirmed`，不能误标为 `failed`，也不能因后来读到当前目标状态而追认 `completed`。照明 Office 状态缺少执行时上报时间；当前状态应与执行收据分开呈现，并作为需要关注的结果进入区域提示。

任务可以带有 `report` 属性。报告由阶段结果和设备审计汇总而来，至少能说明：哪些设备已满足目标、哪些设备实际下发过、哪些设备离线或回读失败、是否发生人工操作，以及任务最终是完成、部分完成、未核验还是失败。报告可以提供可读摘要，但摘要不能脱离结构化执行事实。

## 富交互组件边界

富面也只需要一种任务卡：

```text
task.proposed
  -> 展示任务目标、时间和阶段摘要
  -> 用户确认

task.created / task.updated
  -> 展示同一个任务的区域归属、阶段状态和结果
```

当前 `action.proposed -> turn.draft -> ActionPanel` 是旧的设备草案专用链路。它可以作为兼容适配层，把“一阶段、立即执行”的设备草案映射为统一任务，但不能继续作为自动化领域模型。未来不注册 `action_draft`、`automation_task` 两套业务组件，而是注册一个带版本的 `task` 富面类型，用阶段数量和状态渲染不同内容。

模型不能直接注册组件、写任务或在未来时刻执行设备调用。模型通过 Agent skill 形成结构化任务意图；Runtime 校验设备、区域和目标；任务执行器在阶段到期后直接调用设备接口；对话和区域面板都投影同一个任务对象。

## 边界

- 任务保存具体设备和目标状态；执行时读取全部设备，再按需写入。
- 任务完成后可以保留记录，但不再存活。
- 当前只实现一次性任务；重复计划另行讨论，不进入本阶段。
- 区域选择器只是 Agent 的关注上下文；任务创建时必须把实际目标区域和设备固定进任务。
- 设备提前达到目标状态是成功的无操作，不应重新发命令或报错。
- 区域面板用时间轴展示区域任务和任务报告；设备面板用时间轴投影该设备经历的任务操作、操作人、来源和结果。
- 到期执行使用创建者托管的执行身份，见下文第 6 条。

## 执行规则（2026-09-25 冻结）

1. **设备集合固定**：任务创建时固定已经找到的具体设备和目标状态；之后新加入区域的设备不自动加入旧任务，设备消失则在执行结果中记录缺失或部分完成。
2. **阶段相互独立**：前一阶段部分失败不自动取消后一阶段；例如会议开始时一台空调离线，结束阶段仍然尝试把其他设备关掉。
3. **阶段之间不监控**：阶段之间有人手动开关设备不算异常，到下一个阶段时重新读取全部设备并向该阶段目标收敛。
4. **取消而不编辑**：首版不支持编辑。未开始的任务可整体取消，执行中的任务可取消剩余阶段，已结束的任务不可取消；取消不回滚已经发生的设备动作，记录保留为已取消。用户在区域面板中以“删除任务”发起取消；任务编辑与用户手动创建属于另一业务范围。
5. **明确的创建与取消动作**：Agent 提出的任务创建和任务取消都以富面呈现，用户显式确认后才写入；普通聊天文字不直接产生或撤销未来副作用。这只是写入确认，不是区域角色或审批体系。
6. **执行身份：创建者凭据托管**：用户确认任务时，Runtime 把该用户当前的客户登录凭据加密后与任务绑定保存，到期执行时以创建者身份读取和控制设备，任务结束即删除。凭据只用于该任务，不出现在任何接口响应或日志中；加密密钥缺失时 Runtime 拒绝启动。客户 SSO 是单会话语义，创建者在别处重新登录或退出会使托管凭据失效，此时后续阶段以“创建者登录已失效”失败，不改用其他身份。客户提供稳定的后台服务身份后可替换本机制，但它不再是接入后台执行的前置条件。
7. **错过的阶段**：阶段到期后 10 分钟内仍可补执行；超过则记为已错过、不再执行，后续阶段照常进行。晚到的执行可能覆盖他人在这段时间里的人工操作。同一窗口也约束确认：确认时首个阶段已过去不足 10 分钟则立即执行，超过则拒绝确认并要求重新创建。
8. **设备种类**：未来阶段只支持照明和空调。门禁开门不幂等，不进入延迟或区间任务。
9. **即时操作的兼容**：现有 `action.proposed` 草案确认链路保留为即时执行入口；草案执行完成后写入一条“一阶段、立即执行、已结束”的任务记录，使区域与设备时间轴只从任务记录投影。

长周期重复计划、持续占用监控、冲突检测、复杂优先级和通用工作流不属于当前一次性任务范围。

### 为什么是创建者凭据托管

备选有三：等客户提供后台服务身份、使用固定开发账号、托管创建者凭据。等待客户会让整条任务能力停在外部依赖上；固定账号会让所有任务以同一个人的权限执行，破坏授权设备范围按用户过滤的边界。托管创建者凭据保持“任务以创建者的权限执行”，代价是服务器保存长期凭据以及单会话失效导致的执行失败；前者以加密存储和随任务删除约束，后者以明确的失败原因暴露给区域面板。
