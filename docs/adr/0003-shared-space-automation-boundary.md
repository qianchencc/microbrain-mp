# 共享空间自动化边界

- 状态：已接受（2026-09-25 修订：冲突与接管移出当前设计）
- 日期：2026-09-24

## 背景

办公区、楼层和会议区通常由多人共同使用。自动化的业务语义应以区域为中心，而不是以创建规则的用户为中心。用户仍然需要被记录，因为系统要知道谁创建、修改、确认或处置了规则；但用户不是共享区域自动化的目标 owner。

区域自动化需要一个公共的区域运营面板。用户在 Agent 中说明目标，Agent skill 负责收集时间、区域和动作等必要信息；创建成功后，任务进入对应区域的面板卡片。首版卡片支持查看和取消，不引入单独的区域角色、审批或接管权限矩阵。

## 当前边界

1. Agent 的默认工作范围是用户可访问的全部工作空间。范围选择是物联 Agent 与区域面板共用的单选关注区域，只作为未指明地点请求的默认值，不改变 Agent 的授权可见范围，也不隔离会话。
2. 区域是客户系统中的办公区域，彼此扁平，不做上下级汇总。任务的区域归属由其设备所在区域推出；跨区域任务出现在每个相关区域的面板中。
3. 用户是任务的创建者和维护者，但任务的业务归属是区域。能看到任务中任一设备的用户可以看到该任务；授权范围覆盖任务全部设备的用户可以取消它。
4. 任务只能通过 Agent 创建，不引入通用工作流编辑器；区域面板不提供新建入口。Agent 可以创建任务，也可以提出取消任务，两者都需要用户在富面上显式确认。
5. 区域面板卡片首版只支持查看和“删除任务”（语义为任务取消，记录保留）。任务编辑与用户手动创建属于另一业务范围，首版不做。不设计区域角色、审批、确认或人工接管。
6. 不检测、不提示、不合并共享资源冲突。多个任务对同一设备提出不同目标时，各阶段按自己的时刻独立执行，全部任务都显示在时间轴上，由区域内人员自行判断和取消。
7. 区域列表只在存在部分完成或失败、且当前用户尚未查看的任务时显示异常提示；进行中和已完成的任务不产生提示。首版只有应用内提示，不做微信订阅消息等外部推送。

## 例子

李工、王工和陈工都能看到 26 楼运营办公区：

```text
李工：今天 18:00 关灯
王工：今天 18:00 关灯
陈工：今天 18:00 开灯，我要加班
```

三个任务都进入 26 楼区域面板，并在 18:00 各自执行：李工和王工的任务读到灯已关闭时是成功的无操作；陈工的任务是否最后生效取决于执行顺序。系统不裁决、不避让，但三张卡片和各自结果都在时间轴上可见，任何有权限的人都可以取消其中一个。

## 为什么移出冲突与接管

原方案要求在面板上显式呈现冲突并由人处置，这需要可靠的意图比较、占用事实和处置状态机，而当前没有任何一个前置条件，首版也没有真实用户反馈证明它必要。时间轴已经让同一时刻的多个任务并排可见，这是首版足够的透明度。若之后出现真实的冲突投诉，再以新的 ADR 引入检测。

## 影响

- B02“办公区开闭与节假日模式”是区域运营策略，规则和运行记录进入区域公共面板。
- B12“值班巡检与运营简报”不直接改变共享设备状态，适合作为更早的低副作用切片候选。
- 共享空间任务、个人偏好和即时设备操作都使用统一 Task 表达，见 [ADR 0004](./0004-unified-task-model-and-phase-execution.md)。
