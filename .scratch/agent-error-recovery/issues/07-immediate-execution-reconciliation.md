# 07: 即时确认失败后核实原执行结果且不重复下发

**What to build:** 即时设备草案勾选、保存、还原、重核及确认失败后，系统核实原对象并继续操作；确认断流时取得原回执，智能体基于实际结果解释和补查，结果未知不盲目重放控制。

**Blocked by:** 01 — 操作关联与恢复承接；02 — 安全只读补查。

**Status:** implemented-awaiting-integration-evidence

## 开工与范围

读 [规格](../spec.md)、[执行地图](../execution.md)、[验收方案](../acceptance.md)，尤其即时控制证据边界。仅处理既有确认/回执恢复；不增加模型直接控制工具，不调整空调参数协议、门禁行为或任务执行领域。

## 实现约束

- 区分零下发、受理/拒绝、已下发未知与未选/未下发项。先读原操作回执，后按权限读取可用现态；保留原终态与逐项事实。
- 确认前的勾选/保存/还原/重核/放弃失败先核对当前 revision 和用户草稿，不丢用户选择，不以失败恢复为由自动确认。纯数据读取可重试，参数冲突需要明确差异。
- 客户端回包丢失不能重新调用控制；相同确认只回放，未下发且内容未变的安全重试必须有确定性资格。
- 未知操作的新动作需要独立提案和现行确认；现态不能回填历史 verified，门禁不可由现态证明历史开门与否。
- 总结失败不丢回执；模型可以安全补写解释，不重跑下发。前端显示核实进度、已完成部分与仍未知部分。

## 验收

- [ ] A09：丢回包、明确拒绝、下发中断分别正确恢复，设备写请求计数没有增加。
- [ ] A09a：勾选保存、还原、过期重核与放弃的读取失败/版本冲突正确恢复，用户草稿和服务端 revision 一致，未自动确认控制。
- [ ] 一部分有回执、一部分未知、一部分未下发时逐项诚实显示；不能笼统全部失败或成功。
- [ ] 零下发重试、重复确认和在途恢复均保持原授权/幂等；停止、新消息不启动新控制。
- [ ] 工程夹具覆盖照明/空调及门禁非幂等反例；真实模型据实际回执补查/解释，无直接控制能力。
- [ ] 生产重读已有终态操作证明无新增下发；新的真实设备动作只按 acceptance 中已批准测试对象执行并保存证据。缺少授权/物理证据保持本项未验，不能宣称真实下发恢复已通过。

## 验证与交付

从确认/回执/对话公开接口观察结果和真实协议出口写次数，不直接断言内部 dispatch 标志。发布前保留故障注入与真实读回的证据区别，plan 明确受理、回读及物理效果的证据等级。
