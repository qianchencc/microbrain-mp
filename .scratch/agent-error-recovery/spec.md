# 智能体错误恢复与委托完成规格

Status: ready-for-agent
日期：2026-10-24。用户要求：准备全部后续方案与票据，并由执行代理自行完成真实业务验收。本文冻结后续实施范围；当前仅完成准备。

## Problem Statement

用户委托智能体处理业务，却经常收到参数错误、工具失败、卡片确认失败或“请重试”，需要自己复制错误、刷新和重新描述目标。当前普通工具错误已有模型反馈通道，但恢复被重复调用守卫、提案失败计数和专用提案的终止标记截断；卡片和启动阶段的失败又位于模型循环之外。

## Solution

系统先核实失败阶段与已有结果，程序恢复可确定处理的瞬时错误，模型修正可行动的参数或业务方案。用户看到恢复进度，最终得到业务结果、必要的新确认或明确的未完成原因。失败步骤保留审计关联；每次恢复沿用同一委托、来源和授权，不产生重复任务或控制。

## User Stories

1. 作为委托者，我希望查询偶发超时后系统自行重试，以便不用重复发送问题。
2. 作为委托者，我希望工具参数错误由智能体修正，以便不用理解接口字段。
3. 作为委托者，我希望智能体能连续修正不同问题，以便不会因为第二个字段错误就放弃。
4. 作为委托者，我希望确实无进展时系统及时停止，以便不会无限等待或消耗模型。
5. 作为任务创建者，我希望确认回包丢失后系统先查创建结果，以便不会重复创建。
6. 作为任务创建者，我希望卡片过期后智能体承接原目标，以便无需重新描述设备、时间和口径。
7. 作为任务创建者，我希望时间或成员改变后的方案重新展示并确认，以便授权内容明确。
8. 作为周期计划创建者，我希望已有等价计划时直接取得该计划，以便不反复创建。
9. 作为任务管理者，我希望修改、取消、停用和启用失败后系统核对实际状态，以便不会重复变更或误改范围。
10. 作为公司用户，我希望夜间收口及分阶段提案也能修正错误，以便复杂委托得到与普通提案相同的承接。
11. 作为能耗查询者，我希望后台准备中的数据在有限等待后自动返回，以便不用自己反复问。
12. 作为报告读者，我希望已完成的统计和报告在解读失败时保留，以便不会丢失成果或重做全部读取。
13. 作为设备操作者，我希望确认超时后先核对原回执，以便不重复下发。
14. 作为设备操作者，我希望结果未知时清楚知道哪些已下发、哪些未下发，以便不会误以为全部失败。
15. 作为用户，我希望启动时目录短暂不可用也能自动恢复，以便不会在模型尚未开始前就放弃。
16. 作为用户，我希望模型连接暂时失败时系统安全续接已有事实，以便不用重做整个委托。
17. 作为移动端用户，我希望断流、返回页面及应用重开后恢复进度和结果，以便不会重复操作。
18. 作为用户，我希望停止或提交新意图后旧恢复不再继续，以便系统尊重最新选择。
19. 作为不同来源和身份的用户，我希望错误恢复保持原权限边界，以便不会跨来源或跨账户读写。
20. 作为定时报表用户，我希望到期读取偶发失败时安全恢复，并最终收到同一任务的报告和通知。
21. 作为用户，我希望恢复成功后看到完成结论、恢复失败后看到具体下一步，以便不用从工具日志猜业务是否完成。
22. 作为项目负责人，我希望代理操作真实模型、网关及前端完成验收并保存证据，以便不再由我代替执行验收。

## Seams

- 业务入口与验收 seam：现有对话 HTTP/NDJSON 消息接口、任务/周期确认与管理接口、任务/计划详情/列表/收件箱、小程序真实点击。恢复事实沿这些对象与事件持久化，不新增独立错误编排服务或第二套状态机。
- 测试 seam：优先复用现有 HTTP 行为测试、任务/计划夹具、对话事件恢复和小程序视图测试；真实模型/网关与前端点击作为推理和交互验收，不用私有函数或表结构代替。
- 只有现有对象无法表达恢复关联时，才在现有 proposal/task 行增加最小持久字段；先确认现有接口无法覆盖。

## Implementation Decisions

1. 复用现有 Conversation、Turn、Draft、Task、Plan、Occurrence、阶段、报告和收件箱；不新增独立 Goal、工作流引擎或另一套任务状态机。每轮只推进一张业务票，不顺手修改空调排程或其他功能。
2. 工具步骤失败与委托终态分离。仅在恢复耗尽、无法继续、用户停止或需要实际用户决定时收口；成功以权威业务状态为准，不能靠隐藏错误或模型自述表示成功。
3. 错误按可修正输入、瞬时只读、准备中、对象状态变化、授权拒绝、写结果未知、程序故障分类。模型只接收安全且可行动的事实；底层恢复资格由代码决定，不向模型暴露任意内部异常或凭据。
4. 失败事实包含原操作/对象/版本、来源、失败阶段、已成功部分及副作用状态；已有状态和事件为权威。客户端仅提交对象/操作标识，服务端重读事实；客户端报错文本不是恢复授权。
5. 首票建立最小同会话恢复承接：原业务操作标识绑定主体、来源、会话与版本；重复触发合并为一次恢复，并复用现有事件持久化和一个活动 run 约束。确需新增持久字段时只记录现有对象无法表达的恢复关联，不预建通用错误数据库。
6. 同参重复判断区分上次成功、瞬时失败和新事实。瞬时只读可有限同参重试；参数修正允许继续；完全相同的确定性错误且没有新证据才视为无进展。保留总回合、调用和截止时间预算，禁止靠普遍加大预算解决设计问题。
7. 每次业务恢复沿用原操作 ID；网络重试不重跑整轮模型。确认回包丢失先查原对象，已成功就回放结果。无副作用且已确认内容完全相同的安全重试可继承原确认；成员、时间、目标或管理作用域变化重新确认。
8. 已过期卡片可重建提案，不能自动把过时时刻平移到“现在”或明天。持续空调窗口沿现行排程处理今天剩余检查点与明天完整模板，恢复不改其语义。等价计划返回原对象而非重复创建。
9. 下发后未知先查回执与可用现态，保留逐项 unknown 和未下发事实。现态不反推历史执行；门禁等非幂等动作不能盲重放。模型不能获得直接设备控制工具或绕过确认。
10. 纯渲染、组件缺陷由前端修复；卡片业务请求失败才进入业务恢复。界面复用现有进度、处理记录、卡片和详情，标明恢复中/已恢复，避免整屏错误立即要求用户处理。
11. 数据准备中先在当前截止时间内有界等待；超出预算就诚实收口。本范围不承诺新增跨天异步聊天通知，已有 Task 的持久调度与通知继续使用原机制。
12. 模型中断只在已保存合法消息/工具结果且无待核实副作用时续接；不重放已执行工具。无法续接时保留业务成果与明确状态。租约恢复已有实现，仅验证相容性，不重做事故修复或追查事件循环停顿。
13. 定时任务只在同一已认领检查点内恢复瞬时只读，保持固定成员、授权、统计口径与一次报告/通知。设备控制阶段及过期检查点沿既有执行/漏跑规则，不扩大为停机补执行。

## Testing Decisions

- 从现有 HTTP/NDJSON、确认/管理 API 和前端事件消费进入行为验证；遵守项目“最窄稳定公共接口”，不测试私有标记、表结构、SQL 或逐字提示词。
- 每张票同时覆盖一条成功恢复和它最相关的失败边界，不另建纯测试主线。沿用现有对话、混合草案、公司任务、周期管理、能耗、流恢复及任务通知测试形态。
- 需要证明推理的场景使用真实模型，需看到其收到错误后修正的轨迹；预设模型只证明工程行为。真实模型失败轨迹全部保留，不能挑成功样本。
- 工具错误可通过隔离 staging 对单次请求受控注入，之后读取真实网关；明确标注“真实模型/网关 + 受控故障”，不能写成自然生产故障。
- 真实验收由代理完成，包括创建与确认临时只读任务、实际墙钟到期、报告、收件箱、前端恢复与清理。按 [验收方案](acceptance.md) 区分模拟器、浏览器、真机、物理动作证据。

## Out of Scope

- 重新开发 Agent、引入新框架/依赖、全局重构、任意客户接口工具或更宽设备权限。
- 自动绕过登录/授权/业务确认；恢复时偷偷改变设备、目标、时间和取消作用域。
- 停机补跑、重做全部后台自动化、微信订阅消息、跨天异步聊天投递。
- 视频 SDK/组件渲染缺陷的泛化自修复；未接入能力与历史其他票据。
- 本轮准备阶段实施或切换生产；后续执行阶段按票完成发布和真实验收。
