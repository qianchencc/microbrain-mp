# 04: Company 收口协调设计、真实交付与效率验收

**What to build:** 重新审视并收敛收口的业务模块、Pi 工具和上下文设计，在原小程序用自然表达完成跨两层照明/空调收口、保留区域澄清、确认前调整及任务追问；具备明确现场授权后完成实际两阶段结果验收。

**Spec:** ../followup-spec.md

**Blocked by:** 01、02、03 的源码集成（已满足）；真实控制段另外依赖明确现场授权和受控发布。只读准备不依赖照明新增反馈接口。

**Status:** ready-for-agent

- [ ] 开工先形成简短设计决议：现有问题及证据、Pi/业务模块职责、工具输入与结果、引用生命周期、用户操作流程，以及旧接口保留/合并/替换/退役的明确去向。01–03 的已实现代码不构成必须保留的设计。
- [ ] 固定原项目、运行版本与真实目录基线；区分源码 HEAD 和活动服务版本，保护并行改动、原数据库和密钥。
- [ ] 先完成可审阅的发布差异与回退准备；未获服务切换授权时使用真实只读网关与临时数据库验证候选，不把旧服务行为冒充新实现。
- [ ] 冻结 6 类复杂输入：跨楼层混合与排除、口语同义、真实歧义补充、待确认改时间、已确认任务追问/修改、范围失效或用户更换目标。每类至少 2 次只读验证，保留全部成功与失败。
- [ ] 计划成员和两个阶段符合真实目录；无歧义不多问，歧义不猜；补充/改时不漂移，已登记任务不另建，确认前控制数为零。
- [ ] 按设计决议收敛新旧入口、重复准备与恢复职责，避免只叠加工具/提示/守卫。记录实际入口选择和结果，验证其它观察/即时/任务请求仍可用；超出收口契约的目标不被误改成关闭。
- [ ] 使用同等业务输入记录模型、范围、预检耗时及请求/token 数；首次反馈与可确认结果分别计时，全部失败入账，不把异范围历史数据当性能对照。
- [ ] 原小程序中验证卡片、补充、改时、返回和任务引用；浏览器/编译不代替微信验收。
- [ ] 实际两阶段执行仅在明确范围、时间与用户授权后开展：核对下发集合、并发、回读、重扫不重复和最终唯一通知；照明无权威反馈继续未核验。
- [ ] 交接同时列出设计取舍和替换结果、只读路径结论、微信结论、真实控制结果及上游缺口；设计决议与只读结论形成即可释放 05/06，整票不得提前关闭。

## 范围与成本

目标包含业务协调重设计及真实交付，不以调优设施为交付物。按设计证据决定保留或替换，预计净新增生产代码 0–150 行并允许删除/替换旧实现，另加最窄公共接口回归；行数是预算，不用于阻止必要重写。显著超出先检查模块职责，不顺手重写其它业务。

原票 02 的权威回读与完整真实效率未完成项继续保留。并发上限、新业务动作、周期任务、全局缓存和新模型供应商不在本票范围。
