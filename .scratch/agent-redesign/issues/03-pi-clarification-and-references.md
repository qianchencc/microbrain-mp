# 03: Pi 结构化澄清与跨轮引用收口

**What to build:** 当范围、排除项或用户指代不完整时，Agent 能返回最小必要澄清；用户补充后，Pi 基于服务器返回的结构化缺口继续形成同一业务计划，并保持范围、草案和任务引用一致，不重复搜索或扩大用户未确认的范围。

**Blocked by:** 01: 复杂 Company 请求生成可确认计划

**Status:** implemented-pending-gateway-acceptance

- [x] 地点/排除项以结构化缺口返回，设备类型沿本业务固定的照明/空调，不新增其他类型。
- [x] Pi 的补充请求只携带当前来源、授权上下文和仍有效的结构化引用；对话历史不能单独恢复范围或执行事实。
- [x] 用户补充后只修正明确缺口，不因换地点词或重复提问逐步拼接未确认设备范围。
- [x] “刚才的范围”“排除的会议室”“这个任务”引用以服务器对象重核；已登记任务沿原 Task 查询/修改。
- [x] 服务器错误明确收口；无实际补充、过期、跨会话或已登记任务的续接不重新建单。
- [x] 澄清完成后仍进入现有确认卡，不新增独立的澄清面板或新的 UI 组件体系。

## 实施边界（2026-10-19）

- 复用同一收口业务服务，以独立的新建/补充工具约束参数：只替换服务器列出的未解析项，或调整两个时间；已解析成员和关闭动作不得由模型重新抄写。
- 上一轮结构化请求、缺口及已解析成员绑定保存在现有 conversation_turns 的一个业务 JSON 列中；不建新会话平台、表或前端面板。删除/编辑退役的轮次沿现有生命周期处理。
- 引用限当前 Company 会话及有效期；补充前重核已解析范围的完整成员与控制绑定，变化则要求重新声明完整请求，不悄悄追加设备。
- Pi 每轮只收到摘要、缺口、候选地点及引用 ID；任务引用继续沿原 Task 查询/修改通道。事实来自服务器，不从历史助手文字恢复。
- 预计新增约 200–300 行业务与接线代码，回归仅从消息/恢复/确认接口进入，覆盖复杂补充、过期/跨来源、授权或范围变化与重启。

- 真实 GLM 初测证明单工具同时支持完整请求/引用补充会混带旧数组（7.074 秒澄清、5.050 秒续接被拒绝，零控制），因此拆成严格的新建与补充 schema，共用同一执行函数；这是接口消歧，不增加业务种类。
- 完整回归发现旧测试要求把 runtime_context 作为历史前缀保留，与本票的当前权威输入边界冲突；现保留业务历史前缀，但运行上下文只注入本轮，公开任务追问回归能读取刚确认的正确 taskId。
