# 01: 创建确认遇错后沿原任务核实并承接

**What to build:** 用户确认创建后，暂时目录失败、回包未知和必要内容变化都进入原创建委托；无需再发补救消息即可交付同一 Task/Plan、必要新确认或明确阻塞。

**Blocked by:** None (can start immediately)

**Status:** in-progress

**规格与追踪：** [业务规格](../spec.md)故事 1–4、30–34；[验收矩阵](../acceptance.md) C01–C03、C23、C24；[执行地图](../execution.md)。

## 冻结范围

仅创建确认闭环，建立本票所需最小原委托/操作事实和恢复观察契约。保留既有过期重开和幂等行为，不建设通用恢复引擎，不改其他卡片流程。

预估产品代码变更 180–320 行；测试/证据按必要行为单列，不以行数为通过标准。开始实现前核实当前基线和最窄切片；超出上界约50%时先说明原因并重新收窄/拆票，禁止借机扩成通用平台。阻断外发现记后续，不扩本票。

## 可独立演示的闭环

用真实模型生成只读定时报表待确认卡；确认目录在隔离实例暂不可用，恢复后用户不补发消息。界面显示核实进展，最终只创建一个原任务；另测服务端成功但响应丢失。

## 继续、等待与退出

- **继续：** 已知未创建且同内容仍有效时，在总预算内恢复读取并继续原确认；写结果未知只读原操作。需要推理时真实模型可见原目标、当前事实和合法下一步，系统事件不作为新用户消息。
- **等待必要决定：** 时间已过、设备/内容实质改变或需重新授权时保留原目标，提出必要问题/新版本卡；未确认不能以新时间或新成员创建。
- **退出：** 停止、不兼容新意图或当前权限失效立即停止相关恢复；无新事实/截止到期交付明确阻塞，原结果仍可核实，不假称后台永久重试。

## Acceptance criteria

- [ ] 确认瞬态读失败耗尽已有重试后有持久可恢复事实和实际承接，不停在503加刷新；健康恢复后无需用户补救消息得到同一创建结果。
- [ ] 成功丢响应、双击和双端并发均只产生一份 Task/Plan；未知写入不更换操作标识；新内容必须重新确认。
- [ ] 过期时间/设备变化的真实模型轨迹产生最小必要决定，决定到达后接续原委托；不能要求从头创建来替代恢复。
- [ ] 微信实际点击显示创建中/核实中/必要确认/最终结果；重开保持原状态，成功后旧错误不再是主状态。
- [ ] 断线不取消既有 run；隔离进程重开后下一次已鉴权恢复请求核实原操作，无重复写、无未验证身份自动复活。
- [ ] 停止、新意图、撤权、跨来源和迟到结果通过公共边界验证；卡片系统恢复不误触“新消息退休旧卡”。
- [ ] 从最窄稳定公共接口完成相关红灯→绿灯与必要回归，不测试实现字符串；证据区分受控协议、真实模型、真实网关、微信与生产。
- [ ] 执行变更相关检查及必要窄审，语义提交业务代码/测试/文档，记录实际版本、验收证据、未验边界和清理结果；代理自行完成验收，不以“待用户测试”关闭。

## 验证入口与关闭条件

把既有卡片红灯探针表达的业务要求纳入稳定 HTTP/恢复回归；用真实模型和隔离故障验证错误后的实际合法动作，再做微信点击。交付创建结果、待决卡或有原因的阻塞，不只记录新 run。

源码和既有探针导航统一在执行地图，不把当前行号/私有实现固化为验收。做到相应可观察业务结果、必要权限/取消边界和本票证据后才能 done；待发布或待真实验收如实标记，不能只凭编译、一次重入或错误文案改善关闭。
