# 07: 即时确认结果未知时核实原回执并继续解释

**What to build:** 即时确认后遇到未知回包、部分结果或解读失败时，智能体围绕原回执核实并交付准确说明，绝不因恢复重复下发控制。

**Blocked by:** 06

**Status:** draft（待新拆分粒度与阻塞边确认；尚未发布为 ready-for-agent）

**规格与追踪：** [业务规格](../spec.md)故事 18–20、30–34；[验收矩阵](../acceptance.md) C14–C15、C23；[执行地图](../execution.md)。

## 冻结范围

仅即时执行后的回执核实/结果解读恢复，沿用票06的原草案与操作关联；不新增真实客户控制验收、不把现态推定为历史物理动作。

预估产品代码变更 80–160 行；测试/证据按必要行为单列，不以行数为通过标准。开始实现前核实当前基线和最窄切片；超出上界约50%时先说明原因并重新收窄/拆票，禁止借机扩成通用平台。阻断外发现记后续，不扩本票。

## 可独立演示的闭环

隔离协议接受一份已确认操作但丢失响应；读取原操作分别返回已受理、部分拒绝或仍未知。真实模型据原回执解释结果，写请求计数始终一次。

## 继续、等待与退出

- **继续：** 先读原操作回执，未知期间仅做允许的只读核实；已存回执直接复用，解读失败重做解释而不是执行。
- **等待必要决定：** 新的设备动作或改变原指令必须作为新的业务决定和确认；对未知旧动作不能请求用户“再点一次”替代核实。
- **退出：** 核实无进展/到期保留未知或部分结果，停止只取消后续核实不能撤销已发生动作；撤权不绕过读取边界。

## Acceptance criteria

- [ ] 成功丢响应与并发确认只读同一回执，不换操作标识，受控物理写调用计数不增加。
- [ ] 已受理、拒绝、部分受理、仍未知和已核实结果分别表达，不把读到当前状态冒充原动作成功。
- [ ] 解读失败后原回执仍可查看；真实模型合法补查并解释原结果，不再执行。
- [ ] 微信原卡→核实中→准确结果/明确未知可见；停止、撤权和晚到结果不发新写入。
- [ ] 记录协议/真实模型证据边界；无具体设备动作授权时零客户控制，不声称物理成功已验。
- [ ] 从最窄稳定公共接口完成相关红灯→绿灯与必要回归，不测试实现字符串；证据区分受控协议、真实模型、真实网关、微信与生产。
- [ ] 执行变更相关检查及必要窄审，语义提交业务代码/测试/文档，记录实际版本、验收证据、未验边界和清理结果；代理自行完成验收，不以“待用户测试”关闭。

## 验证入口与关闭条件

公共接口配合隔离执行适配器做接受后断响应与计数；真实模型读取同一回执。UI 使用隔离入口，物理证据明确未覆盖且不成为额外阻塞。

源码和既有探针导航统一在执行地图，不把当前行号/私有实现固化为验收。做到相应可观察业务结果、必要权限/取消边界和本票证据后才能 done；待发布或待真实验收如实标记，不能只凭编译、一次重入或错误文案改善关闭。
