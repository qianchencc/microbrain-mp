# 04: 修改任务冲突或丢包后承接原修改

**What to build:** 用户修改原任务时，冲突、暂时读取失败和响应丢失由系统核实；模型沿原修改意图解释差异、必要时再确认，不覆盖并发更新。

**Blocked by:** 01

**Status:** draft（待新拆分粒度与阻塞边确认；尚未发布为 ready-for-agent）

**规格与追踪：** [业务规格](../spec.md)故事 11–12、30–34；[验收矩阵](../acceptance.md) C09、C23；[执行地图](../execution.md)。

## 冻结范围

仅任务修改提案及确认的原操作承接，复用票01契约；不重写所有任务管理、不改历史已执行结果。

预估产品代码变更 80–140 行；测试/证据按必要行为单列，不以行数为通过标准。开始实现前核实当前基线和最窄切片；超出上界约50%时先说明原因并重新收窄/拆票，禁止借机扩成通用平台。阻断外发现记后续，不扩本票。

## 可独立演示的闭环

把一个只读报表任务改到新的未来时间；让第一次确认响应丢失，再制造另一端已改版本，分别完成同结果回放和最新差异的新确认。

## 继续、等待与退出

- **继续：** 先读原修改操作与最新版本；已经成功直接交付同结果，未成功且仍合法时继续既有幂等操作，需要判断差异时回流原修改目标。
- **等待必要决定：** 并发内容、时间、设备成员变化需要新的实质确认；保留用户希望改变的字段，不能覆盖最新不相关修改。
- **退出：** 撤权、停止、新意图、原任务终结无法修改或预算无进展时明确终止；不得另建替代任务掩盖失败。

## Acceptance criteria

- [ ] 成功丢回包不新增修改版本或新任务；暂时读取失败后无需复制错误完成原修改。
- [ ] 版本冲突的真实模型看到原目标与最新差异，生成必要新确认，确认前无写入。
- [ ] 时间已过只请求必要新时间，不静默顺延；未改变字段和其他端新修改保持。
- [ ] 微信原卡→恢复→差异→新确认→同任务结果可操作；停止/来源/权限及迟到结果不重新修改。
- [ ] 从最窄稳定公共接口完成相关红灯→绿灯与必要回归，不测试实现字符串；证据区分受控协议、真实模型、真实网关、微信与生产。
- [ ] 执行变更相关检查及必要窄审，语义提交业务代码/测试/文档，记录实际版本、验收证据、未验边界和清理结果；代理自行完成验收，不以“待用户测试”关闭。

## 验证入口与关闭条件

隔离 HTTP 并发/丢响应回归，真实模型承接差异，微信实际修改一项只读任务并核对唯一对象/版本。

源码和既有探针导航统一在执行地图，不把当前行号/私有实现固化为验收。做到相应可观察业务结果、必要权限/取消边界和本票证据后才能 done；待发布或待真实验收如实标记，不能只凭编译、一次重入或错误文案改善关闭。
