# 智能体连续承接委托：业务规格

**Status:** ready-for-agent（规格依据已明确业务目标收敛；2026-10-26 配套票据和 Pi 策略已获认可，01开始实施）
**日期：** 2026-10-25。仅准备规格与票据，本文件不表示功能已经实施或发布。

## Problem Statement

用户希望智能体尽量完成原委托，而当前系统常把工具、卡片或应用操作的错误直接展示给用户。已有有限重试、参数纠错、幂等确认和结果保留，但跨模型回合、确认卡、应用入口的业务事实未连续交接。用户要复制报错、重新描述或重新建任务，且宿主有时在取得新进展时仍强制退出。

已复现三个反例：确认卡读失败后无后续委托承接；五个不同成功检索触发全部工具撤除；模型启动前读取失败使后续“继续”缺失原请求。它们是本地受控反例，并非生产故障比例或真实模型验收结果。管理卡、即时草案等另有静态检查发现，需要各自闭环验证。

## Solution

围绕同一业务委托保留可核实的目标、进展和待决事项。短暂技术错误先在统一预算内恢复；需要策略选择或参数修正时，把可行动的错误与权威事实交给智能体；确实缺少业务决定时才暂停并向用户提问。卡片操作回流原委托，不能成为对话之外的死路。

完成条件取决于原委托：创建任务以登记成功、返回同一 Task/Plan 为交付；待确认卡不算创建成功。定时执行继续由现有调度承担，不保持模型空循环。报告委托以原范围/期间的报告和可用结果交付为完成；结果未知必须如实保留。

本规格以十条业务闭环实施。先做创建确认，逐条复用最小状态与观察契约；不先建设通用恢复平台。旧有确定性恢复继续保留。每条闭环都必须证明自动继续、必要暂停和真实退出正确。

## User Stories

1. 作为委托用户，我希望创建确认遇到暂时故障时仍沿原任务核实，以便无需复制报错或再说一次“帮我创建”。
2. 作为委托用户，我希望确认成功但响应丢失时返回同一个 Task 或 Plan，以便不会重复创建或误以为未创建。
3. 作为委托用户，我希望时间已过、设备变化时得到保留原意图的必要提问或新确认，以便不会被要求从头重建，也不会被擅自改时或扩范围。
4. 作为委托用户，我希望退出页面再回来仍能看到原操作的真实进展，以便不会被永久转圈或旧错误误导。
5. 作为委托用户，我希望模型启动前目录或引用读取失败后仍保留完整原请求，以便后续恢复和“继续”确实针对原委托。
6. 作为委托用户，我希望身份重新验证后再恢复有权限的原请求，以便不会把未验证身份的请求写进别人的会话。
7. 作为委托用户，我希望短暂失败恢复后自动继续原查询，以便不需要承担技术重试工作。
8. 作为委托用户，我希望调查多个明确地点时能继续利用每次取得的新事实，以便不会在第五个成功检索后被强制收尾。
9. 作为委托用户，我希望模型能修正可恢复的工具参数并尝试合法替代路径，以便不会把模型能够处理的问题转交给我。
10. 作为委托用户，我希望真实无进展或预算耗尽时得到可理解的未完成说明，以便不会无限循环或把一段解释当成业务完成。
11. 作为委托用户，我希望修改任务出错后核实原修改是否已经生效，以便不会覆盖其他人的新修改或重复提交。
12. 作为委托用户，我希望并发版本变化时看到最新差异和必要的新确认，以便确认的始终是当前真实内容。
13. 作为委托用户，我希望取消本次与取消全部的原选择能在恢复中保持，以便不会误取消其他执行或整个计划。
14. 作为委托用户，我希望周期暂停和恢复遇错后核实同一计划的状态，以便不会重复切换、补跑过去检查点或另建计划。
15. 作为委托用户，我希望即时草案选择和参数编辑失败时保留我的已确认选择，以便不会丢失编辑并被迫重新挑设备。
16. 作为委托用户，我希望还原或重核遇到冲突时沿同一草案协调最新事实，以便不会把过期修订误当可执行方案。
17. 作为委托用户，我希望放弃草案后停止恢复，以便不会在我已退出后重新出现旧操作。
18. 作为委托用户，我希望即时确认回包未知时自动查原回执，以便不会因恢复而重复控制设备。
19. 作为委托用户，我希望部分受理、明确拒绝与结果未核实被准确区分，以便不会把平台受理或当前读数冒充物理动作成功。
20. 作为委托用户，我希望解读失败时仍保留回执并继续说明，以便执行事实不会随着模型答复失败而消失。
21. 作为委托用户，我希望能耗数据确实还在准备且有进展时继续等待和补查，以便不会过早收到要求手动重试的报错。
22. 作为委托用户，我希望部分报告成功时保留原附件，只继续未完成部分，以便不会重复统计、重复交付或丢掉已有结果。
23. 作为委托用户，我希望报告已保存但解读失败时继续解读原报告，以便不会改变统计范围和期间或重生成一份。
24. 作为委托用户，我希望从任务列表、详情、收件箱和报告返回时能恢复原对象，以便查看失败不会把已存在的任务说成不存在。
25. 作为委托用户，我希望对当前任务或报告追问时模型获得经授权的原对象事实，以便不需要复制错误、任务编号或完整报告。
26. 作为委托用户，我希望查看遇到暂时故障时看到核实状态和正确恢复结果，以便页面刷新与智能体解释使用同一权威状态。
27. 作为委托用户，我希望定时报表从创建、修改、暂停恢复到到期交付连续完成，以便可以真正把工作交给系统。
28. 作为委托用户，我希望关闭小程序后未来检查点仍正常执行并只通知一次，以便任务不依赖前端保持在线或模型持续空转。
29. 作为委托用户，我希望第二个真实未来检查点仍能交付并可继续追问，以便验收覆盖持续运行而非一次演示。
30. 作为委托用户，我希望随时停止或提出不兼容的新意图能停止旧恢复，以便旧请求不会后来突然执行。
31. 作为委托用户，我希望权限或来源变化时只恢复仍合法的部分，以便恢复不会跨租户、跨用户或跨 Office/Company。
32. 作为委托用户，我希望必要决定到达后沿原委托继续并保留已完成事实，以便业务暂停不会变成信息丢失和从头重来。
33. 作为委托用户，我希望进程中断后再次通过身份验证能核实并接续原操作，以便不会盲目重放未知副作用，也不会收到虚假的后台继续承诺。
34. 作为委托用户，我希望看到处理中、等待决定、已交付、部分完成或明确阻塞的真实状态，以便能分清模型回合结束、任务创建和未来执行结果。

## Implementation Decisions

1. **权威事实与模型决策分工。** Runtime 决定身份、来源、版本、幂等、可确认范围和真实执行状态；模型在允许的动作内选择补查、修正、解释或提问。UI 展示权威投影。正常勾选、幂等回放等确定性动作不必额外调用模型。
2. **原委托的最小恢复事实。** 利用既有会话/轮次/业务对象关联目标、主体与固定来源、对象与操作标识及版本、已完成事实/附件/回执、失败阶段、潜在副作用、允许的下一步、待决问题、预算和取消/意图标识。事实必须足以重开后核实；不新建平行 Task 引擎，不默认添加新依赖、任意凭据存储或通用队列。
3. **生命周期分离。** 公开状态至少能区分处理中/恢复中、等待决定/确认、已交付、部分完成/阻塞、已停止。单次 run 的终态与委托交付、已登记任务的未来执行分开；不得仅凭模型有文本就标业务成功。内部状态名称与存储复用在首票冻结，不在本规格预设表结构。
4. **自动触发与关联。** 服务端确认的操作故障进入原操作恢复；客户端回包未知时先核实同一操作。并发点击、多标签页、重复传输不产生第二份恢复或副作用。系统恢复事件不能伪造成新用户消息，不能意外触发现有“新消息退休旧待确认卡”规则。
5. **继续条件。** 目标尚未满足、有合法且有意义的下一步、尚在同一总预算/截止时间内，则继续。新授权事实、有效候选、纠正后的参数、后台准备阶段推进可构成进展；重复日志、换错误文案、重复同一失败或模型再次运行不构成进展。连续成功检索不能仅因次数阈值被视作无进展。
6. **限制与退出。** 保留同一活动处理阶段现有的总模型/工具/时间预算，恢复/刷新/重开不重新授予一整份预算；只读核实也不能无限延长原截止时间。必要用户决定到达后可按既有请求规则开启下一有界阶段，等待确认和未来调度不要求模型一直运行，也不由系统恢复自行刷新预算。不以提高阈值替代进展判断。抑制同一无效动作后，允许仍有意义的合法替代动作。无进展且无替代、预算到期或不可恢复异常时，交付已有成果及明确阻塞原因；持久安排不存在时不声称后台会继续。
7. **必要暂停。** 时间已过、实质内容/成员/目标/管理范围改变或缺少授权时，保留原目标并提出最小必要决定/新确认。不自行平移时间、扩大设备集合、重建计划、覆盖并发修改。输入到达后重新核实并沿原委托继续。
8. **副作用。** 未知写入先读原对象/操作回执；禁止恢复时换新操作标识重试。仅既有幂等契约允许的同内容、同版本、有效时间且当前授权的操作可以安全回放；不全量重跑模型回合、设备控制、报告或通知。受理、回读现态和已核实物理结果分别表述。
9. **停止与边界。** 显式停止、不兼容新意图、身份/来源失效使相关恢复停止；晚到结果不得重新唤起旧操作。已经发生的动作保留事实，停止不能伪称撤销。兼容的澄清属于原委托；前端旧卡不能绕过当前版本和授权。
10. **断线与重开。** 小程序断流不等同停止，既有活动 run 在预算内继续；重新打开用原操作核实权威状态。进程中断后由下一次经过身份验证的恢复请求接续可合法推进的部分，不保存任意原始凭据以自动复活。已确认未来任务仍按现有调度执行，不补跑历史检查点；本规格不承诺进程重启后无需任何触发的通用恢复。
11. **入口失败。** 有可信主体后保存原意图及失败事实供后续推理；身份尚未验证时不调用模型、不把请求写入未经验证的用户会话。重新验证后才能恢复；安全的本地草稿不能跨账号自动提交。
12. **前端范围。** 复用现有卡片、列表、详情和报告入口，补足恢复中、待决定与最终结果的状态衔接；保持创建中即时反馈与防重复提交。恢复成功后旧错误不再是主状态，但过程记录可查。默认不改视觉体系、不新做基础控件。
13. **证据关联。** 通过安全关联号串起委托、run、原操作和对象、观察事实、所选下一步与最终结果；不得记录 Token、完整敏感请求或全量客户数据。需要真实推理时记录脱敏轨迹，单有追踪记录不能证明交付。

## Testing Decisions

- 复用已获认可的 HTTP/NDJSON、当前会话恢复和现有微信入口。先从能覆盖行为的最窄稳定公共接口写红灯，再实现；只有纯工具循环策略才从现有公开 runner/provider 边界验证。不上新增私有调试接口，不断言内部函数/字符串或固定工具调用顺序。
- 三个已复现反例作为确定性回归起点；四个已有正确恢复回归必须保留。测试覆盖当前权限、来源、并发、未知结果、停止/新意图和预算退出的相关业务路径。
- 证据分级：受控模型/协议夹具用于可重复故障和幂等；真实模型用于判断可行动错误是否导致合法补查/修正/提问；真实网关用于字段和业务事实；真实微信操作用于状态衔接。不得互相冒称。
- 故障注入只在隔离实例/数据库副本/受控适配器中进行；生产不人为打断客户服务。真实模型的客户控制调用必须阻断，除非获得具体设备/动作/时间授权；协议回执验收不宣称真实物理动作通过。
- 每票以能展示的业务结果及公共接口证据验收；涉及 UI 语义时由代理实际点击验证，不能只编译。纯后端票不强制新增前端流程。发布前运行必要类型/构建与对应测试，小程序有改动则完成既有开发及发行编译，无微信上传/提审门槛。
- 最终以真实只读定时报表委托完成创建/管理、关闭客户端、两个合法未来检查点的真实到期、报告通知及同对象追问，作为持续运行证据。模拟时钟不能替代真实到期；一次成功不能推导全天候无故障。
- 详细故事追踪、验收用例和关闭标准见[验收矩阵](acceptance.md)。

## Out of Scope

- 更换 Pi 或引入 LangGraph、AG-UI、托管 Agent 服务；通用工作流/恢复平台、全局新存储系统、无限重试与单纯增大回合预算。
- 旧 CPU/事件循环长停根因调查、原控制详情503的上游根治与全站性能改造；这些错误的原委托承接仍在本规格相关业务范围。
- 未经具体授权的真实设备控制、把受理称为物理成功；已移出的物理验收不重新成为本轮完成阻塞。
- 计划历史补跑、默认迁移既有客户计划、新通知渠道、微信上传提审和全新视觉改版。
- 无预算的永久模型常驻，或进程退出后缺少触发/合法身份时仍自动恢复所有委托的承诺。
