# 验收矩阵与关闭规则

**Status:** needs-info（与票据拆分同步审阅）。这是一份验收计划，下面没有任何用例被宣称已通过。

## 证据层级与记录

- D：受控 provider/协议夹具的确定性行为。适合故障、幂等、并发、取消和预算；不能证明真实模型理解。
- M：真实模型轨迹，记录输入中可行动事实、合法下一步和最终原目标结果；仅“进入模型/调用工具”不算交付。
- G：真实网关的当前授权业务事实；失败需保留原结果，不造数据。
- U：代理操作真实微信界面，截图/操作记录证明处理中、必要确认、错误退场及最终对象一致。
- L：真实墙钟到期的已确认任务交付；明确开始/结束时间和实际连续跨度。不能由 D/M/U 单独推导。

每条记录最少包含：日期、两仓提交/运行版本、隔离或生产环境、脱敏委托/对象/操作关联号、原目标、故障注入位置、预期与实际终态、已发生副作用次数、证据位置、未验边界和清理状态。不得写入 Token、个人身份信息或全量客户数据。未做填未做；夹具/真实模型/真实网关/生产证据分开。

## 通用通过条件

1. 原目标最终得到交付，或只在真正缺少决定时等待，或在无安全推进可能/预算耗尽时明确阻塞；绝不能因 run 结束而冒充业务成功。
2. 有恢复余地的故障不要求用户复制报错、从头重建或重复确认未变内容。需要新时间/成员/范围/版本时才提出对应必要决定，不隐式变更。
3. 不重复副作用、不扩大当前授权，恢复与系统事件不会误退休原卡；停止、新意图、迟到结果的隔离逐票落实。
4. 涉及界面状态的票由代理实际操作验证；后端策略票用最窄公共边界和真实模型证明，既有 UI 能正确消费可复用不重做。
5. 过程失败可留记录，恢复成功后主状态和说明反映成功；永久失败要有具体阶段、已完成部分及可行下一步，没有真实后续安排则明确本次停止。

## 实施与真实验收分开记账

每票状态依次记录 draft → ready-for-agent → in-progress → implemented-awaiting-acceptance → done；阻塞时记录 blocker 和事实，不改成 done。draft 是发布前审阅状态，不是额外 triage 角色；发布后才使用本地 tracker 的 ready-for-agent。

- 先用公共边界做一个相关红灯，再实现并转绿；逐个业务行为推进，避免先写整套实现再补镜像测试。
- 完成对应行为测试、必要类型/构建、变更相关 UI 编译/实操和必要窄审；记录实际结果，不固定沿用旧测试数。
- 每票自行完成 M/U 等要求，不把已可执行验收全推给票10或用户；真实发布由票10统一完成，票前的 staging 证据与最终生产证据分别记录。
- 票07的真实模型配合阻断实际写入/受控回执只证明恢复和解释；没有具体授权时不执行客户设备控制，也不将物理结果写成已验。此边界不阻塞本规格收口。
- 完成票10后仍须逐项核对其余票的独立验收，才可宣布整组业务闭环完成。一次报告成功不替代草案管理等票的验收；发布健康、编译、追踪存在也不替代业务结果。

## 持续运行的最终口径

真实只读周期报表至少经历两个合法未来发生，客户端关闭期间正常到期、每个发生最多一份权威报告与一条对应站内通知，重开后原报告追问成功。记录每次计划点、实际开始/结束、交付/通知时间与下一未来点，核对没有补跑历史发生。只能声明实际覆盖的持续时长和场景；不能声称已证明全年稳定或已解决旧长停根因。
