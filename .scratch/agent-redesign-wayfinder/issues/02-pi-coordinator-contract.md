# 02 — Pi 协调层与确定性业务接口边界

Status: decided
Wayfinder: grilling
Blocked by: 01

## Question

在首条复杂业务中，Pi 负责哪些理解、澄清和解释；服务器负责哪些范围解析、能力核验、计划展开、确认和结果事实；用户可观察的终态如何限制为事实答复、必要澄清、待确认草案、任务收据或明确失败。

## Boundary

不讨论替换 Pi，不把提示词、工具调用次数或内部循环当作业务契约。

## Resolution — 2026-10-19

Pi 固定为业务协调层，但不再把当前 `find → inspect → propose → recover` 的开放式工具循环当作目标结构。

### Pi receives

- 当前用户消息；
- 当前 Agent 来源和授权上下文；
- 仍有效的结构化引用，例如现有 Task、草案或用户已选择的范围；
- 当前时间和必要的业务语境。

对话历史只用于理解语言，不能作为设备范围、授权、计划或执行结果的权威来源。

### Pi may produce

首条 Company 闭环只允许形成以下业务请求之一：

- 需要澄清的业务请求；
- 已整理的批量操作请求，包含范围表达、排除表达、阶段、动作模板和时间；
- 用户可见的计划解释；
- 任务或执行收据的事实解释。

Pi 可以表达用户说的“全部办公区”“排除会议室”等语义，但不能自行把这些词变成设备成员。

### Server must decide

服务器负责授权核验、范围和排除解析、完整性判断、能力核验、成员展开、状态预检、计划快照、确认版本、执行、回读和结果分类。

服务器返回的计划事实必须包括覆盖边界、包含/排除成员数量、阶段、已满足、不可读和仍需下发项。Pi 只能解释这些事实，不能重写数量或成员。

### User-visible terminal states

每轮只允许收口为：事实答复、必要澄清、待确认计划、任务/执行收据或带原因的失败。服务器校验错误可以交还 Pi 解释，但不能触发无边界的重复检索。`run.completed` 本身不代表业务成功。

### Recovery boundary

模型只在用户补充信息或服务器返回可修正的结构化缺口后重新整理请求。服务器不能用“调用次数”判断业务是否解决，也不能允许模型通过换地点词逐步拼接用户未确认的范围。

首条闭环优先复用现有 TaskProposal、Task、Phase、执行器和报告存储；当前 Pi runner 的工具编排需要按这个契约重组，但不预先抽象成通用 Agent 平台。
