- Runtime 共同基线为 `4ec44dc`。优先将报告 `c04ab5d`（S1/S2）和 MP `8de0a72` 按主题适配到主线；它们不以阶段目标候选上线为前置。保持自然语言调查与附件产出分工。
- 阶段目标 `af06d94` 不整体放行：改时保绑定、数量限制、兼容控制准备/核验标准、旧入口退出及本次失效行为修正完成后才进入整合。具体改动限于对应业务闭环，不先重构整个 Pi runner。
- 两线都改 Pi/app，后续在共同基线逐块整合；保留报告生成/引用/附件、控制 opt-in、只读 `read.agent.spec`、各自结果口径。开关只作候选隔离和回退，不变成永久双实现；兼容等价通过后再退出旧模型入口。
- 设备位置 WIP 按其原主题验证和提交后精确接入，不整树覆盖；G1–G4 位置重构不作为当前先决条件。历史任务/已存附件只读兼容，不猜改旧名称/结果、不自动升级已确认控制快照。

### 首条完整验证：Company 能耗调查到即时报告

选择低副作用、已有统计和 S1/S2 候选的链路，先检验完整委托，避免把“夜间收口”重新当终局：

> “比较26楼运营部和运营接待室上周与前一周的用电，找出增加主要来自哪些表，再按需要核对原采样，整理一份含环比、同比的报告给我。”

期望按目录唯一确定范围；有真实歧义时一次澄清并保留已确定时间。使用同一表集与明确上海日历窗口作比较，沿实际贡献选择必要证据，形成附件并可预览、导出、引用追问。没有增长、缺少同比或采样不足时交付真实可得部分和原因，不换旧时期、不造因果、不建定时任务、零设备控制。若候选尚不支持保存本次多区域/调查事实，先在该闭环中补最小保存衔接，不能退化为只跑固定模板然后宣称调查完成。

先验证一次正常可比和一个“用户要求同比但基期缺数”的关键分支；冻结已有漏项/错期反例作回归，不预设工具顺序、调用次数或成功率。自然语言声明正确性和服务器声明执行完整性分别核对。

### 之后的业务顺序

1. 定时日报：确认立即可见首次/下次安排，到点按本次期间取得同一类事实，附件经原收件箱返回报告；再补每周和自然月，调度与统计期间分开。
2. Company 跨区域分阶段控制及管理：独立范围/排除 → 确认 → 保快照改时 → 执行/核验 → 追问/停止。覆盖原夜间收口与不同阶段范围，修正已冻结反例和失效政策。是否真控保持具体授权，不由本票批准。
3. 告警：每日分类/设备汇总先作为独立只读闭环，再复用记录、当前位置和摄像头候选联查；日报不依赖视频理解，不扩消防处置。
4. 空调：先有限只读巡检，再按已定安全默认做有界调温/停止；后者单独具体确认。不是先铺通用条件规则平台。

每次只实现一个闭环；其它业务保留在原票，不因顺序后置记为取消。报告线既有独立授权不因本图暂停；本图也不直接驱动合并/部署。

### 最少验证与回退

- 实现时用现有公开 HTTP/消息/确认/报告与可控扫描接口，只补新行为和已知反例；稳定切片结束做一次相关集成检查。用户已要求减少频繁双审和无意义全量，不逐字段/文档修改重跑套件。
- 离线行为、真实模型、真实网关只读、微信/Excel打开、实际部署与物理效果分别留证。先证明前一层再做后续，历史日志只引用，不重复刷数量。
- 合流前保存原分支/提交回退点，隔离临时数据库；不迁移运行服务和真实任务作实验。前端/Runtime 共用行为接通后才评估服务发布；关闭候选开关不能改写已保存报告和已登记任务。
- 一次完成针对交付切片的必要审查；发现真实偏离才追加检查。UI/模型/网关验证按授权范围执行，真实控制和生产部署仍需用户针对具体结果批准。
