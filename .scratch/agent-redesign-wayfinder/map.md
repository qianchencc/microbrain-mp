# 物联 Agent 重设计 Wayfinder

## Destination

形成一份以 Pi 为固定运行框架、以真实业务结果为中心的物联 Agent 规格：明确 Company 首条复杂运营闭环、Pi 的最小协调职责、大范围操作的效率与结果语义，以及后续 Office 泛化边界。地图完成后进入 `to-spec`，不直接实现整套 Agent。

## Notes

- 这是决策地图，不是功能清单，也不是实现票据。
- 领域上下文以 `CONTEXT.md` 和 Runtime 的 [重设计审视记录](../../iot-agent-runtime/plan/2026-10-19-agent-reliability-reset.md) 为准。
- Pi 固定，不讨论更换 Harness。
- 复杂度必须来自真实业务的范围、设备类型、阶段、排除、状态差异和结果核验；不提前建设通用工作流、多智能体或新的平台层。
- 已有授权、确认、执行、回读、Task/Phase 和报告底座只是候选复用点，是否保留由决策票验证。
- 用户已授权代理自行收口正常业务细节；只有会改变产品边界、风险等级、授权语义或不可逆数据模型的决定才需要再次汇报。

## Decisions so far

- 已确认 Agent 按观察、即时操作、任务委托和调查四类业务结果重新审视；对话只作为协调面。
- 已确认首条业务应是 Company 的大范围复杂场景，而不是简单单设备操作。
- 已确认候选场景为跨区域夜间办公收口：多楼层、多区域、照明与空调、多阶段、排除项、状态预检、统一确认、执行回读和任务报告。
- 已确认大范围成员由服务器统一展开，Pi 不逐台枚举设备。
- 已确认预检、提案、确认、执行和回读引用同一计划快照。
- 已确认首期不新建长期通用 `OperationPlan`，优先复用现有 TaskProposal、Task 和 Phase。
- 已确认控制执行保持控制器分组、同控制器串行、不同控制器保守并发；当前三路并发是安全基线。
- [Company 跨区域夜间办公收口业务契约](issues/01-company-night-closure-contract.md)：冻结为一次性两阶段照明/空调收口，真实排除必须可解析，阶段独立继续但整体结果按证据收口。

## Not yet specified

- Pi 如何把自然语言映射到一个批量业务请求，以及哪些信息必须由服务器确定性补齐。
- 批量计划的状态预检、执行、回读、部分失败和未知结果如何形成一份用户可理解的报告。
- 复杂闭环的 UI/UX 是否需要原型验证，尤其是大范围确认和分阶段结果展示。
- Office 如何在后续复用这套能力，同时保持个人设备范围和 Company 来源隔离。

地图推进时，以上问题由代理结合现有代码、真实证据和已确认边界自主形成决议；不把每个字段和异常都升级为用户问题。

## Out of scope

- 在地图完成前编写 Runtime 或小程序实现。
- 更换 Pi 或引入新的 Agent Harness。
- 通用工作流平台、多智能体协作、永久规则引擎和泛化规划器。
- 将门禁、消防、视频理解、条件触发和周期规则加入首条闭环。
