# Agent 最终答复恢复交接

用户要求：开发者工具中的普通问题应得到有效答复，不能因为答复协议不匹配而整轮失败。本轮按 ask-matt → diagnosing-bugs → 公开 HTTP 回归 → Standards/Spec 审查推进。

## 定位证据

- 截图问题「为何工作日日均和峰值日为空」对应 Runtime 2026-10-15 13:05 的真实失败轮，约18秒后失败。
- 前端源码和微信编译包均指向 `https://mp-agent.qianc.ltd/api`；请求实际到达真实网关 Runtime。
- 同类只读 HTTP 请求复现 `run.started → run.failed`，后台错误为「模型未返回可展示的消息」。
- SDK 实际请求包含 `tool_choice:required` 及答复工具，上游却返回普通 text 并以 `stop` 正常结束。该普通文本按现行最终答复协议不能直接发布。
- 单纯再提示一次并只提供答复工具，仍观察到上游忽略 `required`。因此补交必须明确指定具名 `reply_to_user`。

## 实现

Runtime 提交：`45431c0`，`fix: recover final replies when upstream ignores required tool calls`。

- 业务规划仍按原工具集运行；仅有答复工具的请求明确指定 `reply_to_user`，共用出口也覆盖执行总结与报告解读。
- 正常 `stop`、未提交最终答复且没有可用的确定性业务回执时，在剩余模型调用预算内最多补交一次。
- 补交仅开放答复工具，不重跑设备查询，不创建或执行控制、任务、计划；不公开原始 text/thinking。
- 已保存报告追问同样允许补交；新生成报告和即时草案继续使用原有确定性回执。
- 取消、超时、上游错误和生成截断不进入该补交；两次均未提交有效答复时保持明确失败，不伪造业务成功。
