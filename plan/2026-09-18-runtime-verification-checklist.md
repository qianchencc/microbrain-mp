# Runtime 核对清单：身份契约（票 01）与设备扩展支持包（票 03）

**目的**：为 `.scratch/agent-expansion-wayfinder` 的票 01（真实 MP 用户身份与 Runtime 隔离）和票 03（客户新增设备接入支持包）区分三类事实——代码/文档已证明的、现有凭据可探测验证的、只能由客户补齐的。产出将直接裁剪为发给甲方的最小资料请求，并回填两张决策票。

**来源**：项目方 — **接收**：后端智能体（iot-agent-runtime 核对与探索） — **结果用途**：核对结论由项目方整理成甲方版本问卷；本文不直接发客户。

## 背景

当前已有照明、中央空调、门禁三类设备的 E5 控制闭环（授权设备发现 → 能力核验 → 草案 → 显式确认 → 执行 → 回读 → 审计）。两张决策票的状态：

- **票 01**：技术边界已明确（生产合入客户小程序复用登录态；Runtime 须区分 `principalId` / `workspaceId` / Provider credential）。现有 owner 键为 `sha256(tenantCode + Authorization)`，Token 刷新会漂移，不能承载长期归属。客户身份契约未补齐。
- **票 03**：E0–E5 证据分级与客户必填支持包已成形（`docs/research/2026-09-18-customer-device-expansion-support-package.md`）。视频 E3、能源 E2、消防/燃气/环境等 E0–E2，客户材料未提供。

两份源文档：`docs/research/2026-09-18-real-mp-identity-boundary.md`、`docs/research/2026-09-18-customer-device-expansion-support-package.md`。

## 如何作答

对每一项给出三种结论之一，不确定就标"不确定"并写明缺口，不要跳过：

- **A｜代码已证**：仓库中可验证。附 `文件:行号` 或测试名作为证据指针。
- **B｜可探测**：用现有开发凭据/只读接口可验证。写明探测方法与实际结果。
- **C｜需客户**：代码和探测都无法回答。改写成一行最小客户索取项（谁提供、提供什么）。

**边界**：只读核对。不修改业务代码、不执行任何写/控制/场景切换接口（包括 GET 形式）、不把 Provider 目录当用户范围、探测仅用现有开发凭据。

## 一、身份与隔离核对（票 01）

### 1. owner 键的真实生成与使用面

`sha256(tenantCode + Authorization)` 在哪些代码点生成、键控了哪些对象（会话、草案、候选集、其他）？是否有进程外持久化？

_为何重要：决定"Token 刷新导致归属漂移"的影响半径，以及未来插入 `principalId` 的接缝位置。_

>

### 2. 是否存在服务端 `principalId` 解析边界

Runtime 目前有没有任何"稳定用户主体"概念，或一个可以挂接客户 SSO introspection / 网关签发的单一解析点？身份解析分散在多少处？

>

### 3. 凭据泄漏面

`Authorization`/Provider Token 是否可能进入模型上下文、会话正文、审计记录或普通日志？逐层核对请求入口 → agent 上下文组装 → 持久化 → 日志。

_为何重要：这是票 01 冻结不变量之一；若有泄漏点需先于身份模型落地修复。_

>

### 4. `tenantCode` 语义与切换行为

`tenantCode`/`Tenantcode` 在 Runtime 内的实际用途（隔离域？上游参数？两者？）。同一凭据带不同 tenantCode 会发生什么——会话隔离、串用、还是报错？

>

### 5. Token 刷新后的归属漂移实测

在开发环境模拟 Authorization 变化（同一 tenantCode）：原会话、待确认草案、候选集是否全部不可恢复？是否存在任何按更弱键回落的路径？

>

### 6. 执行前的设备范围重新核验

确认/执行路径上，设备范围是重新拉取用户范围接口、使用草案时刻的快照、还是使用会话缓存？撤权场景下旧草案在确认时会被拒绝、缩减还是照原样执行？

_为何重要：不变量 4（撤权后旧草案不能继续执行）是验收案例 6 的前提。_

>

### 7. 会话清除语义

"清除会话"当前删除什么、保留什么？是否会连带删除不应删除的长期对象（草案之外的任何持久物）？

>

### 8. 开发身份隔离

`AGENT_DEV_IDENTITY` / `Bearer local-development` 路径的启用条件：能否被正式版前端、非开发环境配置或后台任务意外继承？

>

### 9. 审计 actor 记录

现有审计记录了什么 actor 信息？是否记录了"哪个凭据/主体、哪个工作空间、哪个设备范围快照"，还是只记录会话 ID？

>

## 二、现有 E5 闭环与适配器边界（票 03 基线）

### 10. Authorized Device Scope 的实际来源

用户范围接口的方法、路径、过滤参数、分页处理和缓存策略分别是什么？范围数据在请求生命周期内被读取几次？

>

### 11. Provider 目录越界检查

是否存在任何代码路径用 `api-iot-center`/`api-perception`/`api-energy` 底层目录回填或扩大用户可见设备范围？（预期答案是没有，但需要证据。）

>

### 12. 草案→确认→执行→回读链路的设备类型通用性

这条链路中哪些部分是设备类型无关的（草案模型、确认门、审计），哪些是按 `DeviceKind` 硬编码的？新增设备类型复用该链路实际需要改动哪几层？

_为何重要：决定票 03 中"提供同等契约即可复用适配器边界"这句话的真实成本。_

>

### 13. "已受理 vs 物理完成"的区分点

照明/空调/门禁三类各自如何把平台受理回执与物理完成状态分开收口？回读窗口、超时和未知结果的语义各是什么？

>

## 三、候选设备只读探测（E1–E3 证据整理）

对每类输出：当前证据等级维持/可上调的判断 + 距下一级还缺什么。**只探测只读接口。**

### 14. 视频（当前 E3）

用户范围证据具体是什么？底层目录里有哪些字段可用于稳定身份映射？是否存在流地址、回放、鉴权端点的线索（只编目，不请求播放）？

>

### 15. 电表/能源（当前 E2）

已捕获的目录与样本读数里，计量点层级（园区/楼栋/分表）是否可辨认？`readTime` 滞后问题用现有凭据再测一次的新鲜度如何？历史/区间接口形态是否存在？

>

### 16. 感知/消防（当前 E1/E2）

`api-perception` 中告警、处置、事件相关路径的目录清单；"关键遥测字段为空"的接口重测一次是否仍为空？事件字段（ID、等级、时间、恢复语义）有无样例可见？

>

### 17. GET 形式场景/状态切换接口编目

列出全部疑似有副作用的 GET 接口（路径、参数、疑似动作）。**只编目，不调用。**

>

### 18. 其余候选快速过筛

水/气计量、环境/温湿度、人数/密度、道闸：现有凭据下能否各拿到一条真实样本响应？拿不到就维持原等级并写明卡在哪一步。

>

## 四、汇总输出要求

完成一至三部分后，输出两块汇总（这是本清单的最终交付物）：

1. **需客户补齐的最小清单**：所有 C 类项按支持包表格字段组织——设备类型/业务闭环/用户范围接口/稳定身份/状态读数/事件告警/控制/权限风险/测试条件/验收证据/客户负责人。每项注明对应哪张票、哪个验收案例。
2. **决策票回填建议**：票 01、票 03 各自哪些"待客户确认"可以降级为"已核对事实"，哪些需要新增。只输出建议文本，不修改 `.scratch/` 下的票据。
