### 已认可方向与仍待冻结的实现边界

复用任务/计划、调度、确认、执行结果和卡片能力，让每个 Agent 从各自上游取得设备范围和可执行能力。任务、计划、引用、查询及后台执行必须固定原 Agent 的业务来源；同一用户身份不表示两个来源可直接合并。客户负责产生权限，我方负责按相应来源调用并尊重返回范围；不自建组织权限矩阵。

两端自动化共用业务规则不等于每类设备都有控制动作：可控设备执行已确认指令，计量/感知等设备参与读取、简报或证据，新增动作仍须有可核验的接口。已有周期模型和前台简化方向可以保留，不先建设双份任务系统或通用工作流平台。

告警通知和任务结束通知分开记录责任：甲方明确承担前者；用户认可后者也经甲方渠道发送的推荐，但仍待甲方确认具体服务契约。我方任务结束事件、结果记录与深链仍是待办，不能因甲方负责渠道就删除这些工作。

### 按 ask-matt 推进及每步退出条件

1. **前置配置**：`docs/agents/issue-tracker.md`、triage labels 和单 CONTEXT/ADR 布局均存在；使用现有本地 tracker，不重新运行 setup 或换 tracker。
2. **当前 `grill-with-docs`**：保留已接受决定，只问目前有条件回答的边界。将用户回答分别记录为 accepted/deferred，不把推荐或等待时长当答案。后续治理具体权限的问题等 Q3 顺序确定后再进入下一轮。
3. **原型 detour**：新的输入框/跨页状态需要可操作答案；先 handoff 到现有专用原型目录，修改原周期原型、保留原来源，再 handoff 回主线。验证新引用/委托/确认流程与历史不变，接受用户反馈；不以旧编辑表单走查代替新体验。
4. **`to-spec`**：在共享理解与必要原型结论齐备后，合成完整用户故事、已定规则、排除项与验收。先与用户核对测试公共入口，再发布本地 spec；不在此阶段继续假设新产品决定。
5. **`to-tickets`**：先展示按完整业务闭环划分的编号草案、交付效果与真实 Blocked by，询问粒度/阻塞边/合并拆分；用户认可后才在 `.scratch/<feature>/issues/` 一票一文件发布 `ready-for-agent`。本表的 T/G/X 是盘点分组，不冒充这一步。
6. **`implement → tdd`**：只领阻塞已解除的票；在此前认可的公共入口逐个 red→green，不横向“先全部测试再全部代码”。单票切片贯穿必要数据/API/UI；适当定向测试/typecheck，结束全量检查。
7. **`code-review → commit`**：固定基线和 originating spec，标准/规格双轴并行审查，修复后检查提交范围并按业务闭环提交。浏览器、小程序和真实验收按各自证据收口；不得把原型或自动测试等同用户真实设备验收。

测试入口目前只是**待 `to-spec` 阶段核对的建议**：优先复用 Runtime `buildApp + HTTP inject` 公开接口、受控时钟的既有 scanner 公共入口和生产协议网关夹具；前端以任务引用→提案确认→查询结果的真实操作链路验收；缓存用真实模型出口+禁止 IoT 的夹具探针。没有为本轮盘点新增测试，也没有提前认定新的测试入口已获认可。

同一目录/会话当前继续，不重复制造 handoff。只有转去原型目录、换执行上下文或跨仓库交接才用 handoff；grilling→spec→tickets 尽量保留同一完整上下文，发布单票后实现才使用新的上下文。当前工作量明显跨多轮，不走“凭口头概要直接 implement”的分支。
