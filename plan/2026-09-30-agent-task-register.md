## 已确认与待确认

### 已确认

- T01 的探索方向：周期计划长期存在，未来发生按规则推导，到期落成标准 Task；保留历史执行事实。一次性 Task 保留。
- T01 的视觉要求：复用当前拟物材质、B6 几何与抽屉交互，需通过原型验证新增流程。
- T01 的区间与检查点：用户明确区间起止确定，检查点自由，不接受阶段数量上限。首末检查点不定义区间；现有代码的最多两阶段是待调整的实现约束。
- 上轮五项建议获用户“基本认可”，按设计方向接受：确认时安排检查点、用户可编辑未来检查点；区间结束才汇总及通知；每天/工作日/指定周几、照明/空调、可跨日；创建者编辑与启用，完整设备授权成员可停用并记操作者；通知只发给创建者。核心模型见 ADR 0005，边界尚未全部冻结。
- Q7–Q11 经具体场景重新解释后获用户“基本认可”：完整编辑未来检查点/目标；不跨区间补做旧检查点，终点及进行中调用正常收口；停用只影响未来，取消实际 Task 推送、跳过虚拟发生不推送；订阅不足不阻断 Task；按开始日期归属跨日、截止日不截断已开始区间、错过今日开始则顺延。具体调度迟延阈值在规格中定义，UI 留待原型验证。
- 凭据前提：用户纠正“Token 频繁过期”为文档误记录，本轮不再以跨 Token 实验、刷新接口或失效停用阈值阻断周期任务。账户归属与访问凭据仍是不同概念。
- T02 的范围：自动化结束通知；2026-09-30 用户明确回复“这个通知可以都发”，包括成功结束和异常结束。
- T03 的前提：用户已通过成熟框架验证最上游具备缓存能力；继续检查我方请求构造与适配链路。

## 每项如何探索

### T01 / T01-E：领域场景，再做可操作原型

1. `grill-with-docs` 用三条真实场景收口：工作日 19:00 关灯；14:00–16:00 区间内安排多个检查点，首末检查点不必落在端点；把本次 19:00 改为 19:30、随后再修改整个周期。逐例核对检查点安排/调整、区间结束与结果汇总、跨日、暂停、执行中编辑、授权变化、历史保留和版本冲突。
2. 决定落入 `CONTEXT.md` 与新增周期 ADR；当前 ADR 0004 的一次性执行边界继续作为现行基线，确认后再说明其扩展关系。
3. `prototype` 验证周期列表、创建提案、仅本次/整个周期编辑、停用/恢复，以及未来虚拟卡被真实 Task 替换。使用专用原型目录；现有 B6 作为对照。样例不写 Runtime、不控制设备。
4. 原型通过后用 `to-spec` 固定用户故事与公开行为验收，再用 `to-tickets` 提出完整业务切片及依赖，用户确认拆分后发布一票一文件。

探索完成标准：用户明确选择一期规则、编辑权限与作用域；原型能完整演示上述路径，历史记录保持不变，未来卡无重复；已明确公开 HTTP、可控时间的扫描入口和客户端操作流如何共同验收。当前尚未达成。

### 本轮区间场景与实现差距

源码核对完成，尚未以公共接口重放这些新场景；以下区分实现事实与待确认的领域行为：

| 场景 | 已确认或待决定 | 现有实现差距 |
|---|---|---|
| 14:00–16:00，检查点为 14:10、14:45、15:30 | 区间固定、三个检查点合法已确认 | 当前校验拒绝第三点；即使只移除数量校验，也会显示成 14:10–15:30 |
| 最后检查点 15:00 已完成，区间仍到 16:00 | Q6 方向已接受：不提前终结，区间结束再汇总与通知 | 当前全部阶段终态即结束 Task、删除托管凭据；没有独立区间结束处理 |
| 15:58 检查点因停机在 16:03 才扫描到 | Q8 已认可不补做旧点；终点正常调度与进行中调用收口另行处理 | 当前 10 分钟补执行窗口不检查区间结束 |

任务提案和存储仅有阶段列表，没有独立 `startsAt/endsAt`；区域查询、日历、轨道和任务详情据首末阶段解释区间。详情还把非首阶段统一命名为“结束”。取消依赖存在未执行阶段，因此“检查点已完成、区间未结束”的管理入口也需要随 Q6 定义。具体证据见下方源码入口。

当前决策树：Q1–Q3/Q5–Q11 的方向均已认可，Q4 已撤回。下一步为原型走查编辑、区间、启停、报告和通知深链；删除全部检查点、区间调整等具体操作分歧由可运行体验回答，不再重复业务方向问答。

### T02：先核实渠道，再验证通知全流程

1. 形成终态矩阵：成功、部分完成、失败、中断、错过均列入；取消与跳过单列待决定。保留现有执行口径：流程结束/指令受理不等于物理状态已达到。
2. 从现有订阅封装到 Runtime、发送函数逐段核对：可信接收人绑定、模板字段、授权结果、部署配置、发送认证、去重、投递结果和任务详情深链。用官方资料核对周期通知可用的订阅条件。
3. 给出成功、异常、授权不足、投递失败四种用户体验样例；原型只在体验有实际分歧时使用。前端 API 调用成功不是送达证明。
4. 收口为 `to-spec` 与可独立演示的通知票。一次性自动化的结束通知可先于周期任务接入；周期通知的持续授权问题另有明确依赖。

探索完成标准：每类终态的接收人、发送时机、授权不足行为明确；可说明一项真实 Task 怎样产生一次可追踪通知并返回详情；客户缺项形成精确字段/配置清单。产品方向已认可，返回任务与降级体验待原型；可信接收人和真实发送链路仍需接线，不以纸面认可代替生产验收。

### T03：可重复对照诊断

1. 保留最小红绿反馈：捕获真实模型出口的请求摘要与原始缓存用量；覆盖同一会话连续多轮、一次工具调用后的收尾、会话恢复。冷启动与主动压缩分别标注。
2. 在相同模型、网关、协议和输入条件下与成熟框架对照。每次只改变一个变量：上下文排列、工具定义、收尾时系统提示词变化、思考内容回传、会话/缓存标识。记录预测与结果，再决定修改。
3. 修复后重跑原始业务复现、必要回归与完整终态检查。模型探针不执行物联网工具，功能回归使用网关夹具。

探索完成标准：能解释暖请求中的零命中，并证明原始复现已改善；缓存统计与上游用量一致，工具与回复仍正常收尾。`1c9ca88` 只关闭一个前缀缺陷，不代表此项完成。缺少成熟框架的具体配置时，把未完成的同条件对照明确记录，不能假定已对齐。
