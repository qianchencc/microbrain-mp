# 两项任务与执行结果闭环（2026-09-28）

## 事实

- 用户的 15:00–16:00 会议与 17:30 下班安排是两项独立任务，不能合并为一项三阶段任务。原实现一次 Agent 轮次只能保存一张任务提案。
- Langfuse trace `37a0323fb7cfe80531233b5ef45d56c6` 对应原请求：两次设备检索分别约 15 ms、2 ms；第二次模型回合持续 89.159 秒后因请求被停止而中止。该次卡住发生在模型回合，不是设备检索。
- 14:48 真实任务 `0e06d6f1-f31b-4510-9406-4615e2cef55b` 的两个阶段各保存了五台设备结果；四盏灯的请求没有因空调请求而漏记。平台 `ACCEPTED` 只能证明指令受理，不能还原当时每盏灯的物理状态。

## 当前实现

- 一次请求最多形成两项独立任务提案，每项最多两个阶段；两张卡分别确认或放弃，会话恢复保留各自状态。执行前仍重核权限，提案本身不控制设备。
- 设备执行结果面向用户只显示“未执行 / 已执行 / 不必执行 / 明确报错”。“已执行”指本次指令获平台受理，不声称设备物理状态已达到目标。原始回执和回读证据仍保存在任务记录中。
- 旧的纯 `ACCEPTED/unconfirmed` 阶段在 Runtime 启动时幂等归为已完成的执行流程；含明确拒绝、超时或未知结果的任务仍保留错误。区域异常提示与日历不再把纯受理当异常。
- 设备现态与执行结果独立；打开面板触发的自动刷新有冷却，手动刷新不受限制，执行后的延迟刷新仍会运行。区域目录短期复用，工作台重显保留已有任务，设备抽屉关闭时不预取目录。
- 任务详情不再显示无法清理的汇总提示条；错误仍留在任务状态与对应设备行，区域异常提示按“已查看”水位清除，不改写历史结果。
