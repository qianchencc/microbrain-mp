# Company Agent 客户改进需求、可靠性缺口与推进路线

日期：2026-10-20。

状态：需求整理与拟议交付切片，尚非新实现规格或已批准票据。本文记录用户明确要求、已观察事实、设计建议和待决定事项；不授权联网、发布、外部通知或真实设备控制。现有成熟业务继续保留，不因本记录声称全部自动化已经完成。

## 1. 本轮目标与已确认边界

客户新增三组需求：

1. 每日、每周、每月定时推送能耗日报、周报、月报，包含总用电、同比环比、高能耗区域、异常能耗提醒，并支持导出表格；客户另反馈计划未及时出现、报表形式需要改进。
2. 每日定时汇总公司烟感、燃气、水浸设备当日告警：哪些设备有记录、多少条，首期只要求统计，不扩成消防处置平台。
3. 定时检查公司空调，温度低于 26℃ 时自动调整到 26℃；用户倾向用定时任务与较密检查点表达，但担心公司范围持续控制风险，希望演示有效且风险有限。

用户随后澄清的报告要求：

- 对话中能够产出报告；对话和任务检查点均采用附件加点击预览，现有检查点附件形式可以保留。
- 不把产出做成沉重流程，不要求先建一个定时任务才能取得即时报告。
- 保持唯一任务收件箱；不新增报告收件箱、报告工作台或报告顶级导航，不因本轮重做通知、任务详情或 Sheet 层级。
- 关注点是业务可靠性，而非附件能否保存：不能漏项、错期后仍宣称完整交付。
- 上轮关于改成成果优先的任务详情、重排通知和替代阶段附件行的建议不是已批准范围，本轮不沿用。

## 2. 需求清单

| 编号 | 用户可观察的交付 | 必须保留的边界 |
| --- | --- | --- |
| R1 | 对话中要求整理报告后，得到可预览的附件；可追问、查看依据 | 普通短问答无需强制生成正式报告；不得为即时只读报告增加任务创建或额外审批 |
| R2 | 同一报告能力可被检查点调用，沿现有任务结果查看附件 | 保留原 Task/Phase、返回和已读机制；不另建报告入口体系 |
| R3 | 日报、周报、月报按确认规则到点产出，显示首次和下次执行时间 | 调度周期与统计期间分离；月报不能用每 30 天替代自然月 |
| R4 | 按本次委托取得总用电、同比、环比、重点位置及异常核查内容 | 本次未要求的分析不强加；要求了但缺数须说明，未执行不能冒充已完成 |
| R5 | 导出可用于办公处理的表格 | 预览与导出来自同一已存成果；已有 PDF 不等于完成表格导出 |
| R6 | 确认计划后及时看到规则、首次发生与日历安排 | 未确认提案不是已安排；未来投影不必提前落真实 Task；读取失败不显示虚假的零项 |
| R7 | 每日获得烟感、燃气、水浸分类记录数、涉及设备数和设备明细 | 统计窗口清晰，分页和去重由服务器负责；失败或范围不全不报零、不报全量 |
| R8 | 在确认的设备与时段内定时检查并按条件调整空调 | 先澄清设定温度与室温；确认前零控制，不能以站点环境读数驱动全部房间 |
| R9 | 用户能够了解任务结果、部分交付和失败，并停止未来自动执行 | 停用计划与停止已落账本次任务分开；已发出指令不能假称可撤回 |
| R10 | 定时成果按约定渠道和对象送达 | 站内任务通知与微信等外部投递分别验收；不得用站内消息代替客户要求的外部推送 |

## 3. 当前事实与缺口

核对基线：MP `6ed416e`，Runtime 主线 `4ec44dc`；两仓有并行未提交改动。以下是源码与已有记录的结论，不等于当前活动服务版本验收。

- 已有：Company 计量统计与时间/区域对比、保存事实、受限能耗检查点、任务/周期/报告持久化、任务收件箱、PDF 和报告引用。已有成果值得复用，不以本轮推倒算法、调度和 UI。
- 已有确认后刷新事件与周期未来投影源码；客户的计划延迟反馈仍须核对活动 Runtime、微信构建、确认返回及读取链路，根因尚未定位。
- 持久化报告目前绑定实际 Task/Phase，块类型为文字与电表报告；普通对话共享同一附件产出能力仍需接通。
- 周期规则目前仅 daily、weekdays、weekly，未支持按月；公开报告下载目前为 PDF，未见 XLSX/CSV 导出链路。
- 能耗 Agent 检查点只接收文本 objective 和 result/report 输出选择；当前完成判断主要针对已查询事实的数据质量与提交状态，而非本次委托的全部要求。
- 安全读取已有台账与分页基础，但旧定时读取按近 N 天滚动窗口，不等于当日分类统计；当前能耗专用报告产物也不能直接承载所有安全成果。
- 空调 temperature 来自 tT 设定温度，不是室温。普通“设为 26℃”按不等于目标决定下发，会把 27℃ 调低，不能直接作为“低于 26℃ 才上调”的循环任务。
- 单个环境站点没有经过确认的全房间控制映射；Company/Office 来源不可混用。摄像头、消防设备不因只读统计需求获得控制授权。
- 当前能耗口径沿运行时现行约定：示数增量单位为度、已确认末端表合计。缺测、回退、边界不齐和模拟补数继续明确，不恢复已经过时的单位未确认结论。

## 4. 已复现的可靠性反例

2026-10-20 在 Runtime 主线进行隔离诊断：经公开 HTTP 提案、确认、可控时钟扫描、报告读取进入；模拟模型与进程内生产协议夹具，禁止外部网络，临时数据库，无真实控制。

指令明确要求昨日总量、环比、同比、高耗能区域和异常提醒。为检查服务器完成判定，模拟模型故意只查询一次 statistics 后提交报告：

| 场景 | 保存事实 | 实际结果 |
| --- | --- | --- |
| 漏同环比 | 仅本期 statistics，comparison 事实为 0 | Task、Phase、Report 均 completed |
| 期间错误 | 要求上海 2026-10-11 00:00 至 10-12 00:00，却保存 10-10 00:00 至 10-11 00:00 的请求 | 标题仍称昨日报告，Task、Phase、Report 均 completed |

两例控制调用均为 0。证据：[冻结结果 JSON](assets/2026-10-20-company-report-contract-results.json)。这些合成样本只证明服务器会接受错误完成，不证明真实模型的失败频率、所有报表都错、统计算法算错或生产现场已发生同类事故。此次不重新运行探针或派生新成功率。

当前报告回归通过预设模型脚本安排完整统计/同比/环比路径，可证明保存、权限、恢复和失败处理，不足以证明真实模型必然补齐用户要求。历史成功样例也不能代替稳定性结论。

## 5. 拟议设计方向，不是已冻结接口

### 报告可靠性

- 以确认/本次请求表达的要求为依据，服务端保留计量范围、相对期间规则、比较关系与所需内容；不是让模型每次从一段文字重新决定全部义务。
- 服务端负责成员、期间、计算、比较集合、排名、证据和完成校验；Pi 负责语言理解、必要澄清、基于证据选择调查方向及组织解读。保留现有算法，不写死任意问题的工具顺序。
- 要求项分别表达已取得、数据不足、不支持或读取失败；“未查”不能当作“查过且无数据”。内容完整与数据可比性分开判断，不为了 completed 隐藏缺口。
- 日/周/月只改变期间与调度规则，不分别建设三套 Agent。日期按本次发生和上海时区解释，不能固定为建计划当天或为拿到数字悄悄换到旧日期。
- “高耗能排名”“能耗异常线索”“采样质量问题”分别表达；缺少异常规则和有效基期时不推断故障、浪费或实际节能。具体异常判定仍待设计。
- 一次性对话与定时检查点复用事实准备、验证和成果保存；报告归属的最小扩展、工具形状与旧入口取舍需在实施规格中确定，不预建通用产物平台。
- 附件中可按业务选择和组织已支持的指标、趋势、排名、明细及解读；证据保留不等于把所有工具结果全铺正文；不接受模型下发任意代码/组件。
- 建议新增 XLSX 阅读/明细表格导出，保留现有 PDF；字段、缺失值、期间、单位和来源标识一致。查看、引用、导出继续复核当前权限，且不重跑统计。

### 告警日报

- 以计划时刻确定明确上海时间窗口，服务器分页、按稳定记录身份去重、分类并计数；分别给记录条数与涉及设备数。
- 当天结束前发送只能称截至某时刻；完整当天统计需在日界之后。某类失败保留其它类事实，完整性和未知类别必须明示。
- 首期仅统计及现有记录详情，不自动确认、处置、消警、关闭或联动控制，也不宣称设备已恢复。

### 空调巡检

- 建议首期定义为“开机且制冷、设定温度低于 26℃ 时，仅调整设定温度到 26℃”；这是安全候选语义，尚不等于客户已确认。
- 使用固定成员、排除范围、有效时段和有界检查点；检查间隔根据状态更新和上游承载确定，本轮不批准秒级/固定分钟数或延迟阈值。
- 条件判断由服务器执行，不在每个检查点让模型临场决定动作；不隐含开机、改模式/风速，不把未知或无法满足巡检时效要求的状态当作条件成立。
- 授权/控制绑定变化时阻止受影响控制；下发结果未知时，后续检查点不得变相自动重发；跨任务争抢、参数再次被改动时的暂停/让行规则需设计并核验，不声称能识别人类操作来源。
- 停止要覆盖已落账本次的未执行检查点及排队动作，保留在途和已执行结果；沿现有取消能力判断最小补齐，不能只切未来周期开关。
- 先只读巡检，再在用户具体授权后进行有限设备、有限时长的现场演示；不通过全公司控制来验证基本功能。

| S6 空调只读巡检 | 确认范围/时段 -> 到点检查 -> 显示命中/无需调整/不可判断 -> 结束记录；全程零控制 | 温度语义、条件与范围设计、现有控制准备基线；不依赖能耗导出/月报 |
| S7 有限条件调温与停止 | 具体授权 -> 按条件仅改温度 -> 回读/未知处理 -> 后续检查防争抢/重发 -> 停止剩余点 -> 最终结果 | S6、持续授权/冲突/停止语义决议、现场具体授权与受控发布 |

## 7. 继续前的局部设计事项

1. 推送具体渠道、收件人范围及默认触发时间；不据“推送”一词推定已经同意只做站内。
2. 日报自然日与 08:00 采样日如何命名；周/月统计的请求边界及同比基期。保留请求与实际采样边界，不因为没有 00:00 采样就擅改自然月语义。
3. 异常能耗的明确规则/证据、不足时的呈现；不自行加增长百分比阈值或把排名当异常。
4. 空调究竟指设定温度还是室温、允许的运行模式、成员与排除、持续期限、间隔、覆盖改动后的让行/暂停及停止范围。

这些是局部事项，不要求先解决所有控制风险才能开始只读报告设计。工具命名、字段及模块内部设计由开发根据证据处理，不重复索取用户已确认的 Company/Office 分层、单位或账户条件。

## 8. 验证方式与阶段边界

- 业务行为从公开对话/报告 HTTP、任务确认、可控时钟扫描进入；协议与统计沿既有稳定接口，不锁定内部工具顺序或 prompt 文案。
- 先保护已复现的独立风险：遗漏同环比和错误期间不能获得虚假完整交付。缺基期、基期零、缺测、授权变化、部分失败、重复扫描和恢复继续复用原有回归。
- 真实模型与进程内协议夹具检验意图/提案/业务结果，不预写理想工具路径；真实网关只读用于另核数据覆盖。此处是验证议程，不是已编写的评分器/数据集，不设臆造成功率或抽样次数。
- 微信编译、实际原生点击、真机、活动服务版本、真实设备回读分别验收。附件能打开和模型一句“完成”均不能代替业务判定。
- 新增必要 UI 只针对现有附件无法承载的具体内容做最小可点击原型；不重新设计外围导航。来源和任务入口继续保留现有成熟模式。
- 实施前从 Ask Matt 收口本域设计与公开验证接缝，再形成 spec，用户确认切片拆分后发布本地票据；实现按 TDD 和 Standards/Spec 双轴审查。未经批准不发布新实现票或合并/部署候选。
