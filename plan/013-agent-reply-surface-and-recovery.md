# Agent 回复容器与错误恢复方案

日期：2026-09-15

## 目标

让一次用户输入始终呈现为一条完整的 Agent 消息。处理记录、普通回答、操作草案、执行回执和错误恢复不再是互相割裂的几个区域。

本方案只重做 Agent 层，不重做已经确认的操作草案卡片、设备图片、空调编辑器和门禁配置器。

## 一、统一结构

```text
┌──────────────────────────────────────────────┐
│ 用户输入                                      │
│ 把26楼会议室的空调调到26度制冷，中风           │
└──────────────────────────────────────────────┘
                     │
┌──────────────────────────────────────────────┐
│ 物联 Agent                         已思考 8 秒 │
│                                              │
│ 处理记录 ⌄                                   │
│   ✓ 检索设备候选                              │
│     找到 2 个设备候选                         │
│   ✓ 查询设备状态                              │
│     已读取 2 台空调状态                       │
│                                              │
│ 我找到了会议室的两台空调。                    │
│ 当前均为开启、自动、24°C、中风。              │
│                                              │
│        [现有操作草案卡片]                     │
└──────────────────────────────────────────────┘
```

规则：

- 用户气泡是本轮输入的唯一来源；
- Agent 标题、头像、处理记录、回答和草案属于同一条 `ReplySurface`；
- 回答开始出现后，处理记录默认收起；
- 草案待确认时，草案保持展开；
- 执行完成后，草案转为结果态，Agent 收尾回答紧接在其后；
- 错误时保留用户输入和失败回答，恢复操作靠近用户气泡，不插入新的孤立消息。

## 二、统一状态机

```text
idle
  │ 用户发送
  ▼
starting
  │ run.started
  ▼
searching / thinking
  │ tool.started / tool.progress
  ▼
answering
  │ message.delta
  ├──────────────► awaiting_confirmation
  │                         │ 用户确认
  │                         ▼
  │                    executing
  │                         │ 回执
  │                         ▼
  └──────────────────── completed

任意运行态 ──网络/模型/工具异常──► failed
failed ──编辑──► composer(editing)
failed ──重试──► starting（新的 turn）
用户停止 ──────► stopped
```

前端不能用 `turn.error` 一个字段代表所有异常。至少需要区分：

```text
transport_error   网络断开或请求失败
model_error       模型请求失败
tool_error        工具执行失败
draft_error       草案生成或校验失败
execution_error   设备执行回执失败
stopped           用户主动停止
```

## 三、场景稿

### 场景 A：普通查询，只有一个工具调用

用户：“26楼会议室空调现在什么状态？”

```text
用户                                     
┌─────────────────────────────┐
│ 26楼会议室空调现在什么状态？ │
└─────────────────────────────┘

Agent
┌─────────────────────────────┐
│ ✦ 物联 Agent        思考中  │
│                             │
│ 处理记录                    │
│   ◌ 检索设备候选            │
│                             │
└─────────────────────────────┘

工具完成后
┌─────────────────────────────┐
│ ✦ 物联 Agent        已思考 4秒│
│                             │
│ 处理记录 ⌄                 │
│                             │
│ 26楼会议室有1台中央空调。     │
│ 当前已关闭，设定温度24°C，    │
│ 模式为自动，风速为中风。       │
└─────────────────────────────┘
```

处理记录默认收起，因为它不是用户的主要信息。

### 场景 B：第一次检索 0 个，第二次命中

用户：“把26楼办公区的空调打开。”

```text
错误的视觉：
┌─────────────────────────────┐
│ ✓ 检索设备候选               │
│   找到 0 个设备候选          │  ← 不应短暂出现
│ ✓ 检索设备候选               │
│   找到 2 个设备候选          │
└─────────────────────────────┘

正确的视觉：
┌─────────────────────────────┐
│ ◌ 检索设备                   │
│   正在调整检索范围…          │
└─────────────────────────────┘

命中后更新同一个节点：
┌─────────────────────────────┐
│ ✓ 检索设备                   │
│   找到 2 个设备候选 · 2次尝试 │
└─────────────────────────────┘
```

实现规则：

- 第一次 `count=0` 只进入 `searching` 临时态；
- `tool.progress` 只更新临时文案；
- 后续命中后更新原节点，不新增第二个节点；
- 所有尝试最终都没有命中，才显示“未找到匹配设备”。

### 场景 C：模糊请求，需要用户确认范围

用户：“把26楼的灯关了。”

```text
┌────────────────────────────────┐
│ ✦ 物联 Agent                   │
│                                │
│ 处理记录 ⌄                     │
│   ✓ 检索设备                   │
│     找到 7 个照明设备          │
│                                │
│ 26楼有7个照明设备。             │
│ 其中包括男卫生间、女卫生间、    │
│ 洗手台和办公区。你希望关闭：    │
│ 全部，还是指定区域？             │
│                                │
│ 不生成操作草案                  │
└────────────────────────────────┘
```

不能因为模型已经找到了设备，就默认生成“全部关闭”的草案。

### 场景 D：空调操作草案

用户：“把26楼会议室空调调到26度制冷，中风。”

```text
┌────────────────────────────────┐
│ ✦ 物联 Agent          已思考 8秒 │
│                                │
│ 处理记录 ⌄                     │
│                                │
│ 当前状态：开启 · 自动 · 24°C · 中风 │
│                                │
│          [空调操作草案卡片]      │
│          原状态 → 操作后状态     │
│          自动 24°C → 制冷 26°C   │
│          中风 → 中风（不变）      │
│                                │
│       [取消草案] [确认草案]       │
└────────────────────────────────┘
```

草案卡片由现有组件负责。Agent 容器只负责正确衔接它，不重复解释卡片中的内容。

### 场景 E：门禁连续开门 3 次

用户：“开26楼小会议室的门3次，每次间隔5秒。”

```text
┌────────────────────────────────┐
│ ✦ 物联 Agent          已思考 5秒 │
│                                │
│ 我会连续发送3次开门指令，        │
│ 每次间隔5秒。确认后自动执行。     │
│                                │
│          [门禁操作草案卡片]      │
│          3次 · 间隔5秒           │
│                                │
│                 [确认草案]       │
└────────────────────────────────┘

执行中
┌────────────────────────────────┐
│ 门禁操作                        │
│ ● 第1/3次已受理                 │
│ ◌ 第2/3次处理中                 │
│ ○ 第3/3次等待中                 │
└────────────────────────────────┘

执行完成
┌────────────────────────────────┐
│ ✓ 3/3 次指令已受理              │
│ 门状态不作为执行结果推断。       │
└────────────────────────────────┘
```

门禁不显示“已打开”这类物理状态，只显示真实回执。

### 场景 F：工具失败，允许恢复

```text
用户
┌─────────────────────────────┐
│ 打开26楼办公区空调            │
└─────────────────────────────┘

Agent
┌─────────────────────────────┐
│ ! 这次请求没有完成            │
│                               │
│ 当前没有拿到有效的设备结果，  │
│ 设备没有被操作。              │
│                               │
│              [编辑] [重试]    │
└─────────────────────────────┘
```

点击“编辑”：

```text
┌─────────────────────────────┐
│ 打开26楼办公区空调            │ ← 进入输入框
└─────────────────────────────┘
                         [发送]
```

点击“重试”：

```text
原失败轮：保留，不修改
        │
        └── 新建一轮相同输入
            ┌────────────────────┐
            │ 打开26楼办公区空调   │
            │ ◌ 正在重新处理       │
            └────────────────────┘
```

### 场景 G：用户主动停止

```text
处理中
┌─────────────────────────────┐
│ ✦ 物联 Agent        思考中  │
│ ◌ 正在检索设备               │
│                             │
│                       [■]   │
└─────────────────────────────┘

停止后
┌─────────────────────────────┐
│ ✦ 物联 Agent        已停止  │
│                             │
│ 本次回答已停止，尚未执行设备 │
│ 操作。                       │
│                             │
│                       [重试] │
└─────────────────────────────┘
```

迟到的流式事件不能在停止后重新写入页面。

### 场景 H：设备执行后自然收尾

```text
用户确认草案
        │
        ▼
┌─────────────────────────────┐
│ [操作草案]                   │
│ ✓ 指令已受理                 │
│                             │
│ 26楼会议室空调已受理调节。    │
│ 当前仅确认上游已受理，        │
│ 不额外推断物理状态。          │
└─────────────────────────────┘
```

执行回执必须先落在草案/结果区域，再由 Agent 追加自然收尾；不能让模型回答覆盖或延迟真实回执。

## 四、具体组件拆分

```text
ReplySurface.vue
├── UserMessage.vue
│   └── MessageActions.vue      编辑 / 重试
├── AgentIdentity.vue           头像 / 状态 / 思考秒数
├── RunTrace.vue                收起、展开、临时检索态
├── AssistantMarkdown.vue       流式文本 / 稳定 Markdown
├── ActionDraftCard.vue         现有组件，保持不变
├── ExecutionReceipt.vue        现有结果语义的统一展示
└── RecoveryActions.vue         编辑 / 重试 / 重新连接
```

事件层建议：

```js
{
  id: 'turn-1',
  run: { status: 'streaming', startedAt, stoppedAt, error: null },
  user: { content, editable: true, retryable: true },
  activities: [{
    invocationId,
    tool: 'find_device_candidates',
    phase: 'searching',
    summary: '正在调整检索范围…',
    final: false
  }],
  answer: { text: '', settled: false },
  draft: null,
  execution: null,
  recovery: null
}
```

## 五、落地顺序

### 第 1 个闭环：流式检索 + 0 候选抑制

- 后端事件补充稳定 `invocationId`；
- 前端 `conversation.mjs` 按 invocationId 更新节点；
- 0 候选只进入临时态；
- 命中后复用节点；
- 断线恢复后不重复播放节点；
- 补充单元测试和微信开发者工具验收。

### 第 2 个闭环：失败消息编辑/重试

- 为用户消息增加消息级操作；
- 编辑回填输入框；
- 重试创建新 turn；
- 与已执行草案隔离；
- 补充失败、停止、重试三种测试。

### 第 3 个闭环：统一回复表面

- 把现有多个区域收拢进 `ReplySurface`；
- 保留现有操作草案卡片；
- 完成回答开始后自动收起轨迹；
- 失败和待确认状态保持必要区域展开。

### 第 4 个闭环：图标和动效

- 固定状态 icon 容器尺寸；
- running → completed/failed 采用 cross-fade；
- 节点新增使用 180ms 位移淡入；
- reduced-motion 下关闭位移动画；
- 不为每个 token 添加动画。

## 验收标准

- 用户不会看到短暂的“0 个设备候选”后又跳到正确数量；
- 同一个检索节点可以被更新，而不是重复插入两个节点；
- 用户可以对失败的上一条输入进行编辑或重试；
- 重试不会重复执行已确认的设备操作；
- 草案、回执和自然收尾有明确先后关系；
- 流式停止后没有迟到文本重新出现；
- `npm test`、`npm run test:weixin` 和微信开发者工具均通过。
