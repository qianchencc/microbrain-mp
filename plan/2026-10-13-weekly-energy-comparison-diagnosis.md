4. 两次成功查询并持久化原始历史观察卡，各 20 条，nextPage 分别为 1、2。
5. 09:51:49 出现 run.failed，没有 message.completed。整个补充条件轮约 37 秒。

唯一运行实例的 `iot-agent-runtime/var/runtime-meter-readings-20261013.log` 记录：

```text
[runtime-agent-error] Error: 502: {"message":"Upstream request failed","type":"upstream_error"}
```

堆栈来自模型 runner → Langfuse 观测包装 → app。**直接中断来自模型上游 502，已成功返回的两页电表历史不是 HTTP 失败来源。** 502 的更深原因（服务波动、请求内容、路由等）未取得足够证据，不能归因于模型能力或上下文大小。

失败轮的轮次事件保留了历史数据，但会话 entries 未保留该轮用户消息及原始工具参数；app 非 abort 错误路径不追加 newMessages。这限制了完整模型输入重建，也影响后续继续对话。不能断言首次失败实际传入了哪个 equipmentId。

## 可复现的工具缺陷

使用当前 Runtime 的 buildApp + inject、生产协议进程内夹具、固定模型工具调用序列做单变量对照，没有联网或调用真实设备：

| 条件 | 公共行为 |
| --- | --- |
| 第一轮检索电表，第二轮沿用返回的 `d1_1` 句柄 | 历史查询失败，报“计量点不在当前公司观察范围内” |
| 相同设备、窗口、夹具，仅改为稳定计量点 ID | 历史查询成功 |

runner 的候选 Map 每轮创建；query_energy_history 仅在本轮 Map 中解析句柄。其他工具可显式恢复持久化候选集，这个工具没有对应恢复入口。它声明接受“已查到的设备句柄”，实际跨轮使用失败。

这是已经证明的接口缺陷，与原轨迹首次失败相符；因失败轮原参数缺失，不能把二者完全等同。修复应统一设备引用解析并重核当前授权，或对历史工具提供稳定 ID；不通过放宽授权检查解决。

当前只完成 [原始历史票 05](2026-10-09-meter-history-handoff.md)。query_energy_history 与系统提示明确禁止推导期间耗电；[单表统计票 06](history-observation-tickets/06-single-meter-interval-energy.md)、[比较票 07](history-observation-tickets/07-company-energy-comparison-report.md) 尚保留字段、单位、倍率、边界和不重叠集合的门槛。

分页明细每次都交给模型，模型还需要决定继续翻页、对齐周界、处理缺测和解释口径。coverage.complete 当前描述一页读取是否完整，不能表达每一周是否具备可比较的边界。单纯延长超时或增加提示词不能补足这一业务能力。

源码核对点：同级 Runtime 的 apps/runtime/src/agent/pi-runner.ts（query_energy_history、每轮候选 Map、模型错误抛出）、energy/history.ts（边界过滤与 nextPage）、iot/observation.ts（上游分页与排序）、app.ts（失败路径与消息持久化）。

## 建议的理想流程

1. 解析范围和时间；有当前选中电表就复用并核验，没有唯一范围才澄清。建议“最近几周”默认最近四个完整自然周，周一开始、上海时区，并在结果中明确默认值；本周单列“进行中”。这仍是产品建议，不是已批准默认。
2. 后端完成计量点身份绑定、历史读取、分页终止、去重、异常识别和边界取样。模型不管理页面游标，不直接把累计示数增长率当作耗电环比。
3. 按已批准计量口径计算每期用量，再计算 `(本期用量 - 上期用量) / 上期用量`。四个周用量提供三个相邻环比；若四周都需环比，再取前一周作基期。基期零、缺边界、清零/换表或冲突记录不给假精确百分比。
4. 返回一份可恢复的比较报告：每周请求区间、实际采样区间、边界值、期间用量、环比、是否可比及缺失原因，附字段/单位/倍率/数据来源。生成四行表或图；不把缺失填成零，不把本周半周与上周整周直接相比。
5. 追问沿用报告身份和口径；模型上游失败时保留已经取得的数据和报告，区分“数据读取成功、文字解释失败”，允许只重试解释。受控重试只能作用于明确无副作用的模型阶段，不能整轮盲重跑。

对当前数据，严格自然周报告应说明单位/倍率未确定、零点边界不足和最新采样停止；即使不能给出耗电环比，也应交付完整的覆盖说明与可采取的下一步，不只显示通用失败。

## 建议新增的设计：单表期间比较工具

先以“26楼运营部电表，最近四个完整周”作为唯一业务闭环。

建议新增 `compare_energy_periods`：输入稳定计量点引用、周窗口和比较方式；内部复用已有授权与历史适配器，服务端生成结果。模型接收每周摘要和证据引用，原始采样仍在历史详情中查看。结果通过现有 observation.reported 和恢复机制呈现，仪表盘与 Agent 共用同一计算。

返回状态应区分可比较、部分可比较、无法计算和读取失败；分别附原因，不把单位未知、缺边界等业务限制当作技术故障。

首期不增加通用分析引擎，不汇总 43 台电表，不并入照明集合票 03。公司汇总仍需证明计量点不重叠；这一条件不应阻断单表闭环。

实施前需冻结的最小决策：

- epf 的统计用途及适用单位/倍率；若未确定，可明确只提供原始累计示数增量比较，不宣称耗电 kWh。
- 严格自然周，还是明确采用周一 08:00 至下周一 08:00 的采样周期。后者必须如实命名，不能悄悄取代零点自然周；插值或近邻估算需另批准。
- 是否采用最近四个完整周的默认，本周如何单列。

建议依 ask-matt 路线从已完成诊断进入 grill-with-docs，冻结以上决定后再修改票 06/07 规格并实现。初步生产代码估算：Runtime 180–280 行，mp 报告呈现 80–160 行，引用/错误恢复作为该闭环必要配套；若估算明显超出，先缩减范围再实施。
