# 设备位置纠错修复方案

日期：2026-10-21。状态：待确认方案，未实施、未测试、未部署。

目标：用户说出与目录不同的地点称呼时，Agent 利用当前来源的目录证据自行查证；对应明确时继续回答，有歧义时给出具体真实候选，而不是把一次名称未命中说成区域或设备不存在。

## 事实与待查证项

- Runtime `8a6ef14` 是本次本地核对的已提交基线。`apps/runtime/src/iot/adapter.ts` 另有区域路径相关并行 WIP，不能当作已发布行为。
- 当前每轮 `runtime_context.device_context` 已提供类型、数量、位置提示、位置计数与基础名称提示。目录摘要不是空白，但也不是全量设备清单；目录构造对每类位置和名称提示各有 8 项上限。
- 现有 `find_device_candidates` 返回设备明细、分组、完整性与 `resolution.alternatives`；模型负责解释口语、调整调查和提出候选。宽查询的模型明细和分组仍有展示上限。
- 已确认的工具契约缺口：只传 `scopeTerms` 且零命中时，建议计算依赖非空 `scopeText`，因此该参数形态得不到位置建议。若两种参数同时存在，当前模糊路径又可能运行，不能笼统声称 `scopeTerms` 会关闭所有回退。
- 尚未取得截图原轮的模型输入、全部工具参数与返回。不能把上述参数缺口直接认定为截图根因，也不能用折叠处理记录判断只调用了一次。
- 本机已有 `region-answer-runtime.json` 记录的是后续“26楼有哪些区域”，不是截图原问题；不能用后续轮替代原轮证据。
- 既有位置分组规格及 6 张票属于未实施的较大改造，不是本次修复必须整体启动的前提。其中旧目录数量、模拟结果不充当当前线上验收。

依据：Runtime ADR 0002、0003、0004，以及 [Prompt 职责减负交接](../../iot-agent-runtime/plan/2026-10-13-prompt-responsibility-handoff.md)。完整位置分组方向见[原规格](../../iot-agent-runtime/.scratch/agent-location-groups/spec.md)，本方案不另建执行图。

## 设计约束

| 职责 | 所属 |
| --- | --- |
| 理解“运营办公区”等口语、结合上下文纠错、判断是否需要澄清 | 模型 |
| 提供当前来源真实名称、位置、数量及完整性证据 | 设备目录与发现工具 |
| 身份与来源隔离、候选引用重绑定、能力核验、确认及执行幂等 | 现有 Runtime |
| 显示候选、只读结果和待确认卡 | 现有小程序 |

继续采用“有界地图 + 按需查证”。不常驻注入全量设备，不新增向量检索或另一层语义 Agent，不维护“运营办公区 = 运营部”之类固定别名，不规定固定工具调用顺序或固定重试次数。目录文本始终是数据，不是指令。

来源隔离限制的是设备证据和操作范围，不限制模型理解用户称呼。Company 可以理解用户说“运营办公区”，但其候选、读取与提案只能来自当前 Company 目录，不能借 Office 成员关系证明两个区域相同。

## 推荐的最小修复

### 1. 先锁定失败发生在哪一层

实施前捕获截图原轮，或在同版本、同目录快照上重新产生同类失败。只保留脱敏后的用户问题、当前目录摘要、模型工具参数、返回证据、预算/守卫终态和公开答复；不导出思考文本、凭据或视频地址。

分别判定：

- 摘要是否已有可用位置线索。
- 零命中后是否返回真实候选；返回是否在模型投影处丢失。
- 模型是否已经拿到候选但未继续查证或未向用户给出选项。
- 是否被重复调用、同类型次数或总预算提前收尾。

完成条件是能够对照一次实际输入与工具返回解释失败路径。远端访问、真实网关和模型请求须另获授权；本方案阶段不发起。

### 2. 补现有发现工具的证据，不更换工具体系

保留 `find_device_candidates(DeviceQuery)`、候选集句柄和现有提案接口。优先复用 `resolution.alternatives: Array<{ label, count, score }>`，不增加另一套位置引用或设备 ID。

目标契约：

- `scopeText`、`scopeTerms` 及二者并存的失败查询，都能获得当前来源的真实候选建议；建议文本可使用用户提供的原始范围条件，不依赖模型碰巧选择某个参数字段。
- `devices`、`allDevices`、`totalMatches`、`groups` 仍表示实际查询结果。硬条件零命中时保持零命中和 `unresolved`，不把建议或整层设备偷偷填成精确结果；两种范围字段并存也不能绕过明确硬条件。
- 建议只从当前快照、当前设备类型的真实名称、安装位置和区域路径产生。标签必须可追溯到原始字段，不推导不存在的房间名或同名区域关系。
- 沿用现有有界建议形态，最多 5 项。相似度只用于线索排序，不证明语义相同、用户已选择或设备可操作。
- 建议优先保持已明确且能核验的楼层等上位位置限制；冲突位置不作为替代答案。不能核验时明确保留未知，不靠常识补归属。
- 原名称完全无字面近似时，可以提供满足已核验上位限制的有界目录线索，并保留其“建议”性质；若连该范围的线索也没有，不保证非空。
- 建议中的 `count` 沿用当前目录记录计数口径，不额外声称是物理设备去重数，不用多个标签的数量相加代替范围总量。
- 工具与模型投影共用同一份证据；不额外读取 Office、其他身份或范围外目录，不为生成建议重新加载整份网关目录。

实际原轮若已拿到充分的建议，就不为修复模型行为重复改目录算法。只实施能由失败复现证明必要的差异。

### 3. 让模型在现有自主循环中消化证据

在共用 `deviceDiscoveryPrompt` 及工具契约处合并现有重叠说明，不增加某个区域专用指令。拟替换为以下通用原则，最终文本须随实际差异审查：

> 目录摘要用于导航，不代表全部位置明细。名称未命中时，结合当前目录的真实位置、名称分组和候选建议核对口语；较宽查询用于查证，最终回答和提案保留用户明确的地点限制。有充分证据且对应明确时继续查询；有多个合理解释时列出满足已明确地点限制的真实候选供选择。证据不足时说明不能确定，不把单次未命中说成设备或区域不存在。

模型自行决定采用已有证据、重新查询还是澄清。调查范围可以更宽，用户最终选择范围不能因此变宽。建议不自动成为状态读取对象、草案成员或未来任务目标；沿现有候选查询、引用与核验路径取得明确成员。

先保留现有运行预算与守卫。只有实际轨迹证明合法纠错被守卫拦截，才另做最小局部修正，不借本次问题删除全部守卫。

## 预期效果

以下是验收目标，不是当前已实现或固定回复模板：

| 场景 | 期望行为 |
| --- | --- |
| “26楼运营办公区有哪些设备”，目录中有足够证据对应唯一相关范围 | 自动对齐目录实际叫法，说明按哪个范围查询，列出本次查到的设备类型及真实数量，不返回整层冒充该区域 |
| 同句但存在多个合理范围，例如公共办公区与接待室 | 给出本层真实候选并简短询问用户指哪一处，而不是要求重新想一个目录名称 |
| “楼道的灯”，当前目录使用“过道” | 模型结合目录证据提出相关候选；没有证据时不由服务器配置同义词或强选第一项 |
| 用户回复“公共办公区那个”或“后者” | 沿实际上一轮选项解析，重新核验当前来源成员，不扩大到整层 |
| 仅 Office 有该名称或 Company 目录覆盖不足 | 说明本端证据不足，只列本端能确认的候选，不混用 Office 目录，也不宣布现场不存在 |
| 候选位置仍未明确，却要求关闭设备或建立周期计划 | 继续必要澄清，尚不生成范围含糊的可确认提案，更不下发设备 |
| 用户明确选择后要求安排操作 | 沿现有提案、卡片确认、固定执行快照及到期核验，不改变控制授权 |

不承诺一次请求必成功、必定无需澄清或节省固定秒数；少走无效往返是预期收益，须实测。

## 验证与完成门槛

1. 复现与工具契约：从适配器公开接口构造两种参数及并存形态，验证硬范围、零命中与真实建议分离；包含精确命中、多候选、无相关候选、跨楼层干扰和空位置。用首次失败的最小场景锁定回归，不测试私有评分实现。
2. HTTP 链路：从 `buildApp` 消息接口进入真实 runner，以生产协议夹具和脚本模型验证建议确实到达模型、用户选择后复用正确成员、Company/Office 与不同身份隔离、查询/澄清阶段零控制、范围不明零提案。脚本模型只证明契约，不能证明模型自行纠错。
3. 自然模型验收：沿用户原句及独立变体，分别检查唯一对应、多候选、错误楼层、没有对应、跨轮选择和控制意图。固定版本、目录与配置，保存所有成功及失败，不预写助手候选回答；未获外部请求授权前不运行。
4. 解释口径：不按固定文案或固定工具顺序判定成功；看候选是否真实、最终范围是否守恒、缺证是否如实说明、控制是否仍需确认。不能用单轮成功宣布全面可靠。
5. 修改后只运行覆盖本次差异的既有定向回归，再做必要类型检查和构建。最终集成门槛与两轴审查在实际实施时确定；不因当前文档阶段重跑全套历史验证。

当前尚无原轮复现、红绿证据或新模型验收结论。实施完成、合入主线、部署与微信验收分别记录，不能相互代替。
