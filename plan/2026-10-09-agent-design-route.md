# 物联 Agent 设计：起点、终点与推进路线

日期：2026-10-09。状态：路线探索，已完成首条隔离自然委托比较；不是批准规格或可执行票据。首次记录只核对资料，随后在用户授权下完成隔离模型诊断；没有修改生产业务代码或重启服务。

## 起点：现有业务已接入，Agent 使用它们的能力尚未充分验证

当前问题是用户无法顺畅地把业务意图交给 Agent：对象找错、反复检索、多轮选择丢失、产生未要求的安排，以及失败后无法说明停点。不能把它缩成“缺一个位置工具”。

已经存在的基础是双来源目录、设备读取、提案与确认、任务/周期计划、后台执行、回读、报告和历史查询。继续复用这些业务能力；具体场景是否可用，仍须逐条验收。

## 终点：用户能完成现有业务委托，并继续追问真实结果

建议终点覆盖 Office/Company 当前已接入的业务。不是合同所有未来能力，也不是仅交付新工具。该范围尚待用户回应。

用户用业务语言描述对象和目标，Agent 自行取得必要事实；真正有歧义时询问。用户选择、排除、纠正、修改时间或作用域后，未修改的意图仍保留。提案展示实际对象与安排；确认后复用既有执行器执行确认快照。报告和后续追问引用同一次任务事实；无法确认、预算结束和服务故障如实表达。

只读查询则止于有来源、时间和覆盖说明的结果，不强行创建任务。照明/空调/门禁、环境/安全台账、计量历史及直播/录像入口的不同业务边界继续保留。

终点验收看实际目标集合、动作、时间、重复规则、修改作用域、引用归属和结果证据。测试数量、提示词长度、工具数量、退出成功或出现卡片都不能单独替代它。

## 路线与阶段出口

当前位于 `ask-matt → grill-with-docs` 的范围与验收定义阶段。事实诊断使用 `diagnosing-bugs`，与用户决定产品行为分开；需要运行才能判断的设计进入 `prototype`。决定形成后才走 `to-spec → to-tickets → implement`。

| 阶段 | 要解决的问题 | 可以进入下一阶段的条件 |
|---|---|---|
| 定义委托与验收 | 哪些现有业务必须成功，哪些情况应澄清、拒绝或报告未知 | 用具体用户场景确定终点；技术方案不能代替产品目标 |
| 还原失败与诊断 | 哪一步丢了对象、意图、事实或运行能力 | 有能捕捉原症状的可重复命令；还原实际模型输入、工具定义/返回、历史和预算；同条件逐因素验证，记录未决项 |
| 验证设计候选 | 模型需要哪些事实，代码负责哪些业务保证 | 对话能决定的问题由用户决定；运行问题在隔离候选上验证；自然生成首轮选项，多轮承接正确；不能用固定历史冒充全流程 |
| 冻结规格与拆票 | 哪个方案足够，怎么按业务逐条交付 | `to-spec` 收拢已确认决定；`to-tickets` 每票交付完整业务路径，只声明真实阻塞关系 |
| 实现与交付 | 每条业务是否真的可用 | `implement` 内按 `tdd` 保护公开行为；真实模型检查语义；稳定切片做 `code-review`；微信及具体授权场景验证；提交并记录交接 |

诊断首先建立反馈循环，再提出可证伪的原因假设。固定模型、输入、目录和预算，一次只改变一个因素；当前没有证据把更换模型列为先决条件。缺日志或缺原始请求要明说，不能补造完整输入。

五次直接失败单独进入诊断支线。若发现与定位切片无关，不阻塞该切片；若仍影响实际委托，则阻塞最终集成交付。诊断设施只服务于业务，不成为另一个平台项目。

当前可明确列出的决策能够先在一次 `grill-with-docs` 中讨论；若调查进一步发现无法在一次会话厘清的依赖，再用 `wayfinder` 建决策地图。多会话实现本身不构成使用 wayfinder 的理由。地图若需要建立，出口仍是 `to-spec`，不能从决策票直接跳到实现。

## 首条贯穿业务，以及后续扩展

第一条建议从自然生成候选开始：

> 用户安排办公区照明 → Agent取得真实候选并消歧 → 用户选择第二组、排除一项并改时间 → 展示对应设备和时间的提案 → 用户确认 → 执行与回读 → 从同一报告继续追问。

实验可先在生产协议夹具上贯穿确认、执行和报告，真实模型负责产生首轮和后续判断。夹具验证不冒充现场控制；现场阶段需要明确设备、动作和用户实际确认。加入“没有两个选项却说后者”、更名/重排、纠正地点、恢复会话和撤权等必要反例；不要求固定工具调用顺序或零次补读。

之后依次验证同一设计在以下业务中的迁移，顺序与阻塞关系在规格阶段确定：

1. 整层集合与排除：展示和确认完整实际影响集合，不漏项、不擅加反向动作。
2. 已有Task/Plan引用和修改：仅本次与整个周期、跳过与停用、历史和执行中快照保持正确。
3. Company只读查询：环境、台账、计量历史和录像窗口保持原设备/时间/来源，未知和陈旧事实诚实表达。
4. Office/Company来源与恢复：换设备类型、目录顺序和用户表达后仍正确，旧引用不成为永久授权。

每条完成才扩大下一条；不是先改完数据层、工具层、提示词层，再最后找业务验证。

## G1–G4应回到哪些待决问题

| 候选 | 真正需要决定并验证的内容 |
|---|---|
| G1：命中/未命中词 | 楼层等硬范围与设备描述怎样区分；部分命中可供消歧，但不能静默放宽用户范围成为执行目标 |
| G2：整体结果引用 | 引用代表哪次完整发现；恢复后怎样重核授权；提案展开并固定哪些成员；确认后不动态增加设备 |
| G3：集合排除 | 排除作用于哪份集合；未识别排除项不能当作已经排除；改时间或恢复时保持同一排除事实 |
| G4：渐进披露 | 哪些层级由客户事实支持；模型如何继续取得完整集合；模型展示大小与实际操作范围分开 |

“同hub、同名、跨叶子”支持疑似重复的判断，不能单独证明两个记录的控制语义相同。去重前还须核对回路/动作身份、授权成员和历史引用；离线136台不是可直接覆盖现有目录的生产事实。

稳定ID解决对象引用，不自动建立用户所见“第一组/第二组”的映射。四段短prompt也不是既定目标：应明确长期原则、工具契约、当前证据和权威状态分别由哪里提供，避免遗漏必要业务语义或再次多处维护。

旧候选工具迁移影响计量历史与录像准备，必须计入兼容与恢复验证。已有隔离候选、位置分组候选和提示词候选按同一业务场景比较，先确定必要改动，不同时混合改完后再猜哪个因素有效。
