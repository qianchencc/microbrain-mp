# 公司 Agent 检查点能力扩展讨论

日期：2026-10-14
状态：2026-10-15 用户认可核心语义及先原型路线；现处于原型阶段，前轮隔离实现仍为未验收 WIP，不代表实现或部署获认可。

## 已知起点

- 继续使用 Task、周期计划、发生与检查点，不另建业务对象体系。
- 用户提出公司 Agent 的检查点设置能力范围可以更加灵活。
- 当前 Runtime 检查点承载已确定的照明/空调动作，或环境、能耗、安全、视频设备的只读读取；读取与控制互斥。
- 当前只读检查点保存观察结果，没有把观察结果接入条件操作，也没有调用 Agent 生成指定主题的分析报告。
- 当前 CONTEXT 与 ADR 0005 规定到点直接执行、不重新调用 Agent 做规划。允许后台 Agent 判断将改变这一约定，不能只放宽工具参数就声称已经支持。
- 当前 Company 读取和控制均使用其本端授权目录。观察对象和执行对象可以不同；传感器在同一楼层不证明其覆盖目标房间。

代码依据：Runtime `apps/runtime/src/domain.ts` 的 TaskProposal、`apps/runtime/src/agent/pi-runner.ts` 的 propose_task、`apps/runtime/src/app.ts` 的任务校验、`apps/runtime/src/tasks/scanner.ts` 的到点执行。

## 建议的业务表达

一个公司检查点可以调用 Agent，按用户预先确认的指令，在允许的数据与工具范围内取得事实、分析并组织输出；结果归属本次检查点。这里接入的是一种可调用能力，不是让 Agent 自主完成整项业务，也不限定所有调用都生成报告。

| 场景 | 到点工作 | 结果 |
|---|---|---|
| 每个工作日 09:00 出用电简报 | 查询指定计量范围的最近完整期间，与前一可比期间对比 | 同范围统计/对比报告及分析结论 |
| 14:00 检查会议室环境，温度超过 28℃时开启指定空调并设为 26℃ | 核验对应传感器的有效室温，判断条件，再按授权动作处理 | 实际室温与来源、判断、操作回执和回读 |
| 18:30 核对某区域照明是否关闭 | 读取照明状态，按委托报告或关闭仍开启的设备 | 已关闭、无需操作、执行失败或未核验分别保留 |

这些是设计示例，不证明现场已有传感器覆盖或全部数据条件，不代表已创建计划或授权真实控制。

## 当前设计分叉

1. 保存业务目标及允许的处理范围，到点由 Agent 读取、分析并提出范围内的处理。推荐讨论方向；具体动作权限和判断门槛仍需冻结。
2. 创建时固定全部条件与动作，到点由直接执行器判断。行为更可预测，复杂分析目标的表达范围较窄。
3. 先扩展定时读取、统计、对比和分析报告，条件控制后续推进。

用户随后将当前主线明确为公司周期检查点调用智能体产出报告，任务完成通知关联该报告。如何接入智能体执行能力仍在讨论；自动物理控制的范围没有因报告方向获认可而同时确定。

## 后续需要按所选方向收口

- 保存哪些目标、数据范围、允许动作及参数；分析是否使用 Agent 与物理动作判断是否使用 Agent分别明确。
- 条件证据缺失、过期或覆盖不匹配时，保留无法判断；不能按条件成立下发。
- 何时需要再次确认，如何承接创建时的显式委托。
- 检查点报告如何复用现有结构化观察卡、统计/对比报告及任务详情。

检查点时刻及周期仍沿现有已确认安排；是否允许后台增加或调整检查点不包含在当前提议中。

## 本轮边界

## 报告产物补充讨论

用户提出：增加报告这种产出类型；报告是可复用的内容产物，可进入收件箱，通常由入口点击后在抽屉预览；组织形式及组件组合相对自由；以简单方式补上下载业务，不追求完整交互的导出体验。

用户在后续回复认可报告方向，并明确它主要随公司检查点增强交付，核心是周期任务每次产出报告并放入完成通知。以下组织方式作为设计依据，具体接口尚未冻结：

- 报告具有独立身份，来源可以是即时查询、任务检查点或任务终点。同一个报告可从对话、任务详情和收件箱打开，并作为后续 Agent 追问的引用。
- 原有任务报告仍表达执行事实；分析报告可以组合这些事实。赋予产物统一身份，不要求复制任务执行记录或把每条聊天回复保存成报告。
- 报告保存生成时的内容和数据依据，重新打开不重新生成；重新分析产生新报告，不静默覆盖旧内容。
- 入口默认展示标题、简短摘要和生成时间；点击进入共用 DeviceSheet 的报告预览。抽屉内下钻和返回沿用当前单层导航栈。
- 内容可组合文字、指标、表格、趋势、对比、设备结果及依据。组合和顺序可以灵活，组件类型由应用支持，不能让模型下发任意 Vue 组件或可执行代码。
- 收件箱条目引用报告，保存接收者和阅读状态；报告内容与已读状态相互独立。同一份报告被多个入口引用不创建多份内容。周期每次完成通知关联本次报告；常规对话也可产出报告，但即时报告是否额外投递及扩展接收者不作为已确认需求。
- 建议先导出简版 PDF：标题、摘要、正文、指标、明细表和必要依据；交互图表以对应数据表替代。导出使用同一份已保存报告，不重新查询或让模型另写一份。它不复刻抽屉的交互和视觉，但应保留主结论、单位、期间及影响解释的数据缺失。

组件的存在不禁止生成 PDF，只是互动能力无法带入静态文件。导出格式、页面排版和小程序下载打开流程属于后续实现验证，本轮没有声称已实现。

当前基础核对：Task 收件箱通过 taskId 打开 TaskDetailContent；任务结束通知关联 tasks.report_json。电表统计/对比结果已有 reportId。已有对象可以作为扩展起点，当前不存在覆盖所有这些类型的统一报告入口与下载闭环。

## 智能体作为检查点能力

用户示例：每天早上 09:00 生成昨日公司能耗统计及同环比分析，每次任务完成时把报告关联到完成通知。用户询问把智能体能力接入检查点组合是否是前提，代理判断是。

建议保留检查点的时刻与归属，引入按已确认指令执行的 Agent 调用能力，复用现有模型执行、公司只读工具和报告组件。读取、确定性操作和智能体分析在任务中可组合；对于分析检查点，智能体内部调用现有读取/统计/对比工具，不要求用户逐个编排工具步骤。无需先引入任意节点图或工作流编辑器。

一次发生的建议流程：

1. 周期计划到期生成实际 Task，并认领检查点。
2. 根据本次发生日期和上海时区解析“昨日”和比较期间；不复用创建计划当天的日期，也不直接沿用原聊天历史。
3. 以创建者当前授权范围执行报告委托，调用已有统计/对比工具取得结果与依据；数值由工具计算，Agent 组织解读及内容块。
4. 保存本次报告产物及其 Task/检查点关联，随后收口任务执行结果。
5. 完成通知引用本次产物。收件箱展示入口，点击抽屉预览，可继续引用追问及下载简版文件。

先以这个只读日报闭环验证 Agent 检查点；加入智能体能力不自动允许扩大设备范围、改变未来检查点或下发任意控制。固定设备目标仍由现有直接执行器承担；Agent 条件控制需在相应业务切片中明确委托及确认语义。

报告没有生成时，仍需保存明确的任务失败结果和完成通知，不产生“报告已生成”的假入口。已有统计事实但解读失败时应保留统计结果并说明解读未完成。数据缺失、不足或不新鲜时保留实际覆盖，不能把最近旧数据冒充昨日，也不能凭空生成同比。

尚需收口的语义：“同比”所指的比较基期、Agent 检查点首期可用工具及执行上限、多检查点产物与任务整体完成的关系、报告访问与引用、生成失败后的重试。现有 interval 仍在任务整体终点发送结束通知，检查点完成不默认提前发结束消息。

## 2026-10-15 用户确认与阶段纠正
用户认可：检查点能够调用 Agent 执行用户预先确认的指令。Agent 是一种可调用能力，报告只是可能的输出；任务系统仍负责触发、归属、状态与通知，不交由 Agent 自行扩大范围或改变后续安排。首条验证场景是只读能耗日报；不据此宣称条件控制或全部检查点扩展已经交付。
只有任务收件箱。任务整体结束通知打开同一次任务的结果，再从其附带入口查看报告；报告可有独立身份，但不另建报告收件箱。检查点提前结束不提前结束区间或发送整体完成通知。
对话统计卡、同比卡、环比卡的另一工作线独立维护：同比与环比仍是两次独立时间对比，不为报告产物重构其组件或计算契约。本线程只验证这些已有事实如何作为报告内容引用与组织。同比按去年同期间表达；缺乏有效基期时明确不可比，不改成上周同日。
前轮生产组件与后端实现只作未验收材料。先以独立可点击原型确认任务结果、附带报告、依据、返回、引用与简版下载；原型认可后才形成新的正式规格与实施票据。源码测试、浏览器原型、微信模拟器、真机和真实后端分别验收。

2026-10-15 原型评审纠正：用户只认可报告内部A简报长页，不认可外围任务/收件箱/执行结果重设计。接入方式唯一新增为执行结果中所属阶段的一行报告条目；其余复用现有组件和交互，不新增“本次报告”分区、不重排任务详情、不改变已读、通知或周期展示。四票拆分尚未获认可，上一版原型外围不作为实现依据。
