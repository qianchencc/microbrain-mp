# 完整物联网权限复核

首次复核：2026-09-11；链路补充：2026-09-14

当前 `XSJ` 测试账号已通过只读请求访问 `api-office`、`api-iot-center`、`api-perception` 和 `api-energy` 的核心目录，未遇到 401 或 403。详细数量、分类和目录指纹见 `docs/research/2026-09-08-customer-miniapp-iot-api-inventory.md`。

原 Iotfake 快照曾成功读取门禁 47、空调 53、照明 159 条 `api-office` 关联记录。2026-09-11 的最终复核又发现，门禁和空调关联目录在另一浏览器会话中返回业务码 204 和 0 条记录，因此这些数量只能视为已验证快照，不能再视为所有入口下都稳定可得。物联中心另返回 333 个底层设备；感知服务返回 170 个设备和 129 个照明回路，能源服务返回 43 个设备。

测试环境只需保持统一设备注册层对更多类型的扩展位；当前产品阶段暂不接入监控、能源、楼宇控制、消防和环境传感器。正式 Agent 使用客户小程序当前登录用户的 Office 用户设备接口集合，固定 token 只模拟一个用户，不能被误读为另一套权限模型。

当前业务闭环已经完成：Scope → Capability → Control → Readback（本地确定性回读）→ Agent 收尾；空调、照明、门禁均已在 Runtime 默认授权来源上验证。下一步是把客户已有状态响应体接入生产 `readStates()`，并在微信开发者工具中做真实端到端验收。

已知工程缺口：客户接口已经返回响应体，但 Runtime 尚未把生产状态/详情响应接入 `readStates()`；`devicePage` 的局部 204 不能覆盖或否定用户设备接口的授权范围。能源、感知和更多设备类型暂不进入当前 Agent 产品闭环。

2026-09-14/15 补充确认：Agent 的唯一业务范围上游是 Office/工作区同级用户设备接口族；客户上游已按当前小程序登录用户完成设备授权过滤。固定 token 只是测试环境固定一个用户。 “我的办公室”只是一个页面实现，不是 Agent 的额外隔离边界；各“智慧”入口直接进入云起面板，与 Agent 范围发现无关。此前根据“智慧”页面或局部 `myAreaList` 204 推断工作区分配为空的结论已经撤回。

补充核验的只读事实：333 台底层设备中没有道闸/停车/车牌类设备；空调为云起智慧空调 55 台、三菱控制器 11 台；视频 35 台均有“查看/在线状态”动作和 WSS 地址，但实时 WebSocket 握手失败；环境传感器 1 台可返回温度、湿度和 PM 数据；烟感、水浸、燃气各 1 台均有告警采集动作。能源设备 43 台全部标记为 `ELECTRICITY`，水用/气用分页为空；照明策略和空调策略/场景各有 1 条历史测试记录，不能视为已上线自动化能力。

2026-09-11 已对“空调-26办公区（机房前）”完成一次用户授权的生产控制闭环。该设备属于 `api-iot-center` 的“云起智慧空调”，通过 `acDetailHandler` 回读到开启、设定 24°C、环境 24°C；随后通过 `acControlHandler` 将设定温度更新为 25°C，平台与云起侧均返回成功，再次回读确认设定值为 25°C。该事实否定了“所有空调都存在控制或状态问题”的结论。

Agent 只使用 Office Scope Family 返回并聚合的用户办公室、区域和设备范围。“我的办公室”是其中一个来源；“智慧空调”等云起面板完全排除在范围发现之外，其控制动作只能作为办公室设备内部 provider binding 的候选实现。详细契约见 `docs/research/2026-09-14-my-office-device-scope-contract.md`。
