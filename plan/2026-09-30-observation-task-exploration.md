# 观察设备参与 Task 与业务卡片组合探索

日期：2026-09-30。阶段：本轮 O1/O2/O3 已认可，`prototype` 已完成浏览器走查，等待用户体验反馈。不是冻结规格；未发布实现票，未修改生产业务代码。

## 用户已认可的方向

- 新增设备按本次任务的职责参与：执行对象、观察对象、条件来源、结果验证来源；只读身份继续限制控制。
- Task 从定时控制扩展到完成明确业务，能够容纳只读检查及显式条件；保持确认时安排检查点、到时由执行器处理的方向，不在运行中自主规划。
- 回复组合有限的业务组件，表达观察证据、提案、任务记录和报告之间的关系。模型不注册任意组件，客户端保证呈现质量。
- 先验证证据到草案的体验，首条新增实现闭环采用一次性只读巡检，再扩展条件控制。该切片不要求周期计划先完成，也不改变已有周期任务的排期与范围。

依据：用户在业务场景与建议后回复“认可，继续”。四种角色已补充到 [领域词汇](../CONTEXT.md)。

## 本轮源码事实

| 事实 | 证据 | 设计影响 |
|---|---|---|
| 账号级环境、安全、能耗设备按只读方式加入目录，`officeIds` 为空 | [目录组装](../../iot-agent-runtime/src/iot/adapter.ts:242) | 账号可见不证明房间归属；只读任务的设备选择与区域投影需明确 |
| 环境设备直读标为 `device`，但返回的 `reportedAt` 为 null | [环境读取](../../iot-agent-runtime/src/iot/observation.ts:191) | 查询时间不是采样时间；不能仅凭成功直读认定新鲜度 |
| 环境失败回退影子值，站点级、无时间戳 | [影子读取](../../iot-agent-runtime/src/iot/observation.ts:206) | 允许作为带限制的观察事实，不能自动解释为房间实测 |

| 视频在线状态没有上报时间，安全设备没有当前态读取 | [状态适配](../../iot-agent-runtime/src/iot/adapter.ts:190) | 在线查询不等于画面正常；安全台账不等于实时监测 |
| 扫描器将阶段保存的 actions 交给设备控制执行器 | [扫描入口](../../iot-agent-runtime/src/tasks/scanner.ts:29) | 后台只读巡检没有现成步骤；不能把查询伪装成控制命令 |
| 前端已有多份观察报告与任务卡呈现，但证据到提案的显式关联尚缺 | [回复呈现](../pages/agent/components/AgentReplySurface.vue:23) | 原型需验证证据可展开、提案可追溯，避免多卡简单堆叠 |

本轮没有真实上游探测。以上为源码事实，不证明设备现场归属、读数实时性或生产播放状态。

## 本轮产品问题

用户回复“认可，请继续”，以下推荐按本轮选择接受。更细的区域投影与证据标准仍需通过原型及后续规格核对。

| 编号 | 问题 | 推荐 | 当前状态 |
|---|---|---|---|
| O1 | 无权威区域 ID 的观察设备能否参与首条只读巡检？ | 允许用户明确选择当前有权查看的设备，报告标为用户指定；不据此宣称房间归属，条件控制仍需核验覆盖关系 | 已接受 |
| O2 | 读数旧、影子或时间未知时怎样处理？ | 巡检保留事实与限制；条件控制要求可信覆盖与新鲜度依据，不足时不执行依赖它的动作，独立检查点继续 | 已接受 |
| O3 | 确认未来任务覆盖哪些后续动作？ | 一次确认完整设备范围、时刻、读取项目、条件与允许动作；修改范围、条件或动作重新确认。即时操作确认当次草案 | 已接受 |

O1 的后续决定：观察设备选取如何在区域工作台投影；用户指定设备属于任务范围，不自动修改权威设备位置；是否有需要查询的覆盖关系来源。

O2 的后续决定：按读数种类定义可用证据，新鲜度标准与直读契约的依据；条件无法判断与条件未满足分别如何进入报告。先明确原则，不杜撰采样时间或统一阈值。

O3 的后续决定：纯观察任务的确认文案、未来提案修订和证据引用；确认范围不替代执行时的当前权限复核。

首条实现是纯观察，不引入物理条件控制；O2/O3 中关于未来条件动作的选择服务于后续场景，不用于扩大首条切片。

## 原型准备范围

原型从本轮接受的选择出发，复用现有 Agent 回复、观察块、任务卡、抽屉与报告的视觉语言；开发样例不写真实任务，不控制设备。代码保存在独立 `prototype/observation-task-loop` 分支，主线只保存决定和交接。

原型入口、提交和验证见[原型交接](2026-09-30-observation-task-prototype-handoff.md)。两条流程已经可操作；纯观察任务的区域投影未在本次卡片原型中实现，仍需在规格阶段明确。

### P1：一次性只读巡检

模拟请求：“明天 18:00 检查这些摄像头、环境读数和安全台账，生成一次巡检报告。”

1. 从有权查看的设备中选择范围，按 O1 显示区域归属与用户指定的区别。
2. 一张统一 Task 提案列出执行时间、设备和检查项目；不出现控制目标。
3. 用户确认后进入待执行状态。
4. 本地模拟执行读取，保留各检查项的来源、查询时间、采样时间或未知及结果。
5. 报告组合环境、视频和台账块，摘要说明哪些查询完成、哪些数据不足或未取得。
6. 点开某项报告事实可查看本次证据；同一 Task 的详情与对话引用保持一致。

覆盖三种结果：查询均完成；部分查询失败；查询完成但读数陈旧或时间未知。报告分别呈现查询完成度和证据质量，不把数据不足改写成设备故障。

首条业务验收：用户能确认一次无控制动作的任务，到时读取所选授权设备并保存可恢复的报告；报告不依赖当前设备状态重建历史。不以周期、条件控制或真实通知投递作为此切片完成条件。

### P2：即时会议准备

模拟请求：“先看会议室温度，再给我开灯和调空调的建议。”

1. 呈现本轮温度事实，并区分房间实测、参考影子和时间未知。
2. 提案可查看引用的事实，不逐条复读观察块。
3. 用户确认联合草案；本地模拟设备结果。
4. 区分设定回读、仅受理和失败；不把设定温度写成实际室温。

P2 用于验证卡片关系，不与 P1 同时实施新的生产业务。观察到即时草案的现有链路可单独复验。

### P3：后续条件控制示例

仅在 P1 的报告事实结构可复用后，模拟检查点“室温超过 28℃才调到 26℃”。需要分别展示：条件满足、条件未满足、证据不可用；不得把后三种情况折成一个“跳过”。本期不做连续监控、自主增检查点或通用分支工作流。
