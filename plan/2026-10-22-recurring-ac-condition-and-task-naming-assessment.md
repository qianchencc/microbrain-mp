# 周期空调条件检查与任务命名评估

> 状态：方案评估，未实施、未部署、未执行真实设备控制
>
> 日期：2026-10-22

## 1. 目标和范围

本轮只处理两个相互关联的问题：

1. 支持“公司空调在指定时间段内按固定频率检查，满足条件时调到 26℃”的可靠闭环。
2. 让任务卡、任务列表和任务详情清楚表达检查条件、动作、范围和时间，并解决任务名称过长、截断和语义混杂的问题。

目标是复用现有 `RecurringPlan`、`Task`、`Phase`、任务报告和通知能力，补齐条件检查所需的最小结构。当前不引入通用规则引擎、工作流平台、自由表达式编辑器或新的自动化中心。

## 2. 当前实现和主要缺口

Runtime 当前已经有空调检查的安全执行骨架：

- `AcInspectionSpec` 目前只有 `mode: "inspect" | "adjust_to_26"`。
- `materializeTaskProposal` 要求空调检查使用有限时间区间和不超过 12 个显式检查点，并暂时拒绝空调检查与周期规则同时存在。
- `tasks/scanner.ts` 会重新读取公司空调目录和状态，按“开机 + 制冷 + 设定温度低于 26℃”判断是否可调温。
- 调温前会重新核验授权和控制绑定；未知、关机、非制冷或状态变化时不自动下发。
- 每个检查点会保存 `ac_inspection` 观察结果，并区分满足条件、已满足、未下发、未知和未核验等结果。

当前缺口是同一业务事实被拆散在多个位置：

- 条件写在 scanner 的硬编码判断中，没有完整保存在 `AcInspectionSpec`。
- 小程序 `task-detail-view.mjs` 和 `TaskProposalCard.vue` 又各自硬编码了一套条件文案。
- `interval` 只表达起止时间，不能表达检查频率。
- `repeat` 与空调检查被当前校验互斥，无法形成“每天/工作日，在窗口内每 30 分钟检查”的周期计划。
- `label` 同时承担标题、范围、动作、条件和时间说明。模型生成的长句直接进入卡片，随后被列表或窄屏布局截断。

因此这不是单纯的文字优化，也不是先做一个更复杂的任务编辑器；需要先把“条件、动作、时间、范围、标题”拆成稳定的业务字段。

## 3. 推荐的最小业务模型

继续使用现有任务模型。空调节能任务仍然是一个周期计划，每次发生时生成一个有限窗口的任务，窗口内部由服务器生成固定检查点。

建议把 `read.ac` 扩展为窄领域结构：

```ts
{
  mode: "inspect" | "adjust_to_26",
  condition: {
    power: "on",
    mode: "cool",
    setpoint: { operator: "lt", value: 26 }
  },
  action: {
    setpoint: 26
  }
}
```

`inspect` 可以只保存 `condition`，`adjust_to_26` 保存条件和动作。服务器仍负责校验结构，不允许模型提交任意条件字段或任意比较表达式。

周期计划沿用现有 `repeat`，增加一个有限的监测窗口和检查频率：

```ts
{
  repeat: { frequency: "daily" | "weekdays" | ... },
  monitoringWindow: { startsAt: "09:00", endsAt: "18:00" },
  cadenceMinutes: 30,
  read: { ac: { ...conditionAndAction } }
}
```

创建或发生时，服务器根据窗口和频率生成检查点，并执行以下约束：

- 每次发生只生成当前窗口的固定检查点，不由模型逐个生成时间戳。
- 检查点必须落在窗口内，按时间升序排列。
- 频率首期使用有限预设，例如 15、30、60 分钟；是否开放 10 分钟需先做真实目录读取耗时和网关压力基准。
- 每次发生设置检查点数量上限，超过上限时拒绝创建并给出可调整建议。上限值应在基准测试后冻结，不在本轮猜定。
- 每个检查点读取同一份固定设备成员快照，但执行前重新做授权和设备状态核验。
- 暂停周期计划只影响未来发生；已经生成或正在执行的当前发生按现有任务语义处理，不回填错过的检查点。

首期只支持每天、工作日等已有重复规则能稳定表达的规则。节假日、复杂日历、天气条件和任意组合条件暂不加入。

## 4. 用户看到的任务结构

标题只承担“这是什么任务”，其他事实分行显示：

```text
公司空调低温调节

范围 · 公司空调 49 台
时间 · 每天 09:00–18:00
频率 · 每 30 分钟检查
条件 · 已开机 + 制冷 + 设定温度 < 26℃
动作 · 满足条件时设为 26℃
限制 · 不开机、不改模式、不改风速
```

每次发生或任务报告再显示结果：

```text
本次检查 18 次 · 检查 49 台
满足条件 6 台 · 已调节 6 台
已是目标温度 21 台 · 不满足条件 20 台
状态未知 2 台 · 回读待核验 1 台
```

这样用户可以在确认前判断任务是否正确，在执行后判断“检查过什么、命中了什么、改了什么”，而不需要从任务名称猜测条件。

## 5. 任务命名方案

### 5.1 新任务使用短标题

对于没有明确指定名称的新任务，标题由服务器根据结构化事实派生，不让模型把整句需求拼进标题。建议控制在约 24–32 个中文字符以内：

- `公司空调低温调节`
- `运营部空调低温调节`
- `公司空调温度巡检`
- `每日用电日报`
- `26楼运营办公区照明关闭`

服务器可根据设备范围、动作类型和任务类型组合标题；标题生成规则应是确定性的，便于测试和跨入口一致。

### 5.2 用户明确命名时保留用户意图

如果用户明确说“把它叫作夏季办公区节能”，保存为用户标题，但仍限制长度并做空白归一化。标题旁边继续显示结构化的范围、时间、条件和动作。用户标题不应承担这些字段的唯一表达责任。

### 5.3 兼容历史任务

历史任务的 `label` 不回写、不批量改名，保证历史记录和审计事实稳定。新标题规则只作用于新提案及后续编辑；旧标题在列表中使用现有文本，详情页通过独立字段补足条件和时间。

### 5.4 UI 约束

- 任务列表标题最多两行，超出后省略；关键条件不能只放在被截断的标题中。
- 提案卡、详情页和任务列表使用同一套标题派生和事实投影。
- `task.label`、`repeat`、`interval`、`condition`、`action`、`scope` 分开渲染。
- 不通过缩小字体、强制完整显示长标题来解决信息问题。

## 6. 推进顺序

### A. 先修事实和展示契约

不开放周期执行，先完成：

- 扩展并校验 `AcInspectionSpec.condition/action`。
- 让 scanner 从结构化条件读取判断依据，保留服务器安全白名单。
- 统一 `task-detail-view.mjs`、`TaskProposalCard`、`TaskDetailContent` 的条件和动作投影。
- 引入短标题派生，保留历史 `label`。
- 补充提案、详情和结果文案的窄接口测试。

验收标准：用户看到的标题、条件、动作、时间和范围互不混淆；同一任务在提案卡、详情和报告中表达一致。

### B. 实现一次性有限窗口

先允许一个未来窗口内按固定频率生成检查点：

- 服务器生成检查点，不依赖模型生成时间列表。
- 复用现有 scanner 的读取、授权、控制绑定、回读和结果记录。
- 验证多个检查点下不会重复下发同一状态下的无必要动作。
- 验证状态未知、设备离线、授权变化、绑定变化和回读失败时的结果收口。

验收标准：一次有限窗口任务能够完整展示每个检查点及最终汇总，且没有未经确认的额外控制。

### C. 接入周期计划

在一次性窗口稳定后，复用现有周期计划生命周期：

- 每天/工作日创建周期计划。
- 计划卡显示下一次窗口和检查频率。
- 暂停、恢复、删除沿用现有计划管理。
- 当前发生和历史发生使用标准任务记录，不覆盖旧结果。
- 不为周期空调另建一套通知或报告系统。

验收标准：暂停只影响未来发生，恢复不补执行；历史结果仍可查看；计划失败时能够说明是哪个检查点、哪个设备和哪种结果。

### D. 最后做视觉和真机验收

先用小型原型验证四个状态：待确认提案、已创建周期计划、检查进行中、检查完成报告。确认信息层级后再改生产 Vue。生产验收覆盖窄屏标题、条件可读性、周期开关、任务详情和结果汇总。

## 7. 必须保留的安全边界

- 只有满足条件且仍在当前授权范围内的空调才允许调温。
- 关机、非制冷、状态未知、状态过期或控制绑定变化时不自动下发。
- 检查点之间不因为上一次失败而盲目重试；下一次检查必须重新读取并重新判断。
- 调温动作只修改设定温度，不开机、不改模式、不改风速。
- 周期计划创建和会产生物理副作用的动作仍需显式确认。
- 任何条件扩展都必须先进入服务器白名单和结果模型，不能只在前端增加文案。

## 8. 社区经验及本项目取舍

Home Assistant 将自动化拆为 trigger、condition、action，并在触发后再检查条件；它还把自动化名称、描述、区域、标签与触发/条件/动作分开管理。这个分层适合借鉴，但本项目只取结构化边界，不引入它完整的通用自动化配置面板：

- https://www.home-assistant.io/docs/automation/basics/
- https://www.home-assistant.io/docs/automation/trigger/
- https://www.home-assistant.io/docs/scripts/conditions/
- https://www.home-assistant.io/docs/automation/action/
- https://www.home-assistant.io/docs/automation/editor/
- https://www.home-assistant.io/docs/automation/testing/

Home Assistant 的命名建议强调短名称，把位置放进独立的区域/楼层元数据；openHAB 的规则模型也把唯一 ID、名称、描述和标签分开，名称用于搜索和排序，描述用于补充上下文。这直接支持本项目把标题和条件、范围、时间分开：

- https://www.home-assistant.io/docs/configuration/customizing-devices
- https://www.home-assistant.io/docs/organizing/labels/
- https://www.openhab.org/docs/configuration/rules-dsl
- https://www.openhab.org/docs/tutorial/rules_basic.html

## 9. 附属探索：定时任务执行情况通知中心

定时任务不能只在创建时显示“已启用”。用户，尤其是管理者，还需要在任务发生后快速知道：执行了多少次、成功和失败多少次、哪些设备受到影响、失败原因是什么，以及是否产生了可解释的节能收益。

这部分建议复用现有任务结果、任务报告和通知中心，不另建一套执行记录系统。通知中心首先是任务结果的查询投影，任务和阶段结果仍然是事实来源。

### 9.1 第一版通知内容

每次周期任务发生后，生成一条可回到任务详情的通知摘要：

```text
公司空调低温调节
今天 09:00–18:00 · 共检查 18 次

检查设备 49 台
成功调节 6 台 · 已满足目标 21 台
未满足条件 20 台 · 状态未知 2 台
回读待核验 1 台

失败原因 · 2 台设备状态读取失败
受影响设备 · 空调-运营部-03、空调-会议室-02

节能估算 · 预计减少运行功率约 3.2 kW
估算依据 · 调节前后状态与历史同类时段对比
```

通知摘要只展示最重要的汇总，点击后进入任务详情查看：

- 每个检查点的检查数量、命中数量和下发数量；
- 成功、已满足、跳过、失败、未知和未核验的设备明细；
- 失败原因及影响设备；
- 任务范围、条件、动作和执行时间；
- 节能估算的数值、单位、时间范围、比较基线和数据完整性。

### 9.2 执行事实和通知状态分开

通知中心至少区分以下状态：

- 任务结果：`completed`、`partial`、`failed`、`unconfirmed`、`missed`；
- 通知处置：未读、已读；
- 设备结果：已调节、已满足、跳过、失败、未知、回读待核验。

“通知已读”不能代表任务已成功，也不能代表设备已经恢复。通知点击后应能回到对应的任务、发生记录或失败设备列表。

统计口径也要分开：

- **检查点统计**回答“本次计划检查了多少轮”；
- **设备统计**回答“多少台设备被检查、满足条件、实际调节或失败”；
- **任务状态**回答“本次发生整体是否完成、部分完成、失败或结果未知”。

例如同一台空调在 18 个检查点中被调节一次，不能计为 18 台成功设备；它应表现为“18 次检查、1 台实际调节”。

首期通知受众建议限定为任务创建者和拥有该任务/区域查看权限的管理者。通知中心先做站内查询和已读状态，外部推送继续留在后续范围。

### 9.3 节能情况的证据等级

空调设定温度变化后的真实节电量通常不能仅由一次控制结果直接得到。因此通知中心必须明确区分：

1. **实际能耗**：有对应电表、完整时间窗口和可比较数据时，展示真实读数与比较结果。
2. **节能估算**：只有空调状态、设定温度变化和历史基线时，展示估算值、估算区间和计算依据。
3. **无法估算**：缺少稳定基线、能耗数据不完整或时间窗口过短时，显示“暂无法可靠估算”，不能展示虚假的节电数字。

首期建议只做有依据的估算摘要，不做复杂节能模型：

- 记录调节前后的设定温度、设备数量、持续时间和可用状态；
- 优先使用同设备、同时间段的历史功率或能耗作为基线；
- 没有历史基线时，不能用设备数量乘固定经验值冒充实际节能；
- 估算结果必须携带 `estimated` 标记、基准时间段、单位和覆盖率；
- 后续有电表报告快照时，再补充区域或公司级实际能耗对比。

通知文案应使用“预计”“估算”“数据覆盖不足”等明确措辞，不能写成“已节省 X 度电”，除非对应电表数据已经完成可比性校验。

### 9.4 建议的附属推进顺序

- **N1：结果汇总**：从现有 Task/Phase 报告生成成功数、失败数、跳过数、未知数和受影响设备。
- **N2：通知中心投影**：复用现有任务通知入口，增加周期任务结果摘要和任务详情深链。
- **N3：失败定位**：支持按检查点和设备查看失败原因、回读状态和处理建议。
- **N4：节能估算**：先接入明确的历史基线和数据覆盖判断，再展示估算；没有足够证据时展示不可估算。
- **N5：管理层摘要**：在单任务详情稳定后，再考虑按日、周、月汇总任务成功率、失败设备和节能结果。

这条附属线不应早于 N1 的真实结果收口。否则通知中心只能展示模型生成的总结，无法证明任务实际完成情况。

## 10. 本轮不做

- 不建设通用 `ConditionEngine`、规则 DSL 或可编程表达式。
- 不把空调周期检查拆成新的顶层业务对象。
- 不支持任意分钟数、节假日、天气、能耗阈值等复杂条件。
- 不同时扩展视频、消防、能耗报告和通知渠道。
- 不通过标题截断、缩小字体或隐藏条件来掩盖数据模型缺失。
- 不在方案阶段修改生产代码、部署 Runtime 或控制真实设备。

## 11. 下一步需要冻结的三个选择

推荐默认值如下：

1. 首期重复规则：每天、工作日；
2. 首期检查频率：15/30/60 分钟预设，模型可建议 30 分钟但须经用户确认，服务器不静默套用默认值；最低频率和单次检查点上限由真实网关基准冻结；
3. 新任务默认使用服务器派生短标题，用户明确命名时保留用户标题。

这三个选择确认后，先做 A 阶段的事实/展示契约，再做一次性有限窗口原型和实现；周期计划放在一次性窗口通过真实模拟执行验收后接入。
